### 软件供应链成为最低阻力入口

**Joel De La Garza：**

安全领域有一句老话：门既然开着，就不要费力撬锁。攻击者总是从最容易的路线开始，再逐级尝试更困难的办法。

**Feross Aboukhadijeh：**

模型在这一点上很像人类攻击者。进入一家公司的最容易路径，如今常常是 software supply chain。公共软件仓库几乎没有足够的人工审查，开发者又很可能直接安装其中的软件包，所以发布恶意包成了低垂果实。

AI 不只是攻击者，它也可能成为入口。越来越多非专业开发者让模型编写代码、生成图表或完成数据处理，但使用者并不知道模型安装了什么依赖。表面上这是科幻式风险，底层其实仍是最基础的问题：企业到底运行了哪些软件，又如何验证这些软件。

最近公开的一起事件里，一个几乎所有大型企业都使用的 CI/CD 工具被模型直接找出了 zero-day。这处供应链节点如此关键，企业到底应该怎样理解这种风险？

很多公司还有处于维护模式、已经无人负责的 legacy applications。面对这些系统，行业必须设计新的快速修补方法。否则，模型加快攻击的速度，而防守方仍停留在几周或几个月的升级周期，时间差会迅速扩大。

这里最难处理的地方，是企业依赖的并不是少数几个边界清楚的产品，而是层层嵌套的软件包。一个应用可能间接依赖许多由单个志愿者维护的组件。安全团队即使知道某个底层包有问题，也未必能直接替换，因为升级会改变接口、触发兼容性故障，并迫使业务代码一起重构。

就在清理工作进行时，Hugging Face 的首席技术官发来消息，请我们查看一起与 OpenAI 有关的新事件。那起事件确实使用了 zero-day，但 incident response 清单里排在最前面的仍然是被盗凭证。模型遵循的还是训练出来的最低阻力路径。

### npm worm 从设想变成现实

**Joel De La Garza：**

Feross，过去十八个月你一直在为这类风险报警。我们录制节目时，似乎正有一个大型 npm 仓库遭到持续攻击？

**Feross Aboukhadijeh：**

规模不只是一个仓库，而是几百个 repositories。这是一条 worm。

业内讨论 npm worm 已经很多年。设想是：攻击者先给一个软件包植入后门，开发者安装后，恶意代码从开发者机器窃取访问权限，再利用这些权限感染开发者维护的其他包。这样，蠕虫就能自我传播，快速接管 npm 生态。

这个想法在博客里流传多年，一直没人真正实施，直到 Zachary 找到实现方法。我们有充分理由怀疑相关 malware 是 vibe coded，攻击者借助 AI 快速编写了代码。某个 threat group 甚至把自己用模型生成的工具包开源，供其他人复制，随后已经出现多起模仿攻击。

传统 malware authors 往往不是优秀程序员。因此，如果恶意代码质量突然变好，反而可能说明它由模型生成。

攻击者还会利用开发者机器上已经安装的 AI 工具继续横向移动，并避开传统安全产品。有时真正的 payload 不是可执行文件，而是一段 prompt。它可能只是 Markdown 文件中的指令，要求本地 Claude CLI 搜索整个系统，找出密钥和其他有价值的信息。

EDR 很可能不理解一个 JSON blob 或 Markdown 文件为何危险。开发者机器平时就允许代码助手频繁读取文件系统、运行命令，各种异常操作混在正常工作流中，攻击行为因此不再显眼。

**Joel De La Garza：**

这意味着防守方不能只检查传统二进制文件。一个看似无害的文本文件，也可能在本地 agent 读取后变成操作指令。若 agent 已获准调用 shell、读取项目目录和访问云服务，那么 prompt 本身就能借用这些合法权限执行攻击。

**Feross Aboukhadijeh：**

没错。开发环境天然比普通员工终端更开放，编译器、包管理器、命令行工具和云端凭证都集中在一起。模型辅助编程又进一步增加了正常活动的噪声。企业必须同时理解代码来源、安装行为、agent 权限和凭证范围，单独依靠终端告警无法覆盖整条链路。

今天的事件波及几百个软件包。我们已与一名受影响的 maintainer 通话并提供帮助。Socket 约一半工程师本身就是开源维护者，首席技术官过去还担任 npm 的首席技术官，因此团队与社区联系紧密。

这名维护者仍在调查原因。按照目前的初步迹象，问题可能不是他的个人设备被攻破，而是一项配置不安全的 GitHub Action 被攻击者利用。恶意代码在那里运行，并从环境中取出 token。现在仍是早期判断，我们还在核实。

### 凭证一旦落地，防线就已存在缺口

**Dylan Ayrey：**

npm worm 通过 post-install hook 感染系统后，会立刻搜索 credentials。找到一枚凭证，就进入下一套系统。因此大家经常问，如何把 endpoint 上的凭证清理干净。

我们可以扫描 Downloads、Documents 等目录，但用户 home directory 里本来就有 npm、Amazon 等工具有意写入的凭证，这是它们的正常工作方式。即使把秘密迁移到 HashiCorp Vault 或 1Password，访问这些服务所需的凭证仍要存在 endpoint 上。

除了阻止蠕虫传播，企业怎样才能限制后续利用的 blast radius，防止攻击者窃取凭证并跳到下一套系统？

**Feross Aboukhadijeh：**

生态正在出现一些积极变化。npm 已宣布，计划从 2027 年 1 月起，所有新版本发布都必须通过真人交互式 2FA 确认。这可能彻底终结目前这种 worm 自我发布机制。

代价是高度破坏性。整个生态大量依赖自动化发布，例如 GitHub Actions 自动触发新版本。强制真人确认会让现有流程普遍失效，但我认为这是正确选择。

问题在于，其他仓库可能完全由志愿者运营，没有 GitHub 和 Microsoft 的资源支持，也就未必能采取相同措施。类似攻击仍会在那些地方继续出现。

从根本上说，home directory 不应该长期保存能够发布软件包的长效 token，尤其不该让拥有大量维护权限的人以这种方式工作。

短期凭证、最小权限和及时吊销都很重要。发布权限不应顺便包含读取其他系统的能力，一枚 token 也不应同时控制几十或几百个包。否则，一次开发机感染就会被自动放大成整个依赖网络的事故。

强制 2FA 之所以被称为近乎“核选项”，就在于它会牺牲大量无人值守的便利性。现有 release pipelines 假定机器可以永久持有发布凭证，并在测试通过后自动推送版本。新制度要求真人再次确认，等于重写生态长期依赖的信任模型。迁移过程会很痛苦，但与蠕虫获得自动发布能力相比，这种摩擦是可以接受的。

这让我想起一位朋友。他是非常高产的 npm maintainer。许多年前，我看见他输入密码，虽然没看到内容，但输入速度快到足以判断密码只有大约六个字符。我问他为什么使用这么短的密码。

他住在 Denmark，那是一个高信任社会。他的想法是，自己不愿生活在恐惧和怀疑中。但我提醒他：你是在互联网上。攻击者很快就会猜出六位密码。

世界顶级开源维护者未必接受过安全培训，也没有安全团队和企业级 SLA。他们只是把代码放到 GitHub。因此，软件使用者也必须承担责任。企业不能把网上找到的代码直接部署进 production，出事以后再把责任全部推给维护者。

这不是要把困难全压在个人身上，而是说明责任分布在维护者、仓库运营方和使用者之间，每一层都还有可以改进的地方。

### 资金不足是供应链安全的硬约束

**Dylan Ayrey：**

你提到不同 package managers 拥有的资源差异很大。我们曾在 RubyGems 发现一个 caching issue，可以据此窃取任意 token、进入任意账户并给任意软件包植入后门。

RubyGems 团队没有回避问题，合作非常顺利，也迅速修复了漏洞。但它仍是资源不足的组织。企业选择 Ruby 或 npm 技术栈时，是否应该把仓库背后有没有专业安全团队纳入判断？

**Feross Aboukhadijeh：**

如果企业已经围绕某种语言建立了系统，仅因为仓库资源不足就要求它完全切换语言，并不现实。更可行的办法是为这些基础设施提供资金。

它们并不需要夸张的预算。多聘请一到五名安全人员，就可能给基金会带来巨大改善。依赖这些软件的企业应该赞助对应项目，尤其是 package registries。只要若干公司分别提供二万五千或五万美元，就足以实质改变维护团队的能力。

这里不能把开源理解成“免费获得且由别人负责”。企业从公共基础设施中持续获得商业价值，也应承担一部分审计、响应和修复成本。与一次供应链事故造成的停机、凭证轮换和客户通知相比，提前资助几名安全人员的金额很小。

**Joel De La Garza：**

企业还可以提供 inference 资源，用于自动运行测试和补丁。安全从业者经常接到同一种咨询：怎样保护公司、业务和产品，但又不愿雇人、不愿花钱，还希望尽可能便宜。这种要求本身就是矛盾的。

### 二〇二六年是软件供应链风险进入主流的一年

**Joel De La Garza：**

感谢二位来到 Las Vegas。大家当然也是为 Black Hat 而来。你们今年观察到什么，现场情绪有什么变化？

**Feross Aboukhadijeh：**

对 Socket 来说，最明确的判断是：二〇二六年是 software supply chain 之年。很讽刺，我们参加会议时团队还在同步处理一场攻击。攻击者似乎特别喜欢在 RSA 和 Black Hat 期间启动 npm worms，可能因为安全人员都集中在会场。

过去几年，我们必须反复向企业解释供应链攻击不是理论风险。客户常问“真实发生的概率到底有多大”，我们只能用案例说明攻击路径。

今年这个问题终于进入主流媒体，商业媒体也开始把相关事件放到重要版面。虽然当前事件给团队带来巨大痛苦，但公开关注能给安全负责人争取预算和优先级提供支持。从长期看，这像一次强制接种：行业会因为真实损失而开始修复系统。

**Dylan Ayrey：**

我们最近发现一枚数据库凭证，它可以访问相当于全球人口 3.6% 的个人身份信息。之所以发现它，是因为我们与 Hugging Face 等平台合作，扫描并吊销暴露在公共数据中的有效 credentials。

各平台从许多来源收集的数据形成了集中扫描点，这反而让我们能够一次清理大量风险。

secrets 管理的旧一代公司正在发生变化，HashiCorp 和 CyberArk 都被收购，这推动行业重新讨论 non-human identity：机器和代理的凭证怎样更容易使用、怎样及时吊销，以及怎样突破过去长期没有解决的问题。

**Joel De La Garza：**

风险还会倍增。过去可能是一名用户拥有十个密码，未来则是十个 agents 各自拥有十个密码。

**Dylan Ayrey：**

没错。agents 目前怎样取得、保存和调用 secrets，仍然是未经治理的 Wild West，也是我们正在努力解决的问题。

传统身份系统大多围绕人设计：一名员工有一个账户，可以接受多因素验证，也可以在离职时统一撤权。agent 却可能临时创建、并行运行并频繁调用多种服务。若企业直接复制人类账户的长效凭证给它们，身份数量、权限组合和泄露面都会快速膨胀。

真正需要的是可追踪的 non-human identity：每个 agent 都有清楚的任务边界，只取得完成该任务所需的最小权限，凭证寿命足够短，异常行为可以立即吊销，而且企业能够回答某次访问究竟由哪个模型、哪段工作流和哪名授权者发起。当前行业离这个状态还有明显距离。

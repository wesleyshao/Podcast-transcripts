# How To Design In The Agent Era

## Transcript

### Agent 能加速执行，但伟大公司的设计不能交给默认答案

**Stephen Haney：** Agent 可以让人快很多，省掉大量工作，也能代做翻译、尺寸适配等任务。但 Paper 相信，设计中的人类部分仍然不可替代。我们想做的不是让模型接管设计，而是让人能与 Agent 一起高速工作。

创始人很容易直接采用 Claude Design 或其他模型吐出的第一版，但那不会让产品在人群中脱颖而出。设计是非常强的差异化手段。回顾过去十到二十年的伟大公司，几乎每一家都有出色设计。如果你想成为那类公司，就必须在设计上投入照料，让外部世界一眼看出你不是又一个平均产品。

**Aaron Epstein：** 今天的嘉宾是 Paper 创始人 Stephen Haney。Paper 是一款 AI 原生设计工具，最近在设计行业增长很快。YC 内部已经大量用它处理设计工作。Stephen，欢迎来到 Design Review。

### Paper 为什么从 HTML 与 CSS 开始

**Aaron：** 先介绍一下 Paper 是什么。

**Stephen：** Paper 是一款 Agent 原生设计工具。最关键的技术选择，是直接以 HTML 和 CSS 作为渲染引擎。传统设计工具通常有自定义渲染系统，Agent 不熟悉那些内部格式，因此会消耗更多 token、运行更慢、准确率更低。HTML 与 CSS 大量存在于训练数据中，模型天然知道怎样读写。

团队现在约十二人，都是设计师和工程师。项目起点不是竞争分析，而是我们真的热爱设计，想为下一个时代做出最好的设计工具。

**Aaron：** 只有十二人很难相信。很多从零开始、自己就采用 AI 原生工作流的创始人，都在寻找同样原生的设计环境，而且经常提到 Paper。你为什么开始做它？现有工具哪里不够？

**Stephen：** 它首先来自我对设计的兴趣。我最早是单人创始人，Paper 只是一个不断延续的副项目。有几个月我一直怀疑是否有人关心，后来需求突然变得明确。无论市场怎样，我本来就会做这件事。

做创业公司应该选择即使没人要求也会继续做、而且自己有 founder-market fit 的事情。我最匹配的领域就是为创意专业人士做工具。每天醒来做创意工具，我很难觉得那是坏日子。这个动机先于市场、竞争和商业计划。

我们很尊重 Figma，它为设计行业做了很多，如今也在大型企业市场取得巨大成功。但一家企业规模变大并向上销售后，也许会给一款重新聚焦设计师本人的新工具留出空间。AI Agent 带来的变化太大，我们可以从 HTML、CSS 和 Agent 原生交互重新构建下一代工作环境。

**Aaron：** “Agent 原生”具体意味着什么？

**Stephen：** 最初采用 HTML 和 CSS，其实是为了解决设计师与开发者的交接。我们希望设计师仍拥有类似 Figma 或 Sketch 的自由画布，不需要知道底层就是 HTML，但交给开发者时不再经历格式转换。

后来发现，为人类做好的交接也正好适合 Agent。模型读取 Paper 文件时，直接读 CSS，就知道元素是什么。Paper 一方面是设计工具，另一方面也是 Agent 的可视化界面。用户不只包括设计师，也有销售和工程师，因为自然语言提示并非所有任务的最佳输入。很多时候，直接拖动、框选、绘制比描述“把左边第三个元素向下移动”快得多。

**Aaron：** 软件越来越容易做，真正的瓶颈反而变成“做什么”和“怎样做得有辨识度”。Paper 如何帮助创意流程？

**Stephen：** 世界正在产出比过去更多的软件，工程团队也快得多，但我没有觉得软件体验因此普遍变好。过去六个月，很少有新软件让我惊叹。我从小就是软件爱好者，别人说“Paper 是很棒的软件”，对我来说是最高赞美。

我们想让有品位、懂产品的人跟上工程产能，不要被迫退到 IDE 里只做原型，而是仍能做传统设计工作，只是速度接近提示和 Agent。代码产出快，不等于产品自然会好。

### Shaders、图像生成与把品牌资产当产品做

**Aaron：** 直接演示吧。

**Stephen：** 界面与常见画布工具很相似。因为 Paper 用浏览器渲染，也能自然渲染 Shader。Paper Shaders 是我们开源的 WebGL 动画库，同一个 Shader 改参数就能形成完全不同的视觉效果。品牌设计师尤其喜欢它，因为可以快速获得带动态、又能继续定制的品牌表现。

**Aaron：** YC 最近经常用这些效果。它看起来现代、前沿，一年前却需要大量专业开发。YC 的设计负责人 Eva 为 Startup School 做了带 YC 品牌和参与者姓名的动态入场券。被录取者拿到后可以互动，也愿意分享。设计同时改善体验和传播。

**Stephen：** 我们希望把以前需要图形程序员的效果交给设计师。AI 产品尤其需要表达加载和思考状态，静态稿很难传递。用户可以从预置效果开始，调颜色、速度、混合模式，也能把一种噪声喂进半色调点阵，得到更克制的纹理。

团队甚至研究真实纸张上的随机结构，再用代码建模。我们愿意花看似荒谬的时间打磨这些细节，这也是 Paper Shaders 与普通效果库不同的原因。Quarter 制作财报海报时，就用 Paper 做出很好的复古视觉。

Paper 还有图像生成库，能一次调用多种模型。用户可以只选一个模型，也可以用“variety pack”同时探索四条路线。模型各有优劣，我们会随新模型出现调整组合。生成结果可以再次作为输入，与 Shader 合成；也可以矢量化、提取颜色，迅速建立新的配色和材质。设计师每天不仅做产品界面，也要做社交媒体图片、活动视觉和品牌资产，所以我们不想把产品设计与品牌设计割裂。

**Aaron：** Figma 在很多人心中首先是产品设计工具，品牌和图形工作虽能做，却不是最初形态。Paper 从一开始就把两者放在一起。

**Stephen：** 对，这是价值观选择。Paper Shaders 甚至可以看作营销预算，而不只是产品开发。与其购买广告，我们把钱用来做一个全世界都能免费使用的库。它吸引注意，也对社区真正有用。

用浏览器做真实渲染还有一个直接好处：设计师不只是在画一张“动画应该长这样”的静态示意图，而是在设计工具里看到最终可运行的动画。过去，产品设计师要向开发者解释 AI loading state 如何变化，常常只能画多个状态或附上一段文字；现在可以直接调整 Shader 参数，观察运动频率、颗粒大小、颜色过渡和混合方式，决定什么才符合品牌。

我们演示的 halftone dots 会把另一种 neuro noise 效果输入点阵。它不是简单覆盖两张图，而是在算法层面让一种纹理调制另一种纹理。设计师可以继续改 blending mode，让光影更像真实材料。团队研究纸张，并不是为了做一个“纸张滤镜”噱头，而是想理解自然随机性为什么看起来不机械。许多生成效果的问题，就是随机数在数学上随机、在视觉上却没有真实世界的层次。

Quarter 的财报海报是一个很好例子。它需要在固定信息结构内每期有新鲜感，又要保持品牌识别。过去这种复古印刷质感要在多款专业软件间切换，如今可以在 Paper 内快速建立模板，再通过参数变化得到新一期作品。效率提高的同时，设计师仍决定哪些变化属于品牌、哪些只是炫技。

图像生成演示里，我们输入“一个若有所思、望着月亮的男人插画”，让四种模型同时输出。重点不是一次得到正确答案，而是快速观察可能性空间。某个模型构图好，另一个材质好，第三个色彩更适合品牌，人可以选择一条路线继续。把已有 Shader 复制为图像，再作为参考喂给生成器，就能让新插画继承当前视觉语言，而不是每次从泛化提示重新开始。

颜色提取也不是展示功能列表。设计师经常从摄影、插画或活动海报中发现一组好颜色，过去要手工吸取、整理、命名。Paper 可以提取主色并立即摆到画布上，继续测试文字对比和组件组合。矢量化则让生成图不止停在位图素材，而能进入可编辑品牌系统。这些动作连起来，才构成从探索、筛选到系统化的品牌工作流。

我们还制作了 Paper Mono 字体。多数等宽字体为终端设计，不适合同时用于品牌营销和代码。Paper Mono 想成为一个全面、易读的等宽字体，尤其重视数字辨识度。字体和周边同样是营销：Eva 在纽约晚餐时遇到穿 Paper Mono T 恤的人，全世界当时大概只有一百件，这种真实认同比购买曝光更有价值。

### 设计到代码不再是一次性交接

**Aaron：** 你说 Paper 最初要解决 design-to-dev handoff，演示一下。

**Stephen：** 画布上的 Shader 本来就是 React 组件，右键即可复制为 React。设计师把动画调到自己满意的状态后，可以直接拿到实际代码。任何 Paper frame 都是网站结构，也能复制成 Tailwind 或 React。

最初这已经够有用。到 2025 年 12 月，Claude Code 引发新一波增长，我没想到设计师会进入终端，但事情确实发生了。设计师开始使用本地代码仓库，学习 GitHub，我们必须进入桌面端。

现在的新 Agent 技术栈通常包括 Cursor、Claude Code 等多个 Agent，Paper 作为与它们沟通的视觉层，再加 GitHub 和代码审查。Conductor 等产品还把运行 Agent、提交和合并代码整合到一个界面里。Paper 与 Conductor 的组合在社区里很常见。

我们在桌面应用中内置 MCP server。假设对 Conductor 说：“在 Paper 里做一个向 YC 问好的小 frame。”Agent 会先调用工具了解可用字体和页面环境，再发送 HTML。Paper 能直接渲染，不存在中间翻译。少一层格式转换，就少用 token、运行更快，也减少奇怪幻觉。

另一个例子是让 Cursor 读取 Paper 自己代码仓库里的 `colors.css`，把它渲染为画布上的 style guide。团队也会让它审计现有代码、生成组件架构图。设计工具不再躺在技术栈旁边，而是进入同一工作循环。

**Aaron：** 演示里，Conductor 先询问 Paper 页面有哪些字体、画布如何设置，再发送写入 HTML 的工具调用。屏幕一边是 Agent 的调用过程，另一边实时出现 frame。这里没有“把模型生成的抽象设计格式翻译成浏览器格式”的步骤，Agent 写出的就是浏览器理解的东西。

**Stephen：** 这会同时改善三个指标。第一，省 token，因为不必让模型学习一套长而陌生的节点描述；第二，更快，因为少一次转换；第三，减少幻觉，因为 HTML、CSS 的语义和调试方式是模型最熟悉的内容之一。Paper 的引擎接到 HTML 就渲染，不需要猜一个自定义属性应映射成什么。

把 `colors.css` 变成 style guide 时，Cursor 读的是 Paper 自己真实代码库，不是我为演示准备的简化文件。它可以把颜色 token、变量关系和使用方式展示在画布上。团队因此能反向审计：代码里实际存在多少颜色，哪些名称重复，哪些组合未达到对比要求。设计稿不再是对系统的理想化描述，而是代码现状的可视化。

**Aaron：** 旧流程里，设计师可能维护一套组件，工程师维护另一套。任何一方更新后，另一方都要人工同步；久而久之，大家知道两边不同，却没人有时间清理。

**Stephen：** 所以 Paper 用户越来越少把“设计文件”当唯一真相。真实运行代码才是事实来源，Paper 是读取、理解和修改它的界面。尚未完成画布 components 功能当然会给传统设计师带来不便，我们正在做；但 Agent 原生团队已经用“需要时从代码召回”替代了很多本地组件维护。

Paper Snapshot 也遵循这个思路。用户打开真实网站，选中一个区块，复制进 Paper 后，文字仍是文字，按钮仍有布局和样式，元素可以单独修改。若只截屏，Agent 要从像素猜 DOM，人也无法直接删掉一个节点。Snapshot 把“线上版本”变成可操作的起点，避免团队在过期截图上讨论。

**Aaron：** 过去设计师交稿后，开发者未必按原意实现；即使首次一致，代码继续变化，设计稿又不会同步。团队始终在争论哪一个才是事实来源。

**Stephen：** 很多公司实际维护两套 design system，一套在设计工具，一套在代码，长期同步几乎不可解。新的 Agent 原生团队把代码库当作 source of truth。Paper 还没有完成用户最想要的 components 功能，但在这种工作流里，缺少画布内组件也不致命，因为用户随时能从真实代码召回需要的组件。

我们还做了 Paper Snapshot 浏览器扩展，可以把线上网页直接复制到 Paper。它不是截图，而是可编辑的真实层和布局。设计从用户眼前的当前版本开始，修改后再写回代码，不必围绕一张失去结构的图片工作。

### 现场改版一：Legion Health 的内容清楚，细节却损害医疗信任

**Aaron：** 看用户提交的网站。第一个是 Legion Health：使用保险时精神科服务最低零美元，线上管理 ADHD、抑郁、焦虑、双相障碍等用药。页面顶部的小药丸、圆角模块很像模型的默认风格。

**Stephen：** 细节完成度确实不足。不同区块之间留下不自然的小缝，pill 也很泛化。但价值主张一眼能懂，这是重要优点。右侧图片表现用户获得服务后生活很好，虽然“在田野里开心”有点模板化，至少利益被可视化了。

需要改的是工艺、对齐和对比。精神医疗要求高度信任，而页面里元素没有认真对齐、颜色对比像 vibe coding 直接生成，会让人下意识追问：如果网站细节都没检查，医疗流程还有什么没检查？作为 YC 公司，它也可以更明确展示 YC 背书，增加社会证明。

我用 Paper Snapshot 把其中一段从线上页面复制进画布，得到可编辑结构，再让 Agent 根据工艺、对齐和对比做三种变化。简单提示通常已经够用。

**Aaron：** 多版本是获得灵感最快的方法。人有时知道不满意，却不知道目标长什么样。看三到二十个方向，就能说“我要第一版的结构、第二版的列表、第三版的层次”，迅速离开创意卡点。更重要的是，你只说“处理我在 Paper 里的选中项”，Agent 就知道上下文。

**Stephen：** 现场演示时我改变了选中项，Agent 一度改错对象，这也说明 selection 容易漂移。另一种更稳的办法是在 frame 上留 comment，然后告诉 Agent“处理我在 Paper 里的评论”。大型设计可以一次留下多条反馈，再让 Agent 逐项完成。

很多用户会让循环跑一整夜，生成数百个变化，第二天由人筛选、组合。服务器因此要适应 Agent 规模，任务量远超我们最初预想。设计流程开始从“人亲手画每一版”变成“人设方向、机器扩展、人做策展”。

模型生成第一版后，还会截图检查。若文字压到卡片上，它有机会自行修复；没发现时，人再明确要求处理 overflow。快模型适合演示，却更容易犯错，真实项目应选择当前最强模型。

我的模型选择会按任务变化。需要纯视觉品位时，Fable 和 Anthropic 的模型通常更好，但 Fable 很慢；要求遍历一百个画板、精确完成机械任务时，Cursor Composer 更合适；GPT-5.5 在速度和质量间比较均衡。Cursor 的 Agent harness 也不错，不偷懒，必要时会启动子 Agent。

这次三版中，一版列表很易读，另一版用主卡配侧卡的结构。我不会把任何一版直接当成终稿，而会从有潜力的分支继续生成。

### 两条最有效的去 AI 味规则：减少粗体，压缩字号层级

**Aaron：** 多版本会提供灵感，但设计仍来自模型，也会带着模型常见痕迹。怎样让它成为自己的东西，不是标准 AI slop？

**Stephen：** 第一，模型极爱粗体。尽量把 font weight 拉轻，会立刻显得更成熟。第二，模型喜欢同时用五到八种字号，尽量压到三种。Legion 这一版里，很多标签、标题和卡片内容根本不需要粗体。把 700、800 的黑重字降到 500 或更轻，页面马上干净、亲和。

再检查对比。支撑元素不应与主要信息抢注意力。卡片上的二、三、四这类装饰数字如果没有信息含义，直接删掉。模型常加小图标和编号来填满角落，人要问它是否真的传达内容。

Paper 首先是一款供人直接操作的设计工具，只是同时非常适合 Agent。用户不必为了删一个无意义数字重新写提示，可以点中、删除，布局自动回流。最好的工具取决于动作：有时提示最快，有时拖动和删除最快。Agent 不该把人锁在一条生成轨道上。

改完后，可以右键复制 React，这是较长路径；也可以直接让 Agent 把 Paper 里的选中设计写成代码库的新组件。它既读到刚完成的设计，也了解项目编码规范。如果组件已经存在，就直接更新。传统“交接”在这里消失，同一个人可以设计、实现、迭代和发布。

现场第一次指令实际上暴露了 Agent 工作流中一个常见小问题。我本来想让它修改 Legion Health 的服务卡片，却因画布上选择发生变化，让它碰到了另一个对象。自然语言没有错，引用对象错了。重新选择当然能解决，但评论更稳定：评论附着在具体 frame 上，Agent 可以先读取所有未解决评论，再逐条完成。大型页面有几十处修改时，这比人一直保持 selection 更可靠。

生成过程中，第一版的文字压到了卡片上。Agent 并非给出一次结果就结束，它会截图观察自己的输出，再继续调整。不过快模型有时看不出问题，人可以直接补一句“处理所有文字溢出”。这也是为什么演示结果不能被误解为 Paper 自动保证设计质量，工具只是让发现和修正错误的循环更短。

用户把 Agent 留到夜里生成几百版，听起来像暴力搜索，但对创意探索很有效。人不必逐版给方向，只需先设定边界，第二天把有价值的结构挑出来，再分支。服务器端却会看到与普通人类编辑完全不同的负载：一个用户的 Agent 可以持续创建和截图，调用量像一个团队。Paper 必须把系统设计到 agent scale，而不只是支持偶尔一次 AI 按钮。

**Aaron：** 三个变化不是为了投票选出“模型最喜欢的一版”，而是帮助人发现自己原先没有语言表达的偏好。我可能看到列表后才意识到信息更适合线性阅读，看到主卡加侧卡后才发现层次应该不对称。灵感来自比较，而不是模型替我决定。

**Stephen：** 对。接下来我会从每个有潜力方向再生成几版，也会自己拖动和删除。Fable 适合要求视觉判断的任务，但慢；Composer 适合大规模精确遍历；GPT-5.5 适合现场平衡速度与质量。所谓“最佳模型”没有单一答案，任务结构比排行榜更重要。

回写代码时，Agent 不只复制 HTML。因为它已经在同一代码库工作，会遵循项目的组件拆分、命名、样式方案和数据连接方式。若设计对应既有组件，它应修改组件而不是新造重复代码。人仍需审查结果，但设计与实现之间不再需要一份额外说明文档。

**Aaron：** 这让设计师真正拥有最后一公里。一个人可以完成过去一支团队的工作。

**Stephen：** 团队环境也一样会加速。核心不只是“一个人替代团队”，而是所有 Agent 工作都需要能用其熟悉格式交流的工具。

### 现场改版二：Sytex 首屏应该先回答“为谁解决什么”

**Aaron：** 第二个网站是 Sytex，主张加速现场基础设施运营：规划流程、现场执行，再把每个动作沉淀成可监测、可自动化、可提问的知识库。第一眼仍是超粗标题、发光效果、紫色和典型 vibe coding 配色。动画看起来不错，像 Kanban board，但我仍不确定具体产品是什么。

**Stephen：** 动画抓住注意力，却没有解释为什么施工或基础设施企业需要它。页面下方有工程车辆、戴安全帽的人用手机，看到那里才知道“现场”是建筑和重型运营，但关键线索藏在首屏以下。

我希望首屏更清楚地说明它为施工做了什么。AI Kanban 已经很多，Sytex 的行业特殊性是什么？设计问题不只是美观，更是用户能否马上获得这个答案。

另一个区块又用了四五种字号。用 Snapshot 抓进 Paper 后，我把 frame 命名为 Sytex，告诉 Cursor：最多保留三种字号，不使用粗体，所有字重为 regular 或更轻。命名、选中和评论都是向 Agent 指定对象的不同办法。

**Aaron：** 修改前，产品说明、卡片标题、辅助标签和数据各自使用不同字号，看似每项都被强调，最终却没有真正焦点。施工现场的视频是最能建立行业语境的证据，却刚好落在首屏以下。若用户没有继续滚动，便只会看到一个泛化的 AI 看板。

**Stephen：** 页面内容并非没有价值，问题是信息优先级没有被设计。第一屏应先出现现场运营对象、实际动作和与普通看板不同的结果，再让动画解释流程。视觉改良不能替代价值主张，只能让已经正确的内容更清楚。

Agent 执行时，我们把资深设计师长期积累的规则写入 Paper 指令，例如限制字号层级、避免默认粗体、检查可读对比。有人把这种效果归因于神秘模型或私有训练，其实很大一部分只是把基础专业判断稳定地放在每次生成前。模型仍可能犯错，但不必每一轮都从“不要把所有东西加粗”重新教起。

现场新版只是减少字号和字重，布局没有做夸张重构，却已经比原版更稳定。左右对照能看到，原版更像每个模块各自喊话，新版则让用户先读主信息，再自然进入细节。设计师真正要做的往往不是发明更多元素，而是让已有内容形成顺序。

**Aaron：** 这也说明 Agent 不一定要承担整个改版。人已经知道问题时，手动改几个字重可能更快；若要把同一规则应用到整站几十个页面，Agent 才有明显优势。选择工具的依据应是任务规模，而不是凡事都要显示自己在用 AI。

Paper 自己的模型指令也内置这些规则。有人问为什么生成结果更好，所谓秘密其实是团队资深设计师把基础 typography 和 contrast 经验写入了系统指令。专家给模型加一圈约束，就能省掉大量反复修正。

这次只改字号和字重，右侧新版已经明显更可信、更有意图。内容本身原来就不错，问题是表现方式暴露了“模型吐完即发”。设计当然主观，但去掉最常见的 AI 痕迹后，用户更愿意相信团队认真做过决定。

### AI 设计的四类高频痕迹

**Aaron：** 你最常见的 AI tell 还有哪些？

**Stephen：** 除了太多粗体和字号，还有卡片边缘那一两像素的彩色装饰线，以及任何内容都塞进卡片。模型会在一页放二十张卡，而不是先找更有意义的布局。让 Agent 生成二十种版式再选，通常都比默认卡片墙更好。

**Aaron：** 还有紫色、渐变、过多图标，以及字很小、全大写、字距拉开的 eyebrow 标题。很多 widget 不是为了沟通，只是为了填空间。模型像缺乏安全感的设计师，生怕哪里留白，便在角落放“一、二、三”和小徽章。

**Stephen：** 设计很大一部分就是删除。可以先多做，再不断收回。避免 Agent 风格的核心不是增加更多提示，而是删掉无功能的装饰。

模型偏爱粗体，是因为粗体在训练样本里很容易表达“重要”；偏爱多字号，是因为每个语义层都被单独映射成视觉层；偏爱卡片，是因为卡片是边界清楚、容易组合、在网页数据里高频出现的安全答案。这些选择各自都有理由，叠加起来却让页面失去整体秩序。

真正成熟的排版不会让每一级信息都争夺注意力。主标题、正文、辅助文字三层常常已经足够。字号更少以后，设计师要用间距、位置、段落关系和内容顺序表达层级，这些手段更克制，也更接近用户阅读方式。把所有标题加粗只是把组织问题推给视觉噪声。

对比也不只是满足无障碍数值。主要信息必须清楚，辅助信息要退后，装饰应更弱。Legion 卡片里的小数字颜色太重，会让用户以为数字承载重要流程；删除后，注意力自然回到服务内容。若一个元素无法回答“它帮助用户理解什么”，就不该只因画面空而存在。

深色模式也是典型的“实现成本变低，于是未经选择就出现”。模型可以免费生成，不等于产品需要。MVP 首要任务通常是证明价值、获得用户和完善核心流程。一个对比不佳的深色模式不仅浪费注意力，还会显示团队没有真正测试。Agent 时代更需要创始人区分“容易做”与“值得做”。

紫色渐变和 Linear 风格本身曾经是很好的设计。问题在于，模型从大量成功案例里学到它们，把特定公司的鲜明选择变成行业平均。若创始人想显得像成功软件，直接复制平均答案，最终只会与数百万个同样提示生成的页面撞脸。品位不只是知道什么好看，也包括知道某个好看答案何时已经失去区分度。

**Aaron：** 当用户只能用语言描述“删掉第二张卡右上角的小数字”，修改很费力；能直接点选、按删除、让其他元素回流后，人就不会因赶时间而接受默认结果。速度与品质不必二选一。

另一个 tell 是每个 vibe-coded 应用都同时有浅色和深色模式。真实 MVP 很少把它列为首要功能，只因为模型免费生成、又特别爱做，所以大家都有。若深色模式只是把白改黑、对比失衡，反而更加明显。

**Stephen：** 还有所谓“AI 设计末日四骑士”：拉大字距的小型全大写标题、带小图标的 badge 和 pill、无意义的装饰，以及紫色渐变。Linear 把一套视觉做得很好，随后训练数据把它编码成所有产品的默认答案。单独看这些元素不一定坏，问题是重复使用让公司看起来毫无辨识度。

**Aaron：** 设计标准不断移动。若只停留在训练数据的平均值，产品就只能显得平均，而平均不会让用户兴奋。糟糕外观还影响招聘，优秀人才会用它判断公司是否有判断力。

### 现场改版三：Moreta 有能量，但金融产品先要建立可信度

**Aaron：** 第三个是 Moreta：通过二维码像本地人一样付款，一个全球钱包覆盖亚洲和拉丁美洲的本地二维码。页面上有很多国旗，能看出跨国支付，但金融产品若像 vibe coding，我会紧张。

**Stephen：** 品牌可信度在金融里尤其重要。这页有很强的全球感和能量，方向并不坏，却显得太乱、太随意。真正解释产品的“如何使用”区块很靠下，那里反而干净、专业，越往下看越可信。应该把最好内容和产品机制提前到首屏。

我事先让 GPT-5.5 为它建立一个更专业、可信的视觉基础。结果确实更稳，却损失了原页面的兴奋感。因为仍处在设计工具里，人可以把能量重新加回来。目标不是把品牌磨成无聊模板，而是以可信结构为底，再选择性保留国际化的颜色和动感。

新版文字仍太多，需要删。原版文字渐变太夸张，也应收回。右下角二维码与产品本身有关，是很好的互动入口，但用户习惯把右下角当客服浮窗，可能直接忽略。更好的做法是把二维码移进 hero，明确写“现在试用”。

**Aaron：** 这揭示了生成设计的边界。模型受训练数据和自身偏好支配，能力会持续提高，模型选择也很重要；但用户还需要快速控制，把结果改成自己的愿景。Paper 提供的关键正是生成之后的可编辑性。

**Stephen：** Agent 很适合翻译、改尺寸和生成变化，但我们仍把人类判断放在中心。工具应该让人和 Agent 一起快，而不是让人只能接受 Agent 的品位。

Moreta 的演示尤其说明“专业”与“有个性”并不是一条只能选一端的轴。模型按“让金融品牌可信”重做后，把混乱减少了，却也把国际支付的活力磨平。如果直接发布新版，产品或许不再让人不安，却也不再让人记住。正确工作是保留清晰结构，再有意识加回国旗、色彩和互动二维码，而不是在两个自动生成版本中机械二选一。

首屏应让用户在几秒内回答三件事：这是为谁的，解决什么问题，我下一步能做什么。原页“Pay like a local via QR codes”已经有很强价值主张，但重要机制和信任证据分散在下方。把二维码和“现在试用”放进 hero，可以让品牌视觉直接成为产品体验，而不只是角落装饰。

**Aaron：** 用户长期习惯右下角是聊天客服或隐私控件，会自动忽略。即使二维码很特别，放在那里也会遭遇视觉盲区。设计不是“元素看起来酷”就结束，还要理解人怎样扫描页面。

**Stephen：** 对。Agent 能给十个位置，人仍要知道用户行为、支付信任和品牌目的，才能判断哪一个位置有用。直接操纵让这次判断很便宜：拖到 hero、缩放、改文案、现场看结果，比重新描述整页容易得多。

### 模型会掌握设计技巧，却未必能替组织做设计决策

**Aaron：** Agent 最终能学会 taste 吗？

**Stephen：** 它们会越来越懂字距、字重、层级等技巧。Fable 已比早期模型更像经过思考，而不是只套模板。思考性本身是设计的一部分。

但我不认为模型会完全替代人类设计决策。组织里的设计不是把像素摆好，而是向不同人展示方案，听见“不是这种感觉”，协调高管和其他 stakeholder，吸收需求，理解问题空间，再作出取舍。用户最后看到的是像素，但像素只是组织决策的输出。Agent 目前并不擅长这些工作。

**Aaron：** 人判断一件东西好不好时，有大量隐性的评价标准。若能把每一步语言化、量化，再教给模型，也许它会形成接近人的品位。但若所有模型都学会同一套标准，所有产品会不会再次变得一样？人仍要寻找下一种新东西。

**Stephen：** 人类时代也有同样问题。某个趋势流行后，所有公司几年都像 Linear，直到有人发明新方向。模型会改善战术，少用粗体，这是好事；但产品真正需要表达什么，比战术重要得多。Moreta 的市场也许就需要特别热闹、兴奋，模型必须理解市场、品牌和组织目标才知道。给足信息后也许可以，可能还要十年，也可能我过于悲观，但人仍是必要部分。

### Paper 内部怎样使用 Agent：核心代码逐行看，外围工作大幅放大

**Aaron：** Paper 内部怎样用 Agent？

**Stephen：** 有些方面用得很多，有些方面像“恐龙”。Slack 里没有自动 Agent。我们大量用编程 Agent，但核心代码每一行都由人阅读，通常还不止一个人。

这不是反 AI 姿态，而是按故障成本分层。营销页面某个动画略有偏差，可以快速修；设计工具核心编辑器若在选择、撤销、布局或渲染上偶发错误，会破坏用户信任，甚至损坏工作。越接近核心状态和高频交互，团队越需要理解每一行代码为何存在。

120 FPS 也不是宣传数字。设计师拖动对象时，任何卡顿都会被身体直接感知。代码生成模型可以写出功能正确的实现，却未必自动考虑内存分配、事件频率、重绘边界和复杂画布下的长期性能。多名工程师逐行审查，是对产品承诺负责，而不是因为 Agent 没有价值。

小型精英团队与 Agent 的关系也不是“十二个人虚拟成一百个人”。优势首先来自少沟通层级。每个人可以理解产品更多部分，决定更快，Agent 再放大执行。如果先建立庞大组织，再往每个流程塞 Agent，协调成本可能依旧存在。

Agu 的营销网站说明适合放大的任务是什么：设计意图由资深品牌设计师掌握，Agent 负责把精确画布转成 Next.js 和实现大量互动。Agu 没把第一版网站交给模型凭空设计，而是先完成高质量视觉，再让机器扩展自己没有时间亲手写的部分。人的优势与 Agent 的优势被清楚分工。

Bugbot 同样是第二双眼睛，不是最终责任人。它偶尔对小问题过度挑剔，但抓到真实缺陷就有价值。团队保留人工阅读，避免把“自动审查存在”误认为代码已被理解。

设计工具很难做，今天还不能靠提示写出 Figma 级别产品。它是多维系统，交互必须精确、稳定，设计师需要 120 FPS，任何时候都要快。Agent 还没达到这个可靠性。

我们坚持十二人的小型精英团队，人才门槛很高。现在更好的公司结构是让 Agent 放大优秀的人。人少会降低沟通负担和组织成本，不需要用更多人协调更多人。

Agent 在外围工作的放大已经很明显。品牌设计师 Agu 很擅长视觉，但不自称程序员。他在约一周内独立完成 Paper 整个营销网站，包括发布和所有动画。先在 Paper 里做精确设计，再让 Agent 把它转成 Next.js，并在上面实现动画。六个月前的模型已经能做到。页面还有许多设计师才会加的互动彩蛋，这些工作过去不是他能力上绝对做不到，而是根本没有时间做。

因此，在核心产品里，我们因精度仍以人为主；在视频、营销网站和各种配套资产上，Agent 让同一批人做得更多。工程师广泛使用 Cursor、Claude Code 和 Bugbot 做 PR 检查。Bugbot 有时过于挑剔，但确实能抓 bug。

行业有很强 Agent FOMO：看到别家公司不看代码就发布，会怀疑自己是不是太慢。Paper 的立场是，优质软件需要时间。有的竞争对手功能齐全，却没人关心；Paper 功能较少，用户反而希望它变好。原因是他们能感觉到我们在意精度和品质。稍慢并不自动输，品质会形成注意力和信任。

### 在产品出现前先形成价值共同体

**Aaron：** 设计师中正在形成一种自下而上的 Paper 社群，甚至有点像新工具的文化运动。你们怎样增长、怎样从 Figma 这类巨头旁边获得份额？

**Stephen：** 最重要的是与市场价值观一致。第一年我们没有正式产品，却靠公开谈设计价值获得约 2.5 万 Twitter 关注者。做播客时不复杂包装，就说“我真的喜欢设计，你也喜欢吗”，然后认真谈字体和工艺。

市场若相信你真诚，会原谅产品缺功能，等待功能出现，还会主动支持。设计软件尤其如此，最好的、最真实的产品通常获胜。当然，最终产品本身必须好。十二名设计师和工程师每天按同一套价值观做事，用户能感受到。

产品前先有 2.5 万关注者，并不代表可以只经营观点。它的价值是证明一群人认同同一个问题：设计工具需要重新把设计师和工艺放在中心。等产品出现时，这些人愿意试，也愿意在缺少 comments、components 时继续给反馈。价值共同体降低冷启动难度，却不能替代产品质量。

所谓 authentic 也不是创始人反复说“我们很在乎”。Paper 用开源 Shader、免费字体、设计讨论和产品细节证明价值观。每一种输出本身都能被设计师检验。若品牌宣言强调工艺，产品却粗糙，社群会比普通用户更快发现矛盾。

向企业市场上移造成的“市场时钟”也很现实。大公司采购需要权限、管理、合规和稳定支持，产品自然把资源投向组织买家。早期个人设计师的实验需求会变得相对次要。这不是 Figma 做错了，而是成熟商业的结构结果，也正因此，新工具周期性获得服务前沿用户的机会。

每家公司最终都会向企业市场上移，开始做采购、合规和大型客户，就不再是地下活动里的新酷工具。Figma 已经上市并进入大量大型企业，这给 Paper 留出服务新一代设计师的文化空间。

Ramp 公布企业信用卡订阅数据后，还允许用户用 AI 查询。设计工具支出里，Figma 显然领先，Sketch 仍在，而 Paper 已接近 Sketch，是 Figma 出现后第一家真正对市场造成可见影响的新公司，并且增长很快。创业开始时没人知道结果，我也经历过“不会有人在乎”的月份。如今比我酷得多的人穿我们的周边、主动传播，这是最有成就感的部分。

### 从 Modulz 与 Radix UI 学到：不要同时听两个互相要求对方改变的市场

**Aaron：** 这是你的第二家公司。Paper 早期大家先认同你和你的愿景，再认同产品。它与你第一次创业有什么不同？

**Stephen：** 第一家公司 Modulz 也做设计师与开发者交接，过程中诞生 Radix UI。那是 AI 之前，所有工作都更难。

设计师说“工程师应该按我的系统实现”，工程师说“设计师应该理解代码约束”，两边都把采用责任推给另一边。若创业者同时把两类表态当需求，就会做出一个谁都称赞理念、却没人愿意改变工作流使用的产品。Paper 这次更明确选择设计师和新一代 Agent 原生 builder，再让技术架构自然改善开发协作。

Radix UI 的经历也区分了“产品有巨大使用价值”与“它能形成风投规模公司”。默认 React 组件库被广泛采用，说明需求真实，但开源基础设施的价值捕获路径并不自动成立。团队最终选择免费开放，而不是为了商业叙事破坏一个好工具，再把公司交给更适合承接身份基础设施的 WorkOS。

我们当时同时听设计师和工程师，两边都说问题在对方：设计师希望工程师改变，工程师希望设计师改变，还会告诉你“另一边会用你的软件”。按这种反馈做产品，方向会越来越混乱。我们为“做出人们真正想要的东西”交了学费，Paper 用上了这些经验。

Radix UI 有很强 product-market fit，后来成为默认 React 组件库之一，但我们没有看到把它做成风投规模业务的路径，于是免费开放。公司最终卖给身份认证公司 WorkOS，Paper 也使用 WorkOS。几年后，我回到最喜欢的创意工具领域。

**Aaron：** 哪些教训这次一直在用？

**Stephen：** 产品建设很容易被过度复杂化。`Make something people want` 之所以经典，是因为许多问题真的可以直接问：公司现在最需要发生什么？最初我们需要进入行业对话、需要关注者，那就上播客、谈用户真正重视的事，不必发明天才营销战略。识别下一个瓶颈，再用最直接办法解除，也不要因事情听起来难就回避。

我强烈相信 bottleneck-first。现在早期采用者已经在用 Paper，下一批更主流的设计师习惯原工具，缺 comments 和 components。此时业务瓶颈重新变成功能，所以团队就集中把这些 table stakes 补齐。

另一个简单但重要的做法是每天与用户交谈。公司第一年，我规定自己每天至少和一名设计师谈话，坚持全年。创始人知道太多内部信息，无法自然保持普通用户视角，持续交流能把判断拉回现实。

**Aaron：** 第二次创业时，你更愿意自己成为品牌代表。在产品还很早时，用户购买的不只是功能，也是在判断创始人是否会长期把工具带到他们想去的方向。

**Stephen：** 对，但代表价值观不是表演个人魅力。每天和设计师谈话，让对外表达来自真实问题。第一年坚持一天一位用户，意味着全年持续校正，而不是发布前集中访谈二十个人后就回到内部假设。

用户交流还影响团队分布式决策。十二个人中，工程师碰到一个取舍时不应总等我判断。如果他长期在 Discord 看见用户怎样失败、怎样描述需求，就能自己做出更接近正确的决定。创始人无法靠集中审批保持速度，真正可扩展的是共享的用户理解。

**Aaron：** 公司扩大后，火急事情越来越多，最容易挤掉用户交流。但长期核心仍是做产品、与用户谈话，再加足够运动，避免自己崩掉。

**Stephen：** 新员工入职后必须进入 Discord 或 Slack 和用户说话。有些人来自大公司，以前被禁止直接联系用户，会担心说错；我们告诉他，进去交流，不会把事情搞坏。

即使只有十二人，我也不可能做所有决策。成功公司的路径可以往回追到几个关键判断。如果每个员工都了解用户，正确决策就会分布在组织各处，而不是等创始人审批一切。

### Agent 时代，设计职能不会消失，工具必须跟上发布速度

**Aaron：** 设计的下一步是什么？

**Stephen：** 很多事情其实不会变。设计在组织中仍负责探索问题空间、做竞争分析、协调管理层和利益相关者，这些职能没有消失。软件和公司变多，世界反而需要更多设计。

工程速度提高后，设计团队面对的现实不是“有没有时间再做一版”，而是产品可能在设计师完成判断前就已经发布。若工具跟不上，组织不会因此停止交付，只会跳过设计环节。因此，Agent 原生设计工具的目标应是让设计判断及时进入发布循环，而不是单纯统计设计师一天生成了多少画面。

设计师也不会因为能够直接写出 React 就突然只剩工程职责。他仍要理解竞争产品、用户行为、商业目标和组织分歧，把模糊问题转成可以比较的方案。代码只是让最终选择更快落地，不能替代选择本身。这也是为什么我们把 Paper 看作连接人类判断与 Agent 执行的界面，而不是自动设计机器。

会显著变化的是工具速度。无论设计师是否来得及参与，竞争环境都会推动软件发布。设计工具必须让设计师跟上工程和产品团队，才能在发货过程里真正提高质量。但屏幕上的像素仍只是最终媒介，背后的判断仍是人的问题。

**Aaron：** Paper 接下来做什么？

**Stephen：** 先补 components、comments 等基础能力，解除当前采用瓶颈。用户还在不同地方做大量原型，有的在 Vercel，有的只是本地 HTML。团队不知道别人说的是哪一版，也很难集中反馈。

今天的原型生产已经从“没有原型”变成“原型太多”。同一个功能可能有数个 Vercel 链接、几个本地页面和多轮 Agent 分支。成员在消息里说“第三版按钮不对”时，其他人甚至无法确认他指哪一个。生成速度把组织和反馈变成新的瓶颈。

把这些原型嵌入 Paper 画布，不是把运行网站压扁成截图，而是给每个版本固定位置、名称和讨论上下文。设计师、工程师和管理者能在同一空间查看，直接留下评论，再把意见交给 Agent 或人处理。Paper 因此更像原型控制台，而不只是另一台原型生成器。

**Aaron：** 这与整期反复出现的主题一致：Agent 让供给爆炸后，人需要的不是更多无边界生成，而是比较、选择、组织和反馈。设计工具的价值从“帮你画出来”扩展到“帮团队知道哪一版值得继续”。

我们计划让用户把原型用 iframe 放到 Paper 画布上，统一组织，并像普通设计稿一样评论。严格说这不是 Paper 自己做所有 prototyping，而是为各处生成的原型提供一个可见、可反馈的工作台。许多公司给设计师建了 vibe coding playground，随后得到一堆散乱结果；接下来六个月，我们希望 Paper 成为整理这些结果和运行反馈循环的地方，同时补齐主流用户期待的基础功能。

**Aaron：** Stephen，谢谢你展示 Paper，也谢谢你分享多年创业和设计工作积累的判断。

**Stephen：** 谢谢邀请。

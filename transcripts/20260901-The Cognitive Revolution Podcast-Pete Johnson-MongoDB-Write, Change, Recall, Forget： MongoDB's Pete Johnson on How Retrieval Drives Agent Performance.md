**Pete Johnson：** MongoDB的检索能力最初来自一个看起来不太相关的地方。2020年我们注意到，很多客户在MongoDB集群旁边另外部署Apache Lucene，因为他们想对document里的不同文本字段做关键词检索。MongoDB有Community、Enterprise Advanced和Atlas几种部署方式，Atlas是我们负责运营和支持的托管服务，可以部署在AWS、Google或Azure等云上。

**Pete Johnson：** 因此我们在2020年推出了Atlas Search，把关键词检索作为托管MongoDB的一部分。客户可以直接指定已有的文本属性，系统自动建立索引。几年后，向量检索成为自然的下一步。向量本质上是浮点数数组。无论输入是文本、图片、音频还是视频，只要经过embedding模型，就能得到一组浮点数。对MongoDB来说，这只是document里的另一个属性，于是可以在这个数组上建立向量索引。

**Pete Johnson：** 这形成了混合检索。比如一本书可以有标题、封面URL、页数、出版年份和简介。开发者可以对简介生成向量，在标题上做关键词检索，再先过滤出版年份。一个查询就可以把元数据预过滤、词法检索和向量检索组合起来。

**Pete Johnson：** 到2023年，我们开始考虑如何让这套流程更容易使用。2025年收购Voyage AI，是因为我们看到了embedding模型和reranker并没有被真正商品化。Voyage可以单独与任何向量数据库配合，也可以与MongoDB一起使用，形成更完整的组合。

**Nathan：** 现在用户需要自己执行向量搜索、关键词搜索，再把结果合并吗？

**Pete Johnson：** 这减少了一次往返，也减少了开发者自己维护融合逻辑的负担。向量结果和词法结果不一定有相同的分数含义，因此有时按rank融合，有时按score融合。预过滤还可以在查询前缩小数据集合，避免在不相关的记录上浪费计算。

**Nathan：** 这听起来像是把很多手工拼接的工程工作封装起来。

**Pete Johnson：** 我们常开玩笑说，开发者分成喜欢MongoDB的人和还没试过MongoDB的人。功能经常来自社区反馈。客户原来自己维护Lucene服务器，我们就把检索集成进平台；客户需要融合，我们就把它做成查询里的一个stage。开发者节省下来的时间，可以用来写业务逻辑。

**Nathan：** 另一个难题是长文本怎么切块。一本书有篇章、章节、段落和句子。是应该固定一种chunk size，还是做成树状的主干、分支和叶子？

**Pete Johnson：** 这通常发生在RAG或agentic memory里。企业希望把自己的专有资料安全地注入通用模型，不必为每一份内部资料重新训练模型。切块时存在取舍：切得太小，例如只保留一个句子，检索到时上下文不足；切得太大，例如一次放入三页，存储和传输成本增加，真正需要的句子反而被其他内容淹没。

**Pete Johnson：** 开发者需要针对自己的场景迭代。先选一个chunk size，做测试，观察检索质量，再换一个大小重复。通常要做三四轮，找到成本、上下文和质量的平衡。

**Pete Johnson：** Voyage提出了contextualized chunking。传统embedding把一段文本作为一个大文本块处理，检索质量会随chunk size先提高、后饱和、再下降。contextualized chunking把真正需要精确检索的句子和它的上下文作为两个字符串输入，让模型在生成一个向量时同时考虑两者。这样可以使用更小的检索单元，却保留上下文，减少开发者反复试错。

**Pete Johnson：** Voyage去年发布了第三版，最近又发布第四版。它的目标不是让开发者完全不做评估，而是降低学习曲线。未来三年开发AI agent的人会比过去三年多得多，如果每个人都必须先成为检索工程师，生态很难扩展。

**Nathan：** 这种contextualized chunking返回的还是一个向量吗？

**Pete Johnson：** 是的，仍然是一组浮点数。区别在于，开发者不需要自己决定所有chunk边界。另一个特性是Matryoshka Representation Learning。embedding可能有256到2048个维度，维度越多通常表示空间越丰富，但存储和索引成本也越高。

**Pete Johnson：** 传统模型如果先用1024维，再测试512维，就要把整个语料库重新跑一遍。Voyage模型的浮点数是有序的，使用1024维生成后，可以直接截去后512个维度，用前512个维度测试。这像俄罗斯套娃，外层和内层仍保持相容。它没有替开发者决定最终维度，但能更快完成成本和质量比较。

**Nathan：** 我自己有一个覆盖多年邮件、Slack、公开文章、私信和播客转录的检索系统，规模约一GB，主要依靠agent自己选择数据库和优化方式。我怎么知道自己已经错过了重要优化？是用户规模、数据规模还是推理成本决定什么时候需要认真做？

**Pete Johnson：** 还是速度、规模和检索质量。很多人从Postgres加PGVector开始，这作为demo或早期概念验证完全合理。但当向量数量接近十万时，规模问题开始更明显。毫秒是否重要，取决于你的产品。对于检索质量，Voyage模型在Hugging Face的RTEB等基准上经常排名靠前，相比其他embedding模型可能有约14%的改善。

**Pete Johnson：** 14%有时就是幻觉和正确答案的差别，尤其是在加入reranker之前。reranker可以在不改变原始数据的情况下，再次排序候选结果，让真正相关的内容进入上下文。很多人以为embedding已经商品化，但我们观察到模型之间仍有很大差异。Anthropic目前没有自己的embedding模型，也推荐Voyage，这说明质量差异仍然有实际价值。

**Nathan：** 这让我想到“bitter lesson engineering”。有些手工规则在早期确实有用，但模型变强后，应该定期检查哪些东西已经不需要了。

**Pete Johnson：** 我也看到两处简化。第一是rerank。过去要先做向量检索，把结果发给reranker，再把排序后的结果放进上下文。现在可以用$rank或相关stage，在一次API调用里完成。第二是auto embeddings。开发者指定collection、document里的属性、Voyage模型和维度，之后每次document改变，系统自动重新生成embedding、更新向量和内存索引；新document出现时也会自动处理。这样开发者不必自己维护embedding pipeline。

**Nathan：** 说到更广泛的系统，百万token上下文窗口似乎让大家暂时放松了对记忆的设计，但成本会随用户数增加。今天一个好的记忆系统大概是什么样？

**Pete Johnson：** 历史很重要。ChatGPT在2022年底出现时，架构很简单：把问题放进上下文窗口，LLM处理后返回答案。后来大家发现模型只在训练截止日前知道公开数据。如果你问当时MongoDB的股价，它无法知道，因为知识有截止日。到2025年，工具和MCP解决了一部分问题，模型可以调用搜索或其他API获得新信息。

**Pete Johnson：** 另一个变化是agent循环。一次循环的输出会成为下一次循环的输入。短期记忆早期做法是把本次会话的所有回答都塞进上下文，长期记忆则把过去几天甚至更长时间的会话也塞进去。现在大家开始反对这种token maxing，因为每个循环填满一百万token，成本很快失控，而且功能上也不一定更好。

**Pete Johnson：** 有学术研究显示，开头和结尾的一小段token往往最重要，中间大量内容可能反而混淆模型。因此问题不是如何每次塞入最多token，而是如何为当前循环选择最相关的二十万token。短期记忆应该只保留与这一步相关的内容，长期记忆也要做选择。

**Pete Johnson：** 我们在财富500强客户里开始看到一种taxonomic memory。每个行业或公司都有专门术语。一个汽车企业可能有一百个内部术语，但当前agent循环可能只需要其中五个。记忆系统应当使用向量、词法检索和预过滤，把当前任务所需的那几个概念找出来，而不是每次把全部术语放进上下文。

**Nathan：** 我自己的系统既有原始月度日志，也有月度摘要、年度摘要和实体之间相互链接的wiki结构。发生新事情时，我很难知道哪些地方需要更新。有些项目其实只是短暂尝试，模型却把它们当成持续开放的计划。如何维护记忆，使它准确而不是只在第一次创建时看起来合理？

**Pete Johnson：** 我认为这是agent现在最难的问题。数据库行业有六十年经验，agent行业只有约十八个月，没有人知道全部答案。一个更成熟的记忆系统让应用作者承担两项责任。第一，给记忆系统一个查询和token预算，请它返回最相关的内容；第二，把agent得到的新答案送回记忆系统，让它整理并写入。

**Pete Johnson：** 记忆还可能共享给相同岗位的同事，这就是所谓的回馈或共享记忆。但最困难的是四个动作：write、change、recall、forget，也就是写入、改变、回忆和遗忘。记忆有半衰期，最近发生的事通常比几个月前的事情重要。系统必须让新事实修改旧事实，也必须能标记一个已经放弃的项目，不要长期把它当成开放任务。

**Pete Johnson：** 检索质量在这里很关键。更好的embedding模型和reranker可以带来约5%到10%的检索提升。对于更大的语料，也可以先用两到六层甚至十几层的graph结构，把数据按组织、项目、主题或产品分类，再在叶节点内部做向量检索。MongoDB基于JSON的结构可以同时承载核心数据、图结构、向量索引、embedding和reranking，减少开发者把多个系统缝在一起的工作。

**Nathan：** 有哪些客户把记忆系统做得特别好？

**Pete Johnson：** 11 Labs是一个有趣的例子。它从语音模型提供商发展成音频编辑平台，为每个客户提供许多微型agent，执行编辑、转换和其他任务。多个agent和客户上下文结合后，记忆系统就必须知道每个客户的历史、偏好和正在进行的工作。

**Pete Johnson：** 我会警惕一种做法：用很多次LLM调用来分类和压缩全部语料，再把压缩结果交给更大的模型。这样会增加token和延迟。embedding和reranker更像是适合检索的专用工具，成本更低，也更快。即使小模型也可能花很久推理，整个决策循环的延迟会累积起来。

**Nathan：** 现在什么已经成熟到可以直接买，什么仍然需要自己构建？

**Pete Johnson：** 我今年去了七个国家，与大约一百家客户交流，它们大致分成三类。第一类是买了一个工具就认为AI战略完成了。买工具可以作为起点，但很少足以解决企业整体问题。第二类做过概念验证，甚至有几次生产部署，却没有得到理想ROI。很多时候不是技术用错，而是选错了问题。第三类已经进入更复杂的记忆和系统优化阶段，有时购买平台，有时自己构建。

**Pete Johnson：** 我建议企业先列出当前最重要的十到十五个问题，然后问三个问题：哪个问题有高质量数据，哪个问题已经有可量化指标，哪个问题值得投入。坏数据和糟糕的安全状态不会被AI自动修好，反而会被AI放大。如果没有现成指标，就无法知道AI是否真的让事情变好。

**Pete Johnson：** 呼叫中心是常见的低风险起点，因为企业已经知道每次通话成本、通话量和员工绩效。软件交付也是例子。有人说有了Claude Code或Codex后，工程师能写五倍代码，但代码行数并不是好指标。更重要的是从想法到生产部署的速度、缺陷率和客户结果。

**Nathan：** 我上周在一家只有一个门店的披萨店打电话，接听电话的是AI agent。正常点餐很自然，但我开始进行对抗性测试时，它误解了我的问题。你看到财富500强在呼叫中心方面走到哪一步？

**Pete Johnson：** 我接触的大多数财富500强，先做员工面对的场景，并保留人在回路中。员工每个岗位都有关键绩效指标，例如保险理赔员、制造业流水线工人或客服人员。AI如果让这些指标改善，ROI就比较容易测量。

**Pete Johnson：** 面向客户的完全自治系统风险更高。如果同一家公司两个员工之间的工资数据意外泄露，已经很严重；但如果一个客户看到另一个客户的数据，责任和品牌损失会更大。因此今天企业通常优先选择员工场景、人工监督和可测量流程，而不是直接把客户交互全部交给自治agent。

**Nathan：** MongoDB有传统文档，也在努力让agent能读懂文档、调用数据和选择MongoDB。你们如何让产品适合agent？

**Pete Johnson：** MCP工具是重点。MongoDB已经有MCP server，现在也把一些能力作为Atlas生态的一部分托管。另一个方向是agent skills，可以把过去写在文档里的数据建模、操作优化和部署流程，整理成一组Markdown文件，作为经过整理的系统提示或技能，直接交给agent。

**Pete Johnson：** 软件公司都在考虑如何让agent在用户第一次解决问题时推荐自己的产品。但重点不是营销，而是把可靠的操作方法、数据模型和安全边界写得足够清楚，让agent能够在正确的上下文里调用它们。

**Nathan：** MongoDB已经有向量数据库能力，为什么收购Voyage AI，而不是收购一个向量数据库初创公司？这对软件行业的价值和护城河说明了什么？

**Pete Johnson：** MongoDB的核心一直是让开发者少花时间处理底层管道，多花时间写业务逻辑。向量只是document里的另一个属性，所以在已有JSON模型上加入向量索引相对自然。MongoDB还已经解决了复制、分片、安全、跨云部署和多数据中心运行。新的向量数据库公司需要逐渐补齐这些企业能力。

**Pete Johnson：** Voyage的价值在另一层。市场普遍认为embedding和reranker已经商品化，但我们认为Voyage在检索质量上有明显差异。收购后可以提供auto embeddings、共享API key管理和更顺畅的组合体验。开发者过去要去一个控制台管理核心数据，另一个管理向量数据库，第三个管理embedding，第四个管理reranker。把这些放在一个地方，长期运营更容易。

**Nathan：** 有人说，向量数据库的大量数据原来从未进入任何数据库，而是散落在data lake、data warehouse或文档堆里。你们看到的数据边界是在扩大吗？

**Pete Johnson：** 是的。向量检索就是把某种数据映射到几何空间，再找距离最近的向量。视频、音频、PDF和没有结构的SharePoint文档都能被索引。过去词法检索不容易处理这些内容，因此它们一直没有被纳入高等级基础设施。现在问题不只是如何把数据放进数据库，而是如何快速、可扩展且高质量地找到它。

**Pete Johnson：** MongoDB的优势在于可以同时做元数据预过滤、词法检索和向量检索，还能提供数据复制、安全和地理分片。对于法律或主权要求，企业可以把数据保留在特定区域。由于这些能力来自核心产品，向量功能不需要另起一套完全孤立的运营系统。

**Nathan：** 你今年走访了多个国家。我长期关注旧金山和硅谷，可能低估了其他地区。哪些地方在AI使用上最让我意外？

**Pete Johnson：** 我想反过来说。很多国家默认美国领先，但我今年在墨西哥城和圣保罗遇到的两家客户，是我见过最成熟的客户。它们原以为美国竞争者已经领先，实际情况却相反。地点分别在墨西哥城和巴西圣保罗，之前我也去过阿姆斯特丹、伦敦、多伦多和班加罗尔。

**Pete Johnson：** 云时代，如果一个云服务商没有在某个国家建设数据中心，当地客户就很难使用它。现在几乎每个国家至少有一个大型云数据中心，模型、向量数据库、embedding和reranker的访问已经全球化。互联网和云基础设施的普及，正在削弱地理对AI领先地位的限制。

**Nathan：** 这是美国公司更保守，还是其他国家在技术上发生了跨越式采用？

**Pete Johnson：** 我不认为这是对美国公司的指责。更主要的原因是美国以外的访问障碍下降了。移动时代要先有基站，手机才有用；现在全球基础设施已经铺开，更多国家可以直接使用相同的工具。于是当地企业不需要等待本土技术经历所有上一代周期，就能直接构建先进的AI系统。

**Pete Johnson：** 最后还想补充Voyage的共享embedding空间。Voyage第四代文本模型有多个尺寸，通常是小、中、大，再加上一个开放权重、免费的nano模型。四个模型共享同一个embedding空间，所以在开发时，语料可以用大模型生成embedding，查询则可以用本地或低成本的nano模型完成。

**Pete Johnson：** 这样开发者可以降低查询阶段的token成本，只在语料嵌入时承担较高成本。换用较小模型会有一些检索质量差异，但对于开发和测试非常有用。模型之间相互兼容，减少了因为改变embedding模型而重新处理全部语料的负担。

**Pete Johnson：** 更广泛地说，agent技术会继续快速迭代。MCP在两年前感恩节前的星期一发布，到第二年三月，竞争者已经大多接受了这个协议。token maxing在三月初成为话题，到四月大家就开始讨论它的成本后果。功能、协议和架构的变化速度，比过去任何软件周期都快。

**Nathan：** 这意味着我们还在共同学习，没有一套永远不变的答案。

**Pete Johnson：** 是的。数据库已经积累了几十年，agent才刚起步。我们会继续迭代，努力让开发者更容易理解检索、记忆和部署。未来日常生活里会有更多agent，但它们要真正可靠，就必须让数据质量、检索质量、权限和反馈循环一起进步。

**Pete Johnson：** 谢谢邀请。

**Nathan：** 你刚才说MongoDB不是完全没有schema，而是更灵活的schema。这一点很重要，因为灵活并不代表不需要设计。如果一个collection里的document可以有不同形状，开发者怎样避免它变成一堆互不相容的对象？

**Pete Johnson：** 灵活的schema给你的是选择权，而不是强迫你放弃约束。你可以在应用层规定哪些字段必须存在，也可以对一部分collection使用验证规则。区别在于，当产品需求改变、某类document需要新增属性时，不必像传统关系数据库那样同时修改大量表、迁移所有历史数据，再等待整个系统完成升级。

**Pete Johnson：** 在早期互联网应用里，开发者经常需要快速增加属性。用户资料、订单、设备状态和内容记录都可能在几周内改变形状。把相关数据放在一个JSON document里，读一次就可以拿到业务逻辑需要的内容。这样做会付出一点重复存储的代价，但换来更少的连接、更少的数据转换和更容易演进的应用。

**Nathan：** 所以规范化和反规范化不是道德判断，而是对不同稀缺资源的回应。1970年稀缺的是存储，2007年更稀缺的是时间和可用性。

**Pete Johnson：** 正是如此。数据库设计总是在资源之间取舍。早期系统会优先节约磁盘，所以重复数据是问题。现代云应用更关心响应时间、开发速度、横向扩展和持续在线。如果把旧环境里合理的解决方案机械地带到新环境，可能会让系统承担不必要的复杂性。

**Nathan：** AI把这个问题再推了一步。现在我们既希望所有数据都可检索，又不希望把所有数据都塞进上下文。企业数据本身的结构、索引和新鲜度会影响模型结果。

**Pete Johnson：** 对agent来说，检索质量是输入质量。模型的推理可能很强，但如果检索返回了错误、过时或不相关的document，模型就会在错误基础上给出自信答案。RAG不是把数据库变成一个文件仓库，而是要为每个任务选择足够、准确和可解释的上下文。

**Pete Johnson：** 传统关键词搜索擅长处理明确词语，例如标题、产品号或精确名称。向量搜索更适合表达语义相近但用词不同的内容。混合检索把两者结合起来，再用元数据做预过滤，通常比只选一种方法更实用。比如先限定业务部门和时间范围，再在剩下的资料里按标题关键词和语义相似度排序。

**Nathan：** rank fusion和score fusion的区别，是否可以理解为一个更关注两个系统各自给出的顺序，一个更关注分数的大小？

**Pete Johnson：** 可以这样理解。不同搜索系统的分数未必在同一个尺度上，因此直接相加不一定合理。rank fusion只看一个结果在各自列表里的位置，再按照排名合成；score fusion则利用搜索返回的分数。开发者可以根据数据和实验结果选择。关键是，现在这两个步骤可以放在aggregation pipeline里完成，应用不需要自己维护一套脆弱的合并代码。

**Pete Johnson：** 这也是数据库平台化的价值。我们已经为Atlas解决了跨数据中心复制、分片、加密、认证和运营问题。向量搜索不是一台孤立的实验机器，而是在同一个安全和可扩展系统上运行。企业可以按业务或法律要求把数据留在特定地区，也可以让不同云上的节点协同工作。

**Nathan：** 长文档切块时，很多人会直接取固定数量的token。你认为文档结构是不是比固定长度更重要？

**Pete Johnson：** 文档结构很有帮助，但没有一个对所有语料都正确的固定答案。一份法律合同、一份产品手册、一个聊天记录和一段视频，最有意义的边界不同。合同可能按条款划分，手册可能按章节划分，聊天记录可能按主题或时间划分。应用开发者应当从真实查询出发，检查返回片段是否能支持正确回答。

**Pete Johnson：** chunk太小，模型看到一个孤立句子，不知道它指向什么；chunk太大，检索命中的主题被大量无关内容包围，存储和上下文费用增加。最实际的方法是选几种大小、准备代表性查询、比较命中质量和成本。contextualized chunking的意义，是让模型知道小片段处在什么上下文里，从而不必把整个段落或整页都当成检索单元。

**Nathan：** 这种方法对个人系统也有意义。我的邮件和播客材料中，很多句子只有和前后内容放在一起才有意义，但每次都召回整个文件太贵。

**Pete Johnson：** 对个人系统，成本和质量的平衡可能不同于大企业。你可能愿意用更大的上下文，因为用户只有一个，响应频率也有限。可是当同一系统服务几千或几百万用户时，每一次多出的token都会乘以用户数。那时检索、重排和合适的chunk size就会直接影响单位经济性。

**Nathan：** 什么时候才需要关注十万向量这个规模？

**Pete Johnson：** 这不是严格的悬崖，但大约十万向量以后，索引、延迟和更新策略会更容易暴露问题。小规模demo中，很多数据库都能给出不错结果；进入生产后，你还要考虑并发查询、数据分片、向量更新、权限过滤和故障恢复。一个方法在一千条document上看起来很好，并不表示它在一亿条数据上仍然合适。

**Pete Johnson：** 检索质量也有同样问题。benchmark提供方向，但真实企业任务的分布更重要。你要问的是，系统能否找到这家公司的正确政策、这位客户的正确历史或这个案件的正确条款，而不是它在一个公开数据集上排名第几。某个embedding模型带来十几个百分点的改善，若恰好改善的是企业最容易出错的查询，价值会很高。

**Nathan：** reranker是否可以弥补embedding模型的一些不足？

**Pete Johnson：** 可以提高候选集的排序，但不能从完全没有召回的候选中创造正确答案。因此embedding负责把足够大的、相对便宜的候选集合找出来，reranker再对候选集合做更精细判断。最好的系统通常会把过滤、向量召回、词法召回和重排组合起来，而不是期待一个模型完成所有工作。

**Nathan：** 你提到大模型上下文的“首尾更重要”现象。企业如何设计短期记忆和长期记忆，才不会把重要信息压在中间？

**Pete Johnson：** 可以把记忆看成多个来源，而不是一个越来越长的聊天记录。短期记忆保留当前任务中刚发生且仍相关的状态；长期记忆保留稳定事实、过去决定和长期偏好；分类记忆保留行业或组织的词汇。每次agent循环前，先根据当前目标检索这些来源，再按预算组合成上下文。

**Pete Johnson：** 例如一个汽车售后agent当前要处理发动机故障。它需要本次对话里客户说过的症状，需要这个车辆型号的维修政策，还需要公司对保修范围的定义。它不需要把全公司的销售术语、过去三年的所有对话和所有车型说明一起放进去。记忆系统应当知道哪些内容与当前循环有关。

**Nathan：** 但新事实出现时，旧记忆怎么办？如果客户换了地址、项目取消了，或者我原来考虑的创业想法已经放弃，系统如何忘记？

**Pete Johnson：** 这就是write、change、recall、forget。写入是把新的观察保存下来，改变是让新状态覆盖或修正旧状态，回忆是按当前问题找到相关内容，遗忘则是降低旧内容的权重、标记它失效，或者彻底删除。遗忘最难，因为系统很容易只会追加，而不会管理冲突和时间。

**Pete Johnson：** 维护时可以给事实加时间、来源、置信度和状态。一个“项目正在考虑中”的记录，如果后来出现明确的取消信号，就不应继续作为开放目标。它可能仍然有历史价值，但在回答“我现在正在做什么”时不应被召回。新记忆应当能解释为什么修改旧记忆，而不是无声地堆叠两条互相冲突的信息。

**Nathan：** 这听起来需要数据库里的版本和关系，而不是简单的文本向量。

**Pete Johnson：** 是的。向量适合相似性检索，但它不能单独表达全部业务关系。某个人属于哪个组织、某个项目取代了哪个项目、某个政策在什么日期生效，这些关系可以用document字段、引用或图结构表达。常见做法是先沿着组织、项目、产品或时间的层次缩小范围，再在范围内用向量检索语义相关内容。

**Pete Johnson：** 这不一定需要一个很深的专用图数据库。很多客户用两到六层的分类和引用结构，足以把大型语料分成适合搜索的节点。电商产品目录就是例子：先按类别和品牌过滤，再在具体类别内按描述向量搜索。MongoDB的JSON模型可以把这些关系和原始document放在一起。

**Nathan：** 你提到11 Labs的微型agent。一个客户有多个agent时，它们之间共享什么记忆？

**Pete Johnson：** 要区分客户私有记忆、任务记忆和组织共享记忆。一个音频编辑agent需要知道当前项目的轨道和编辑历史，另一个转换agent需要知道输出格式。某些偏好可以在同一客户的多个agent之间共享，但不能把一个客户的数据暴露给另一个客户。身份和权限必须随记忆一起传递。

**Pete Johnson：** 如果把所有记忆都交给一个更大的LLM来分类，成本会很高，也会增加延迟。embedding和reranker可以在许多场景承担更专门、更便宜的筛选工作。LLM应该把预算用在需要推理和决策的地方，而不是反复执行可以用索引完成的整理。

**Nathan：** 这就是你所谓的“对正确问题使用正确工具”。

**Pete Johnson：** 对。数据库、embedding、reranker、LLM和人工审核各自擅长不同事情。把所有步骤都交给LLM，不一定更智能，可能只是更贵、更慢、更难审计。

**Nathan：** 从买和建的角度看，企业常常要么完全购买一个平台，要么完全自己做。你会建议怎样开始？

**Pete Johnson：** 先买一个工具并不等于拥有AI战略。企业需要从实际问题开始。选一个有高质量数据、已有指标、风险可控的流程，先验证结果是否改善。客服、内部知识检索、软件交付和员工辅助往往比直接让agent独立操作客户账户更容易衡量。

**Pete Johnson：** 买来的平台通常可以帮助你获得认证、部署、索引、监控和基础模型能力，但企业独有的流程、数据和责任边界仍然需要定制。你不能期待一个通用产品自动理解公司的例外规则，更不能让它在没有权限设计的情况下接触所有内部数据。

**Nathan：** 企业应怎样定义AI项目的ROI？

**Pete Johnson：** 不要用“模型看起来很聪明”作为指标。呼叫中心可以看每次通话成本、解决率、等待时间和转人工比例。软件团队可以看从想法到生产的时间、故障率和回滚次数。理赔团队可以看处理时间、错误率和客户满意度。先有基线，再引入AI，才知道结果是否真的改变。

**Pete Johnson：** 如果一个团队只说“我们生成了五倍代码”，我会继续问代码是否进入生产，客户是否更快获得功能，缺陷是否增加。生产结果比输出数量重要。AI可能让一个人写更多代码，也可能让团队更快发现不该写的代码，指标必须围绕业务结果设计。

**Nathan：** 面向员工的AI为什么比面向客户的自治agent更容易落地？

**Pete Johnson：** 因为员工通常已有身份、岗位和可量化KPI，且人在回路中。一个员工使用AI建议处理理赔，最终仍可以审核；一个面向客户的agent如果直接读取、修改或发送客户数据，错误的影响范围更大。企业会先在风险更可控的内部场景学习，再逐步放开自治程度。

**Pete Johnson：** 数据安全也有类似的风险梯度。同事之间意外看到不该看的薪资数据已经严重，但两个客户之间的数据串了，会带来更大的法律和品牌问题。权限过滤应当发生在检索层，而不是只在模型生成答案之后补救。

**Nathan：** 这意味着MongoDB的检索必须理解用户身份，而不是只做相似度。

**Pete Johnson：** 是的。向量命中不代表用户有权看到它。企业检索要把租户、部门、地区、数据分类和角色权限作为预过滤条件。然后在允许的集合上做词法和向量搜索。只在最后一步要求模型“不要泄露”是不够的，因为不该进入上下文的内容一旦进入，就已经产生风险。

**Nathan：** MongoDB如何让agent使用自己的文档和产品？

**Pete Johnson：** 一方面是MCP，让agent通过标准化工具与数据和操作连接；另一方面是agent skills，把数据建模、索引、运维和查询优化的做法整理成Markdown文件。过去开发者要阅读很多文档，再把知识转成系统提示；现在可以给agent一组经过整理的技能，让它在具体任务中按照可靠流程工作。

**Pete Johnson：** 这不意味着agent永远不会犯错。技能需要版本、评估和维护，工具需要最小权限，重要操作需要审批。但把知识组织成机器可读的流程，会比把一堆网页链接丢给模型更容易复用。

**Nathan：** Voyage AI的收购，是否也反映了数据库公司价值从存储和查询扩展到了模型周边？

**Pete Johnson：** 我认为更准确的说法是，数据库正在成为AI应用的工作基础设施。embedding决定数据如何进入检索空间，reranker决定候选如何排序，数据库决定数据如何存储、更新、过滤、复制和保护。若这几层由不同供应商提供，企业还要自己承担连接、密钥、观测和故障排查。整合它们可以降低开发和运营成本。

**Pete Johnson：** 当然，开放生态仍然重要。客户可以选择其他embedding模型，也可以把Voyage和其他向量数据库配合。我们的判断是，选择权与更紧密的组合可以同时存在。

**Nathan：** 非结构化数据进入数据库，会不会使“什么都存进去”重新成为坏习惯？

**Pete Johnson：** 会有这种风险，所以索引和治理必须同时发展。视频、音频和PDF可以被embedding，但仍需要来源、时间、权限、版本和删除策略。向量化不等于理解，也不等于数据质量自动提高。垃圾数据进入一个更强的检索系统后，可能更快地被错误地召回。

**Pete Johnson：** 数据质量差和安全姿态差，通常会被AI放大。企业要知道数据从哪里来，谁能改，什么时候过期，以及模型回答是否引用了正确来源。平台能提供工具，但不能替企业决定业务事实。

**Nathan：** 你在墨西哥城和圣保罗看到的先进客户，是否有共同特点？

**Pete Johnson：** 它们不一定拥有最多的研究资源，但能更快把可用的全球基础设施接入自己的业务。过去地理位置可能决定你能否使用某个云服务，现在模型和数据库更容易获得。它们把AI当成解决具体运营问题的工具，而不是只等待一个完美的统一平台。

**Pete Johnson：** 这也提醒美国从业者不要只看硅谷。不同国家的监管、成本、人才和业务流程不同，同一个模型可能在不同市场产生不同的最佳用法。云和开放模型降低了地域门槛，真正的差异可能转移到数据质量、执行速度和组织采纳能力。

**Nathan：** 回到shared embedding spaces。你说开发时可以用免费的nano模型查询，但生产时换成更大的模型。嵌入兼容是否会降低迁移成本？

**Pete Johnson：** 它让你可以在相同空间里比较不同模型，而不必马上重新嵌入全部语料。开发阶段用较小模型降低查询token成本，生产阶段根据检索质量和成本选择更大的模型。不同大小仍可能有质量差异，所以必须用自己的查询集验证，但兼容性给了团队渐进式升级的路径。

**Pete Johnson：** 这类功能的共同目标，是把时间还给开发者。开发者应该花时间理解客户和业务逻辑，而不是反复编写索引更新、API密钥管理、查询融合和embedding同步的管道代码。

**Nathan：** 我想把一个常见误区再展开一下。有人听到“百万token上下文”就认为数据库和RAG不再重要，因为模型可以自己读完所有材料。但企业使用不是一次性读一份材料，往往是很多用户、很多循环、很多权限不同的请求同时发生。

**Pete Johnson：** 而且上下文窗口大不等于上下文内容都相关。每次把全部历史放进去，不仅要付输入token费用，还会增加模型处理时间。模型可能把正确答案放在一堆相似但过时的内容之间。检索的工作是把可用的候选缩小，把来源和权限先处理好，再把有限预算交给模型。

**Pete Johnson：** 企业还要面对数据持续变化。产品说明会改，政策会改，客户状态会改。如果只在第一次导入时生成embedding，后续文档变化而向量不变，检索就会返回旧内容。auto embeddings的价值不仅是省代码，也是让更新和索引保持同步。

**Nathan：** 对个人知识库来说，月度原始日志和摘要之间也有同样问题。摘要可能很方便，但它会把细节和来源压缩掉，模型后来可能只记得一个过于宽泛的结论。

**Pete Johnson：** 所以记忆系统不应只保留摘要。摘要适合导航，原始记录适合验证，结构化事实适合精确过滤，向量适合语义召回。不同记忆类型可以协同，但必须知道每类记忆的用途。一个没有来源的摘要，不应该覆盖一条有明确时间和出处的事实。

**Pete Johnson：** 这也是write和change的关系。写入不只是追加文本，而是识别这是新事实、旧事实的修正，还是一次暂时的计划。change需要让系统知道旧状态是否仍然有效。recall需要根据查询选择正确版本。forget则要降低不再适用内容的权重，必要时删除它。

**Nathan：** 记忆半衰期是不是可以按事实类型不同来设定？一个人的出生信息可能多年不变，一个项目的下一步计划可能几天就过期。

**Pete Johnson：** 这是很有用的思路。稳定事实、短期状态、临时想法和外部市场信息不应使用相同的更新规则。市场价格需要实时工具，项目状态需要时间和来源，行业术语可以是共享分类，用户偏好则可能需要明确确认。系统越能区分这些类型，越不容易把暂时内容当成永久事实。

**Nathan：** 这似乎又把我们带回schema。灵活的document可以容纳不同类型，但如果不记录类型、时间和来源，灵活也会变成含糊。

**Pete Johnson：** 完全正确。schema flexible不是不建模。你仍然要思考document包含什么、谁能修改、哪些字段用于过滤、哪些字段用于embedding。只是你可以逐步演进这些字段，而不必一开始就把所有未来变化固定成关系表。

**Pete Johnson：** 在向量搜索中，元数据字段尤其重要。embedding只能告诉你语义相近，不能代替发布日期、组织、产品、地区和权限。先做pre-filter，再在允许集合中做向量和词法搜索，通常比先召回全库、最后再过滤更安全，也更节省计算。

**Nathan：** 如果一个document同时包含文本、图片或视频，是否应该给每一种模态单独嵌入？

**Pete Johnson：** 要看查询方式。视频可以按片段、画面和音频建立不同表示，也可以使用支持多模态的embedding模型。但应用需要保存来源、时间位置和模态信息，检索到后还要能返回用户可理解的片段。把所有模态压成一个向量并不自动解决结果解释问题。

**Pete Johnson：** 向量数据库初创公司的机会，很多时候就来自这些以前没有被索引的数据。数据湖和共享文件夹里有大量内容，但传统词法搜索不容易发现它们。向量检索让这些数据第一次有了语义入口。与此同时，企业仍然需要成熟数据库提供的安全、复制、分片和审计能力。

**Nathan：** 这也解释了为什么你们既可以与向量数据库竞争，又可以把Voyage模型提供给其他数据库。竞争的是整合后的开发和运营体验，不是要求客户永远只能使用一种模型。

**Pete Johnson：** 对。我们希望开发者能够从一个容易开始的入口进入这个生态。可以先在Atlas里用现有document做检索，也可以选择自己的embedding模型。随着需求增长，再考虑专用端点、分片、跨区域部署和更复杂的记忆结构。

**Nathan：** 对企业来说，真正的“买”可能是买一组基础能力，而不是买一个能自动解决所有问题的AI产品。

**Pete Johnson：** 这是我的看法。企业可以购买数据库、模型、向量索引、reranker和部署平台，但仍要自己决定哪个业务问题值得解决，哪些数据可以使用，什么人有权限，以及怎样量化结果。最成熟的客户不是盲目购买，也不是把所有东西从零重写，而是在通用能力和独有流程之间划分边界。

**Pete Johnson：** 还有一个很容易忽略的因素是运维。一个demo只需要今天能跑，生产系统要持续运行。模型要升级，embedding要更新，索引要重建，数据要删除，权限要撤销，故障要恢复。平台能承担一部分工程工作，但企业仍需有负责人和流程。

**Nathan：** 呼叫中心的例子很直观。一个AI接电话的demo可以表现得很自然，但进入真实业务后，它要识别客户、查询订单、处理退款、遵守政策，并把无法完成的请求交给人。

**Pete Johnson：** 没错。语音的自然性只是第一步。生产系统还要知道客户是谁，哪些信息可以读，哪些动作需要确认，怎样记录通话和结果。对于员工辅助，agent可以先建议答案，由员工确认；对于客户自动服务，动作权限必须更窄，审计要求也更高。

**Pete Johnson：** 因此我常建议从员工面对的、有人在回路中的任务开始。你可以比较使用AI前后的关键指标，也可以在出现错误时及时干预。等组织理解了数据、指标和例外，再考虑增加自治程度。

**Nathan：** 你今年在墨西哥城和圣保罗看到的客户，是否也遵循这套从问题和指标出发的方式？

**Pete Johnson：** 我不能把每家公司概括成一个模式，但先进客户通常很清楚自己要解决什么，而不是只想“使用AI”。它们有可用的数据，知道成功的衡量方式，也愿意调整流程。地理位置不是能力的充分条件，真正重要的是把基础设施和业务执行结合起来。

**Pete Johnson：** 这也提醒美国从业者不要只看硅谷。不同国家的监管、成本、人才和业务流程不同，同一个模型可能在不同市场产生不同的最佳用法。云和开放模型降低了地域门槛，真正的差异可能转移到数据质量、执行速度和组织采纳能力。

**Nathan：** 最后再回到agent skills。把经验写成Markdown给agent，是否意味着文档工程会重新变得重要？

**Pete Johnson：** 文档一直重要，只是读者从人变成了人和agent。面向agent的文档需要更清晰地写出前置条件、工具参数、失败处理、权限边界和验证步骤。一个只描述产品概念的页面，不一定足以指导agent安全地完成数据建模或运维操作。

**Pete Johnson：** agent skills可以把这些步骤组织起来，但它们也要像软件一样版本化、测试和审查。技能如果写错，agent会以很快的速度重复错误。因此技能、MCP工具和数据库权限应当形成一个整体，而不是把一组提示词当成魔法。

**Nathan：** 这使得“速度”有了三个层次：数据库返回得快，模型推理得快，整个agent工作流还要能快速而正确地完成。

**Pete Johnson：** 是的。只看其中一个层次会误导。模型很快但检索错误，系统仍然失败；检索很快但工具调用串行，用户仍然等待；所有环节都很快但没有权限，系统可能更快地造成损失。真正的性能是端到端结果、成本和风险的组合。

**Pete Johnson：** 因此，未来企业的AI成熟度不只是“有没有模型”，而是有没有可维护的数据、可解释的检索、可更新的记忆、可审计的工具和明确的业务指标。数据库是其中一个重要基础，但不是全部答案。

**Nathan：** 这也回答了节目标题。AI系统要写入新信息，改变旧信息，回忆相关内容，还要忘记已经失效的东西。任何只会追加、不知道改变和遗忘的系统，最终都会被自己的历史拖慢。

**Pete Johnson：** 这正是我们现在共同面对的问题。我们有很多局部技术可以购买，也有很多部分可以自己构建，但没有一套像传统Web开发那样成熟的标准栈。最好的方法是保持实验，用真实指标验证，并让系统随着业务变化持续更新。

**Pete Johnson：** 还有一点容易被忽略：检索系统也需要像其他生产系统一样接受审计。每次返回的内容要能追溯到原始document，权限过滤要在进入模型前完成，embedding更新要和document变化保持同步。只有这样，企业才能解释为什么agent得到这个答案，也才能在错误发生时定位是数据、检索、模型还是业务流程出了问题。

**Nathan：** 所以一套真正成熟的agent记忆，不是把历史保存得越多越好，而是让当前任务拿到可验证、可更新、在权限范围内的正确历史。

**Pete Johnson：** 对。写入越多不等于记忆越好，召回越多也不等于答案越好。好的系统知道什么时候写、什么时候改变、什么时候回忆，什么时候应该忘记。数据库提供了这些动作的基础，业务指标和人工判断仍然不可缺少。

**Nathan：** 这也意味着企业不应把“模型回答得像人”当作完成标准。它还要能说明用了哪些数据、遵守了哪些权限、是否引用了最新版本，以及当信息冲突时如何处理。

**Pete Johnson：** 没错。AI真正进入生产，不是因为它在演示里显得聪明，而是因为企业可以测量它、维护它、限制它，并在必要时纠正它。检索、记忆和数据库的价值，最终都要落到这些可验证的动作上。

**Nathan：** 可追溯的来源、正确的版本和先于模型发生的权限过滤，才是把演示变成生产系统的最低条件。

# Building the Automated AGI Lab: Core Automation's Jerry Tworek and Rohan Anil

## Transcript

### 开场

**Jerry Tworek：** 如果我踢足球，这个学习过程很像强化学习。我反复踢球，每次做一点调整，再看结果是否接近预期，其中会发生某种自我强化。可当我学习数学时，感觉完全不同：我会阅读困难的概念，在脑中深入思考，直到它们突然贯通、彼此连接。这两件事都可以说是在从经验中学习，但方式截然不同。

我们现在用于“从经验中学习”的算力可能比历史上任何时候都多，但强化学习并不是从经验中学习的终点。未来几年，研究人员会提出更好的方法，以更丰富的方式利用这些数据。

### 为什么要重新审视 Transformer

**主持人：** Jerry、Rohan，非常感谢你们参加节目。你们是 Core Automation 的联合创始人，也是旧金山最受关注的新实验室之一。在成立公司之前，你们参与并领导了 AI 时代一些最重要的研究。Jerry 曾在 OpenAI 负责 Strawberry 和推理团队；Rohan 是 Gemini 的预训练负责人之一，此前参与 Google Brain 的基础 AI 研究，也曾在 Google 和 Anthropic 处理棘手的技术问题。

Jerry，你最近写道：“取代 Transformer 的第一步，是充分理解它曾经把我们带得有多远。”这是在为 Transformer 写悼词吗？

**Jerry Tworek：** 我最近很多访谈都变成了解释自己的推文：我当时到底说了什么，又是什么意思？

所谓欣赏 Transformer，就是理解它做得好的地方。要寻找替代方案，不能重复解决 Transformer 已经解决得很好的问题，而要聚焦它的弱点。理解一个系统的长处和短处，其实是同一件事，都是在认识 Transformer 的能力边界。

很多架构研究只是在尝试让 Transformer 更便宜、更高效。我很少看到有人认真思考，怎样让它更强大、具备更丰富的表达能力。现在我们已经非常擅长训练超大模型，也掌握了两类大规模算法：大规模预训练和大规模强化学习。接下来的问题是，机器学习的下一步是什么？

我认为，阻碍我们获得更好模型和更智能系统的瓶颈，已经转向架构本身。过去六年，我们一直沿着同一条路线前进：给本质上仍由 MLP 和 attention 构成的系统增加越来越多参数。现在应该重新审视这条路线。

Codex 和 Claude Code 已经为编程及工作流自动化带来了巨大价值。今天的系统和产品，是六年扩展训练的成果。正因为如此，我们首先要承认已经解决了哪些问题，再判断下一阶段尚缺什么。

每次我用 Codex 成功完成任务，我都会问自己：为什么没有把它再推进一步？我每天仍然要来工作，仍然需要逐项告诉它该做什么。为什么我还必须在这个循环里？Core Automation 的名字就来自这个问题：我们希望自动化任务，但为什么这些任务还没有被自动化？为什么 Codex 不能替我完成全部工作？我们的研究目标，就是弄清楚还需要什么样的模型、系统和能力。

### 从强化学习扩展到测试时学习

**主持人：** 认为问题出在架构本身，是一种相当反主流的观点。你为什么会得出这个结论？

**Jerry Tworek：** 根本矛盾在于，模型在实验室里训练，却被部署到现实世界。

这也来自我的个人经历。我加入 OpenAI 后一直是强化学习的坚定支持者。我相信，大规模强化学习是通往 AGI 必不可少的一步。看到 LLM 从 GPT-3 扩展到 GPT-4，而强化学习仍使用得很少时，我相信一旦开始扩展 RL，我们就会解决所有问题。

后来我们真的开始大规模扩展 RL，我就在这项工作的中心。假如你在 2024 年问我什么时候会有 AGI，我会回答 2025 年。我当时认为，所有问题即将得到解决。

我们训练了一个又一个模型，模型不断变好，基准测试分数不断上升。但现实世界里的任务并没有全部解决。问题在于，用于评估模型的 benchmark，本质上与训练模型的任务来自同一种分布；训练与评估是同一枚硬币的两面。现实世界的任务却更混乱、更模糊，也与训练分布相差很大。

训练模型的人经常抱怨没有足够困难的训练任务，但即使把现有训练任务做到极致，模型仍没有覆盖完整的现实世界分布。因此，我得出的结论是：模型必须能够在测试时学习，能够跟随用户，在用户的数据、真实任务和真实分布上继续学习。

今天的 Transformer 为什么没有做到这一点？测试时学习大致有两条现成路径。

第一条是上下文学习（in-context learning）。它没有灾难性遗忘（catastrophic forgetting）这个根本问题，数据效率也不错，但扩展性很差，能够容纳的信息有限，而且构建 context 本身还存在机械限制。我使用 Codex 时，大约二十分钟后就需要压缩上下文再继续。假如模型只能学习二十分钟，这远远不够。

第二条是持续微调（fine-tuning）。但持续微调会遇到灾难性遗忘，数据效率也很低。这些问题都不容易解决。如果解决方法很简单，早就有人解决了。

我的判断是，我们需要找到一种可以通过元学习获得、并在架构层表达的学习算法。它必须能够表示“学习本身如何发生”，并在长得多的时间尺度上工作。

### 扩展定律背后的经济约束

**主持人：** 新架构还会像 Transformer 吗？在 Transformer 出现之前，OpenAI 已经尝试扩展强化学习很久了；似乎正是 Transformer 提供了一个可以扩展 RL 的世界模型先验。你要怎样扩展一种全新的范式？

**Jerry Tworek：** 这两件事大致同时发生，但真正改变局面的主要是经济性。技术上也可以扩展 LSTM，只是几乎没有人敢沿着那条路线投入。LSTM 的扩展定律明显更差。假如从未发明 Transformer，我们也许仍会不断扩展 LSTM，也会得到一些模型，但训练成本会高得多，产品表现会弱得多，很难说服投资者投入巨额资金，因为得不到足够的市场回报。

Transformer 最了不起的地方，是它具有经济价值：训练成本低于模型能够创造的收入。这在机器学习里近乎魔法，并不是任何架构天然都能做到。LSTM 很可能无法形成这样的经济闭环。

很多架构其实都能扩展。过去研究人员不愿扩展，部分原因是扩展曾被视为“不够科学”。算法研究更关注如何提升效率，在相同算力预算下获得更好结果。OpenAI 当时做了一个重要押注：不把重点放在越来越复杂、越来越高效的算法上，而是寻找更简单、更容易扩展的算法，然后持续增加算力。OpenAI 因此受到学术界长期批评，但也正是这个押注带来了今天的模型。

Core Automation 的一个核心判断是，架构研究长期停留在过小的规模。很多人会先在小数据集和低算力条件下测试新架构，只有小规模证明有效后才考虑扩展。但强化学习告诉我们，有些能力必须达到最低算力和基础能力门槛后才会出现。很可能也有许多架构只有达到一定规模后，才会表现出有趣和有用的能力。

**主持人：** 如果需要相当高的基础算力，这听起来更适合在大型研究实验室内部完成。为什么要成立公司？

**Jerry Tworek：** 关键是时机。最大的实验室恰好处于史上最激烈的市场竞争中，这让它们不愿尝试不同路线。Transformer 已经可以盈利，如果继续扩展它就有机会赢下一个季度，那么很难把大量注意力和资源投入一种也许一年或两年后才会更好、甚至重新定义行业的方案。

我几乎和所有大实验室都谈过，它们对 Transformer 替代路线没有太大兴趣。规模稍小的实验室则在努力复制领先实验室的做法。现在所有人都在开发同一种 coding agent。看看最近一周的发布，每家公司都在推出 coding agent。我们需要不同路径，这正是 Core Automation 想填补的生态位置。

### Rohan：计算应该花在哪里

**主持人：** Rohan，Transformer 被发明时你就在 Google Brain。你同意 Jerry 对 Transformer 的这篇“悼词”吗？

**Rohan Anil：** 同意。Ashish Vaswani、Noam Shazeer 等人提出 Transformer 时，我也在做模型蒸馏相关工作，我们在同一次内部研究会议上展示。它当时在 Google 内部并没有引起轰动，只有少数人真正理解其意义。大多数人只是觉得，这又是一项普通工作。

最初的 Transformer 论文针对的是一个非常具体的问题：机器翻译。它在翻译任务上击败了 LSTM。Google 内部确实有人希望扩展语言模型，但直到 GPT-2 和 GPT-3，人们才真正看到 Transformer 的巨大价值。

我看架构时，核心问题是“怎样花计算”。Transformer 是一种曾经非常高效的计算方式，但今天行业的大量算力都花在推理阶段逐个生成 token。

如果要寻找更好的架构，就应该把预训练和 RL 放在一起优化，寻找比当前 chain-of-thought token generation 更有效地使用算力的架构。今天的流程大致是：预训练构建了一个具有固定 context length 的 Transformer，RL 随后发现这还不够，于是通过每次增加一个 token 来追加计算。这从推理角度非常低效，因为系统只能逐个 token 自回归解码。业界于是用 speculative decoding 等办法补救，但它们更像是对“每次只能生成一个 token”这一结构问题打补丁。

Transformer 在如何分配算力方面还有很多问题。很长时间里，行业训练的都是大型 dense model；之后又花了大约两三年，才把架构演进到今天习以为常的稀疏化和 Mixture of Experts，并解决相应的训练效率问题。这些今天看似显然的设计，当初并不显然。

Transformer 的一个核心问题是计算深度不足（computational depth）。多数 Transformer 即使被称为深度学习，实际也只有大约一百层。我们还没有真正证明模型能够学习极深的表示。

通过 RL 让模型生成 chain of thought，是增加计算深度的一种方式。每增加一个 token，就相当于增加一段计算路径，从而越过预训练架构原先设置的深度上限。增加推理 token 可以带来更强结果，也就是 inference-time scaling；代价是模型必须生成更多 token，而且仍然一次只生成一个。这一问题可以从架构层直接改进，也是我们正在研究的方向之一。

基础研究通常要五六年才能进入工业应用。要加快这个过程，组织首先要明确这项研究非常重要，并把它当成真正的押注。Jerry 内心一直相信 RL 必不可少；我在 Google 时则是预训练的极端支持者。

另一个现实要求是，新架构必须在硬件上高效运行。理论最优、但无法在硬件上高效执行的架构，对任何人都没有用。从研究构想到生产化，再到内核实现，需要一个端到端闭环。现在只有少数地方拥有真正一体化的团队。我们把各领域专家放在一起，不让他们分散在不同孤岛里，让所有人从端到端视角解决同一个问题。这也是我加入 Core Automation 的原因。

假如把这件事完全交给现有行业机制，取代 Transformer 可能需要更长时间。许多人已经在抱怨 token 成本。我来自 Google，习惯思考怎样为数十亿人提供服务，必须满足严格延迟和 token 数量限制。今天能够使用前沿技术的仍只是全球人口的一小部分。需要有人加速更高效的架构，让技术能够服务更多人，我们正在押注这件事。

### Transformer 的能力上限

**主持人：** 你说 Transformer 的计算深度不足。如果这是关键问题，它具体意味着什么，又该怎样解决？

**Rohan Anil：** Transformer 通常很浅，最多大约一百层。之所以称为深度学习，是因为我们希望它学习更深的表示，但目前没有人真正展示过极深表示的学习。通过 RL 让模型执行 chain-of-thought reasoning，可以增加计算深度，因为每生成一个 token，模型就增加一条计算路径。这样可以突破预训练架构设定的限制，但也带来了逐 token 生成的低效率。我们正在研究怎样让这类计算更高效。

**主持人：** 如果 Transformer 不是最终形态，它还能把我们带多远？什么时候会触顶？

**Jerry Tworek：** 这取决于我们用 Transformer 训练什么，以及允许它做什么。

预训练擅长把互联网上的知识压缩进 Transformer；RL 则可以把我们想要的工作流“烘焙”进模型。Transformer 可以容纳人类知识、知识之间的关系，以及组合知识的方法。只要某项任务存在训练数据，就可以把它训练进一个使用大量算力和全球数据构建的巨大模型。

但可以做一个思想实验：如果 OpenAI 和 Anthropic 今天停止训练新模型，把当前 Transformer 当成最终版本，会发生什么？几个月或几年后，模型会越来越没有用。即使实验室记录了全球人类今天在做的每项工作、任务和环境，世界仍会出现新事件、新关系、新任务、新代码库和新工具。

Transformer 的价值高度依赖于有价值的信息和任务是否已经进入训练。当它们没有进入训练时，模型表现就会下降。模型具备一些适应能力，但幅度不大，也不灵活。这就是我认为 Transformer 会触顶的地方。

如果有一个理解 Transformer 局限的人类，他可以调度模型、撰写合适的 prompt，并把失败任务加入下一轮训练数据，模型就能变得非常成功。但这个闭环仍要求实验室替用户重新训练模型。问题是：我们是否能让模型在不返回实验室重新训练的情况下自行更新？

### 强化学习不是从经验学习的终点

**主持人：** 你们读过 Rich Sutton 和 David Silver 的论文《The Age of Experience》吗？你们在多大程度上赞同它，哪些观点不同？

**Jerry Tworek：** 强化学习并不新。从某种意义上说，“经验时代”一直存在。人们批评预训练，是因为它使用静态数据，而且数据主要由别人生成。我甚至认为，今天的预训练在很大程度上是在把其他模型蒸馏进新模型，因为互联网上越来越多 token 由 AI 生成。

预训练本质上包含行为克隆、模仿和对互联网数据的压缩。强化学习也早已被用于双陆棋、围棋、StarCraft、Dota，现在又用于编程。它们的共同点，是模型生成自己的经验，再从经验中学习。

真正值得注意的是，强化学习并不是从经验中学习的唯一方法。未来还需要算法层面的创新。RL 只是实现目标的一种数学形式。我们当前使用 RL 时，通常依赖大量并行 rollout 来降低方差，并比较模型在多个平行版本世界中的表现，但人类并不是这样学习的。人类利用经验的效率更高，方式也更多样。

大脑里可能并非只有一种学习算法，而是多种算法相互协作。踢足球很像强化学习：反复踢球，每次略作调整，看结果是否接近目标。学习数学却完全不同：阅读困难概念，在脑中深入思考，直到它们突然贯通。两者都在从经验中学习，但机制截然不同。

所以，我的结论是：我们一直都在从经验中学习，而且今天投入的算力可能比以往任何时候都多；但强化学习不是终点。未来几年会出现更好的方法，在更丰富的设定中利用经验数据。

### 优化器、架构与端到端训练

**主持人：** Rohan，你的很多工作都围绕优化和效率。怎样才能得到计算效率和数据效率高出几个数量级的学习算法？

**Rohan Anil：** 我会先从衡量方式入手。今天定义的预训练，本质上围绕压缩展开。我们观察 perplexity，衡量怎样降低它，然后发现增加参数和算力有效。算力每在对数尺度上增加一次，指标就改善一点。这种方法适合建立模型先验，但不是看待最终问题的正确方式。

我们应该端到端地问：训练模型究竟是为了什么？应该看最终结果。比如我训练一个模型后交给 Jerry，他再做 RL，可能会破坏我在预训练阶段建立的全部 perplexity 指标。预训练是迄今启动这个过程的最好办法，各实验室也确实创造了很有价值的智能，但它只是 bootstrap 阶段。

真正的数量级改进，可能来自把预训练和 RL 合并为一个训练过程，也就是一个新的学习算法。

我在 2016 年进入 Google 时，从逻辑回归优化开始，参与了 Sybil 大规模线性求解器的工作。神经网络兴起后，我想做的事情很明确：理解训练算法，并让它变得更好。

后来 Vinit Gupta 来找我，说听说我很擅长写优化方法。他们在白板上构思了一个方案，后来成为 Shampoo optimizer，希望我帮助把它扩展到大规模神经网络训练。我的经理 Yanghui Wu 一直支持这项工作，直到我 2024 年离开。但很长时间里，社区和很多同事对此并不兴奋。有人认为 Adam 已经够用，为什么要把时间花在优化上？

对我而言，既然已经投入大量算力，就应该让训练本身变得更好。优化器和架构是一枚硬币的两面。更强的优化器可以训练更难优化、但性能更强的模型；较弱的优化器则要求架构本身更容易优化。架构研究中有大量设计，其实是为了让网络能够被现有优化器训练。

我们后来把 Shampoo 用在 Gemini 1.5 Flash，社区也逐渐重视这条路线。之后出现了 SOAP 等工作，形成了以 Shampoo、SOAP 等名称组成的一系列优化器研究。相较此前方法，它可能带来约两倍改进。

即便如此，Shampoo 利用的训练信息仍然很少。训练时纳入的信息越多，改进空间越大。某种意义上，优化算法会决定你能够发现什么架构。残差连接对训练神经网络极其有用，但已经有人用更好的优化方法移除残差连接，并学习到更深的表示。计算效率的大部分提升，将来自架构、优化方法以及对问题的端到端思考。

RL 当前使用算力的方式也非常低效。模型得到的反馈很少，却要解码很长的 chain of thought，最后只把一个很小的反馈信号写回网络。这是一个很明显、可能带来数量级改进的目标。

**主持人：** 我们最终会接近，甚至超过生物学习效率吗？

**Rohan Anil：** 至少使用现有硬件，我认为可能性很低。正如 Geoffrey Hinton 所说，生物系统使用的是“有生计算”（mortal computation）：人在成长过程中构建自己的神经回路，学习算法与硬件共同形成；人死亡后，这套硬件和算法也消失。

神经网络则不同。硬件保持不变，网络也保持不变，却以很低的效率学习，需要更多网络单元和大量并行计算，才能传递少量信息。除非我们设计出更接近人类工作方式的硬件，例如更多使用模拟计算，同时解决模拟电路、纠错和信息传递问题，否则很难达到生物学习效率。所以短期内，人类应该还算安全。

**主持人：** “预训练和 RL 应该端到端优化”听起来似乎很直观。大型实验室是否已经意识到这一点，只是组织结构和流程妨碍了落地？

**Rohan Anil：** 它并不显然，因为两者是完全不同的优化问题。RL 有先验、rollout 和更高方差；预训练使用超大 batch，单位时间能够投入更多并行算力。只有深入理解为什么简单拼接两种训练过程不起作用后，才可能真正把它们统一起来。

如果询问大实验室最优秀的研究人员，他们可能会说这个方向合理、值得探索，但不会把它放在最高优先级。实验室必须赶在下一个发布周期训练新模型。正如 Jerry 所说，公司正在按发布周期竞争，因为“token 业务并没有黏性”（tokens are not sticky）。在这种环境下，即便只是六个月的长期研究，也很难获得优先资源。

### 建立原生于 AI scientist 时代的实验室

**主持人：** Sam Altman 和 Dario Amodei 都谈过 AI scientist。研究人员的工作正在发生根本变化，而你们可以从公司成立第一天就为这个时代设计组织，因此可能运行远多于传统实验室的实验。研究工作究竟可以自动化到什么程度？你们怎样建设“全球自动化程度最高的实验室”？

**Jerry Tworek：** Core Automation 所说的自动化，是让每个人拥有尽可能大的行动能力。我们不是简单地把人移出循环，而是让人在有限时间里完成尽可能多的工作。

人步行只能走一段距离，骑自行车可以走得更远，开车则能覆盖更大范围。过去农民用手耕作，只能处理很小一块土地；有了机器，就能管理大得多的土地。研究自动化也是同样的逻辑。

我非常喜欢今天的 coding agents，也很高兴看到它们出现。某种意义上，这正是我多年工作的目标，包括编程研究，以及在 OpenAI 内部开发多个版本的 AI scientist。最后我意识到，成立公司是实现这一愿景的最好方式之一。

今天单个研究人员可以完成多得多的工作。迭代速度、研究速度、验证想法并获得数据的速度，都已发生根本变化。你可以勉强调整旧组织、旧团队工作流和旧数据收集方式，也可以从头建设一套原生流程，最大限度赋能每位研究人员，让他们更快迭代自己的想法。

我们正在重建 deep learning stack，重新思考几乎每个操作有哪些不同实现方式。即使每天只能完成一个此类实验，也已经比过去快很多。物理定律并没有规定我们不能每天做十个，甚至两百个实验。对于架构搜索和优化过程，更多高质量实验意味着更有机会找到在 deep learning 环境中真正有效的方法。

我们的团队从一开始就围绕 agent 和自动化建立。我们在做一个组织实验：一支尽量精简、尽量自动化的团队，究竟可以把前沿研究推进多远？

### 什么才算 AGI

**主持人：** 我们什么时候才能确认已经达到 AGI？

**Jerry Tworek：** 我过去常说，每个人心里都有自己的 AGI 定义。OpenAI 的定义是，在所有具有经济价值的工作上超越人类。但这里仍要回到前面的问题：如果 OpenAI 停止训练新模型，自动化水平还能维持吗，还是会随着环境变化而下降？

对我而言，AGI 是一个能够在完全没有人类参与的情况下改进自身的模型（a model that can improve itself without human in the loop）。这时我们才可以有意义地讨论 AGI，因为改进 AI 模型本身就是一项人类可以完成、并且具有经济价值的工作。

但到目前为止，把人从模型工作循环中彻底移除一直极其困难。我们离目标还很远。我几乎找不到一项任务，模型能够真正把人完全移出循环。今天成功的是“人类与 LLM 的混合系统”，没有人类参与的 LLM 则远没有成功。

我在 2024 年和 2025 年初看到的是，当前路线无法把我们带到这个目标。Core Automation 或其他机构都需要进行更深入的研究，让模型能够在测试时学习和适应，而且适应程度必须远超今天。

### 六个月路线图：先自动化 kernel generation

**主持人：** 我们一直从不同角度触及同一个问题，像几个蒙着眼睛的人在摸象。你愿意分享 Core Automation 的总体计划吗？

**Rohan Anil：** 我可以分享未来六个月的路线图。新架构不能只在理论上表现好，还必须运行良好，并让用户，包括实验室里的我们自己，真正使用。

我们现在可以做很多事情，但最困难、也最希望自动化的是内核生成（kernel generation）。面对固定的 GPU 硬件，我们既要训练模型，也要运行推理。我们希望构建能力最强的模型，把“产生一个能够消除架构瓶颈的新想法”到“让它在 GPU 上以尽可能高的 TFLOPS 运行”之间的时间压缩到最短。

当前 coding agents 与人类配合已经能走很远。以我们和 GPU MODE 举办的 QR kernel 竞赛为例，QR factorization 是一种经典线性代数运算，会用于 Shampoo 等优化方法，也用于许多其他场景。目标是在 B200 节点上高效执行特定矩阵形状的 QR 分解。

直接使用 cuSOLVER 可以得到一个基础性能；人类配合搜索循环，大约能达到 7 倍加速。但要得到约 60 倍加速的方案，需要世界上判断力最强的极少数专家，可能总共只有三个人，并在四周内向 coding agents 投入约 10 万美元。今天的模型距离独立生成这种 60 倍性能的 kernel 还非常远，这就是一个真实瓶颈。

QR 分解看似单一问题，实际可能包含三个不同算子：处理一个 panel、执行矩阵乘法、再把结果折回去，如此反复。把这个问题交给当前前沿模型，例如 Gemini，它们仍无法解决。对我们来说，自动化这个环节非常重要，因为它正是探索更高效架构的内部循环。

**主持人：** 为什么首先选择 kernel？是因为要最大化每次浮点运算产生的智能，就必须自己生成 kernel 吗？

**Rohan Anil：** 我做过三个相关项目，其中两个已经进入工业应用。第一个方向是二阶优化方法（second-order methods），kernel 是核心瓶颈，因为算法必须真正高效运行。在 Google 这样的地方，不可能为了两倍收益多花十倍算力；更现实的要求，是增加不超过约 20% 的预算，换取两倍收益。

当时很多操作都是新的，几乎没有人研究对应 kernel。Google 内部可能只有 Rasmus Larsen 和 Peter Hawkins 等极少数专家能够编写所需的底层 XLA HLO 代码，而且完成实现花了两年。

另一个项目是我和同事在 2020 年尝试用额外 memory 替代 Transformer 的部分参数，我们称之为 N-gram memory。较小版本曾在内部部署，但训练需要高效执行稀疏 gather 和 scatter。要做到这一点，需要硬件变化和对应的软件支持。

我们与 TPU 团队及其他相关人员开过很多会，疫情期间一度认为这项支持终于会落地，但最终没有实现。我后来在 Anthropic 使用 TPU，离开时才刚触及实现的可能性。与此同时，DeepSeek 后来提出了自己的 N-gram 记忆方案，通过 N-gram embedding 增加 memory，并在部分场景替代 MoE。对我来说，那像是一个跨越五年的想法，看到它出现我非常高兴。

如果不编写 kernel，这类架构甚至无法实现。为了达到最高性能，需要辅助生成或直接求解 kernel，而且硬件 roofline 留出的空间很大。以 QR 为例，cuSOLVER 能提供一定性能，而竞赛获胜方案快约 60 倍。这已经是完全不同的计算条件，会打开一整套此前无法实际使用的算法。QR 对 Transformer 训练、优化器以及 eigen decomposition 等分析都很基础，但拥有这种能力的人才极少且分散。如果模型具备这种能力，价值会非常大。

### 如何判断找到了 Transformer 的替代者

**Jerry Tworek：** 从更高层概括，Core Automation 的目标是构建能够持续学习、并从部署中继续学习的模型。我们认为 Transformer 无法实现真正的持续学习，因此必须找到不同架构，也就是 Transformer 的替代方案。

我们希望建立一个高度自动化的实验室，以最快速度开展大规模实验，快速迭代并测试大量架构想法。与此同时，我们要对目标有清晰先验，才能高效搜索架构空间，比其他人更快到达正确方向。kernel、大规模训练和新架构实验，都是对这个空间的探索。

**主持人：** 你们可以通过实验寻找更好的架构。但当真正找到时，要怎样确认“就是它”？

**Jerry Tworek：** 这个问题有两个角度。依照我的经验，每项成功研究最终都会出现一张与其他图不同的图表：某条曲线以不同方式弯曲，你看到后知道这正是自己想要的结果。

但图表通常出现在研究旅程很晚的阶段。在此之前，研究者多半已经知道自己想找什么，也大致知道自己在做什么。我半开玩笑地说，我人生中最好的图表都先在梦里出现，然后才在真实实验中出现。我隐约知道目标是什么，只是不知道它什么时候会真正“咬合”。

大多数时候，你知道自己在找什么，却一直找不到。尝试第一种方法，不行；换第二种，仍然不行。深度学习系统非常复杂，往往必须连续把五件事都做对，系统才会开始工作。最终所有正确部件汇合，曲线呈现出预想的形状，那时你就知道找到了。

我们真正寻找的是能够在测试时学习，并表现出有意义、长期适应能力的系统。我们会用实验室的日常工作评估它：系统是否每天都更擅长完成 Core Automation 科学家的工作？

**Rohan Anil：** 最直接的测试，也许是整个团队去度假一周，回来看看实验室是否自己产出了更好的成果。

**主持人：** 那回来以后做什么？

**Rohan Anil：** 把假期延长两倍、三倍、四倍，直到我们永久休假。

**主持人：** 这是一个很好的结尾。Rohan、Jerry，谢谢你们参加节目。你们过去的工作深刻影响了今天的 AI，我也非常期待看到 Core Automation 接下来能做出什么。

**Jerry Tworek、Rohan Anil：** 很高兴来到这里和你们交流，谢谢。

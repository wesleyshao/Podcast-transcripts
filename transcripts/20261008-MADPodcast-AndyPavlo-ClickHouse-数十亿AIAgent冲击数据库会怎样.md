**主持人（Matt Turck）：** 嗯，它们应该推荐哪个？刚才那是它们实际推荐哪个的答案，但是……

**主持人（Matt Turck）：** 对。我想引出的部分是速度问题，那正是 ClickHouse 擅长的地方，我们稍后会更多地聊 ClickHouse。另外还有“上下文层”“本体（ontology）”这样的概念，它似乎在推动图数据库。你觉得什么是合理的？

**嘉宾（Andy Pavlo）：** 我对图数据库有很强烈的看法。我认为你不需要图数据库。我还没见过任何基准测试表明原生图数据库优于关系型数据库系统——前提是这些关系型系统在 SQL 或 API 中有正确的构造，让你可以在服务端完成图遍历，而不用来回往返。SQL 标准在 2023 年加入了对属性图查询的支持，Oracle 支持它，Postgres 本来应该在今年支持，在 Postgres 19 中推出，但我想它被推迟或者回滚了，我不知道为什么。不过这都是题外话。不，我认为上下文层同样取决于需求：你有多少个 agent，多个 agent 之间是否有共享状态。对于其中很多场景，Postgres 通常是、也应该是 OLTP 的首选。如果你做的是分析，那就是另一回事了。

**主持人（Matt Turck）：** 我们来聊聊 MCP。

**嘉宾（Andy Pavlo）：** 好的。

**主持人（Matt Turck）：** 过去一年左右，似乎每家数据库供应商都在自己的产品里加了一个 MCP 服务器。你对此怎么看，有哪些利弊？我是从一两年前那一整波 text-to-SQL 运动的角度来问的——当时大家都想让 LLM 在数据库之上工作，尤其是用于分析目的，而那件事某种程度上没成功。我们现在做到了吗？

**嘉宾（Andy Pavlo）：** text-to-SQL 就是把自然语言转成 SQL。这是人们从 70 年代就一直在尝试做的事，对吧？时不时地，自然语言处理会有某种突破，人们就说：“好，终于能实现了。”但在 LLM 之前一直没实现。我一直对那些 text-to-SQL 框架的学术文献和研究论文持怀疑态度，因为它们经常展示 Spider 和另外几个基准——这些是众所周知的基准，模型就是在上面训练的，所以它当然会复述出正确答案。其实我昨天还在和一家非常大的银行的人聊，他说他们现在有了一个 text-to-SQL 接口。在最初的实现中，他们用的是现成的东西，然后在内部做了进一步优化，但准确率大约是 60%，也就是说 LLM 或 agent 只有 60% 的时间能生成正确的 SQL 查询、得出正确答案，对吧？这大致也是我之前在其他一些报道中看到的。但他们说，通过多年、花费数百万美元，提供一个更丰富的语义层、上下文层，他们把准确率提高到了 99.5% 左右，这太疯狂了。我认为如果你投入时间建立正确的语义层和所需的上下文信息，这件事现在是可行的——这样 agent 就有足够的信息，知道如何从你提的问题推导出正确的 SQL 查询。但再说一次，那是一家拥有无限资金的大银行，他们做成了。我认为如果一个普通人现在随便下载个东西，会发现现有工具达不到那种熟练度和准确度。但这并不意味着我们做不到，对吧？至于 MCP，模型上下文协议，我理解他们为什么这么做。我想它出自 Anthropic，然后所有人都很快把它采纳为标准。时不时就会有 Hacker News 帖子说 MCP 已死之类的。我不认为它会消失。它基本上就是一个 REST 接口，对吧？一种标准方式，用来规定从 agent 到你拥有的任何数据系统的请求应该是什么样的。接收 MCP 请求的数据系统，它的工作就是把请求转换成获取所需数据的正确 API 调用。对数据库系统来说，就是写 SQL 查询去获取你需要的数据。但通常——很多时候——它是对传入内容的严格翻译，而不是试图推导 MCP 请求的语义含义，因为 MCP 请求必须定义得比较明确。我对 MCP 没有意见。我认为它不是解决世界上所有问题的灵丹妙药，它只是一个数字接口，对吧？你现在可以用它把不同的 agent 和不同的系统衔接起来、互操作，去收集你需要的数据。所以我完全支持，因为你是在更多地使用数据，而不是用某种自己土法炮制的东西。所以，是的，很棒。它能改进吗？我觉得它效率不高，因为你是通过网络发送人类可读的文本去获取数据。显然用二进制协议有更好的方法，但说到底，它够用了，对吧？而且它似乎是大家都在用的标准。

**主持人（Matt Turck）：** 它应该成为你前面提到的那个安全层吗？

**嘉宾（Andy Pavlo）：** 是的，你可以，但这和请求来自一个传统应用客户端、通过 JDBC 或 ODBC 发出的 SQL 没什么区别——也就是这些数据系统的网络协议或终端。请求来自那里，还是来自一个通过 MCP 发出的 REST 请求，没有区别。说到底就是：好，我收到了这个请求，我需要知道是谁在请求、他们要求做什么、是否应该允许他们做。所以我们之前谈到的那些护栏，无论请求是以 SQL 进来还是以 MCP 进来，都是一样的。

**主持人（Matt Turck）：** 好。这是对话的一部分：数据库作为 agent 的记忆层或执行层。我们把讨论反过来，聊聊 AI 能为数据库做什么。显然，我们生活在一个 AI 几乎可以编写任何代码的世界。对数据库也是如此吗？

**嘉宾（Andy Pavlo）：** 是的。举个例子，我在卡内基梅隆大学教数据库系统课程。一年前，agent 还无法完成我们的整个项目。这些项目大概是：我们给你一个数据库系统的脚手架，你必须实现索引、查询引擎之类的东西。它能做一部分，不能做全部。我想是 Anthropic 去年推出的 Opus 某个版本，一下子打开了闸门。agent 基本上不需要什么提示就能完成我们所有的作业，对吧？当然，这方面有大量训练数据，因为我们所有的项目都是开源的，都在 GitHub 上——我们不仅让卡内基梅隆的学生用，也让校外的学生用——所以有大量训练数据供它们去实现这些东西。所以我认为 agent 现在基本上可以实现构建数据系统所需的任何东西。当然，你必须用正确的方式提示它、手把手带它，确保生成正确的设计，或者根据你想要的设计产出实现。但说到底，我认为这些 agent 非常有能力做到这一点。

**主持人（Matt Turck）：** 所以它们可以构建一个完整的数据库？因为作为风险投资人，我对构建数据库的经验是：那是一段 10 年的痛苦旅程，前三年几乎什么都没发生，世界上一些最聪明的人聚在一起，去解决每次看起来都难以逾越的问题。而我们现在说它能把整个东西都构建出来。

**嘉宾（Andy Pavlo）：** 是的。数据系统领域有句老话：一个数据系统需要 10 年——你可以在 3 年内构建前 90%，剩下的 10% 需要接下来的 70 年，或者说 7 年。所以，是的，我认为 agent 非常有能力——当然要有足够的 token——在足够的指导下，人们可以 vibe coding 出一整个数据系统。现在肯定有公司在这么做，而且几乎每家公司都在用 agent 帮助开发。我热爱数据库，我的一个副业项目是“数据库的数据库”dbdb.io。我们现在做的一件事是追踪我知道的每一个数据系统。对于开源的那些，我们每天晚上都会从 GitHub 拉取所有最新的提交，然后追踪哪些提交是由 Claude 或 Codex 之类的工具共同署名的。当然有人会关掉这个功能，你就不知道它是不是生成的，但大多数人不会关。到现在，我认为 60% 以上的开源数据库系统都有来自 agent 的提交。

**主持人（Matt Turck）：** 那么除了编写之外，这是否也适用于运行？回到“自动驾驶数据库”的概念，我记得那是你 10 年前的一个大项目。

**嘉宾（Andy Pavlo）：** 是的。

**主持人（Matt Turck）：** 给我们讲讲那段历程。当时不可能、而今天变得可能的是什么？

**嘉宾（Andy Pavlo）：** 好。我刚到卡内基梅隆大学时，前几年做的一件事是去拜访各家公司，看看他们在数据库方面面临什么样的挑战。我一次又一次看到的总体主题是：运行、维护和优化这些系统是一场巨大的挣扎。这对我来说并不是什么重大发现，人们几十年来一直在尝试解决。自从 1970 年代关系模型和关系数据诞生以来，人们就一直在尝试做自动调优：索引、分区键、分片键、调参旋钮等等。微软研究院在 2000 年代初的 AutoAdmin 项目中做了大量工作，他们有一堆工具让你能够自动管理和优化数据系统。

**主持人（Matt Turck）：** 补充一下背景，这是因为数据库有成千上万种可能的配置。

**嘉宾（Andy Pavlo）：** 对。比如我的表上应该建哪些索引来加速查询？显然如果索引太多，写入会变慢，磁盘空间也会用完。还有控制系统运行时行为的各种旋钮：给某个内存池用多少内存、给索引用多少，等等，对吧？这超出了任何一个人的推理能力。如果你开始看——比如你有成千上万个数据库——任何人都不可能管理得过来。所以我们花了一些时间研究如何构建自动化工具，使用机器学习——也就是现在你可能称之为 AI 的东西——用自动化方法、机器学习技术来实现自动化。我们有两条研究路线。一条是把数据库系统当作一个不透明的黑盒：我们不能改变内部，只用这个数据库系统暴露的 API 能做什么？基本上就是如何自动优化现有的数据库，MySQL、Postgres、Oracle 等等。另一条研究路线是：如果你从零开始构建一个数据库，假设它将由机器学习工具——或者现在我们所说的 agent——来控制，你会如何以略有不同的方式设计系统？我们在优化 MySQL、Postgres 时学到的很多东西，最后都用在了我们自己的系统里。对于这些自动化工具来说，挑战始终在于要有足够多的生产数据库训练数据，并且能把在一个部署上优化学到的东西应用到另一个部署上。就像我之前说的，大多数人有一个预发布或开发环境，然后有生产数据库。你显然不想在生产数据库上随便尝试，那可能会在你摸索怎么调优时拖慢速度、降低性能。所以你会在预发布数据库上验证，然后尝试应用到生产数据库上。但很多时候硬件从来不一样，工作负载也从来不一样。所以我们一直面临的一大挑战，就是获取足够的训练数据来喂给模型，从而在生产数据库上做出好的决策。然后 LLM 出现了，这真正改变了你解决这个问题的方式，因为它们基本上是在互联网上所有可获得的、关于如何调优这些数据库的博客文章、文档、最佳实践指南上训练的。在研究方面我们发现，LLM 在调优某些东西时可能能帮你完成 85% 左右。当然还有一些奇怪的边角情况，定制算法可以处理。但我们的模型——假设你有足够的训练数据——往往要训练好几个小时才能得出完美的最优配置，而 LLM 可以在大约 15 分钟内给出一个足够好的结果，这对大多数人来说已经足够了。那我们做到了吗？我们是否处于一个数据库基本可以自我调优、自我优化的世界？答案是肯定的，但当然取决于你实际想要多大的改进。就像我说的，LLM 能帮你完成 80% 到 85%。是否总有更多性能可以挤出来？是的，有些人总会在乎这些，因此我们过去构建的自动化方法对他们会重要得多。但对大多数人来说——其实让我非常惊讶的一件事是，当我们创办那家试图为 Postgres、MySQL 做自动调优的初创公司时……

**主持人（Matt Turck）：** 那是 OtterTune（字幕作 autotune）。

**嘉宾（Andy Pavlo）：** 对，OtterTune。让我惊讶的是，有那么多人在亚马逊或谷歌的云平台上直接用开箱即用的默认配置运行，他们会告诉我们：“哦，我们以为亚马逊在帮我们调优。”不，他们没有，对吧？所以有足够多的人可能在用默认配置运行——那个东西简直糟透了，别那么做——在这种情况下，LLM 可以进来摘掉一些低垂的果实，在短时间内为人们带来有意义的改进。

**主持人（Matt Turck）：** 在软件世界的其他领域，我们已经看到开发者这份工作的性质发生了深刻变化。如果你今天是 CMU 的学生，对数据库世界超级兴奋——是的，你可以去 ClickHouse 或 CockroachDB 这类公司工作。但除此之外，如果我们身处一个 agent 会去调用、管理数据库，而数据库本身又会自动驾驶的世界，今天还有什么工作需要深厚的数据库知识？

**嘉宾（Andy Pavlo）：** 我总是对上我课的学生说：即使你不打算成为数据库系统工程师、不去做 ClickHouse、CockroachDB 或 Postgres 的内核开发，说到底每个人都会与数据库系统打交道。如果你理解它们的内部机制、它们是如何实现的、对于给定的查询数据系统在试图为你做什么或不做什么，你就能更好地理解世界上、技术栈里正在发生的事情。那么你需要我的课才能搞明白这些吗？不需要。如果我那么想就太天真了，agent 已经把我所有的东西都吸收进去了，它们反正能复述我会教的所有内容。但说到底，无论你是从传统大学课程学的、自学的，还是让 LLM 教你的，只要你理解数据系统在试图做什么，它就会消除大部分谜团，帮助你理解你的应用中正在发生什么：为什么查询跑得慢或不慢。你就是处于一个更好的位置去理解正在发生的事情。所以如果你读计算机科学或工程学位，专注于数据系统——我认为那个“你自己从零写一个系统”的时代，如果我认为它还会继续存在，那就太天真了。但说到底，数据库公司仍然在招人来做这些东西，因为需要有人理解 agent 实际在做什么，并对其做出判断。

**主持人（Matt Turck）：** 但把问题问到底：我们是否会进入一个在数据库的管理和部署方式上完全没有人类参与的时代？

**嘉宾（Andy Pavlo）：** 我会说，ClickHouse 的架构、核心基础，按 2026 年的标准并不新颖，但按 2016 年的标准当然是新颖的。它的本质是：你以列式布局存储数据。也就是把单个列的所有属性、所有数据连续存放在一起，而不是像行存那样，把单个元组所有列的值连续存放。以这种方式存储数据；使用 CPU 上的向量化指令，在一条指令内同时处理多份数据，而不是写 for 循环、以更低效的方式运行；内置的压缩机制；它们采用日志结构存储的方式——你不断追加一堆变更，因为你想尽可能快地摄入数据，然后最终在后台进行合并，以更高效的方式存储。这些核心架构的很多理念来自 Snowflake 所做的工作，而在 Snowflake 之前，还有一个叫 VectorWise 或者说 X100 的系统——MonetDB/X100，后来商业化为 VectorWise——出自 CWI，也就是诞生 DuckDB 的同一个机构。所以人们为这些列存系统、分析系统、实时分析系统开发的很多理念一直在向下扩散。但据我所知，2016 年还没有哪个开源系统能做到所有这些。所以当 ClickHouse 一出场就说“嘿，我们拥有基于前人所有这些研究的全部东西”，这太了不起了，对吧？从那以后，DuckDB 有了类似的东西；还有阿姆斯特丹那帮人做的 Polars；Firebolt 最初是 ClickHouse 的一个分叉，他们重写了内部很多东西，现在也具备所有这些；Databricks 有自己的版本引擎。所以每个人都有这种建立在 Snowflake 和 VectorWise 工作基础上的架构。但再说一次，2016 年它超级新颖，现在它基本是标配了。我认为 ClickHouse 这些年做得非常好的一点，就是不断进一步提升性能，并扩展它们实际能支持的工作负载。

**主持人（Matt Turck）：** 恰恰相反，对吧。

**嘉宾（Andy Pavlo）：** 是的。

**主持人（Matt Turck）：** 图数据库我们在开头提到过。不是要针对它们，但 Neo4j 已经存在 20 年了。

**嘉宾（Andy Pavlo）：** 当然，是的。

**主持人（Matt Turck）：** 而这本该是图数据库在 AI 时代的高光时刻，对吧？那里发生了什么？

**嘉宾（Andy Pavlo）：** 我和 Hacker News 上的某个人有一个还没结的赌约。他说到 2030 年，图数据库市场将超过更大的关系型数据库市场。如果这成真了，我就穿一件写着“我爱图数据库”的 T 恤，用它拍驾照照片、大学证件照，挂在我的网站上直到我死的那天，对吧？我对此相当有把握。现在是 2026 年，还剩四年，这不会发生。不，它一直是个小众市场。从我在研究方面的视角来看，研究表明，如果你在实现引擎时做某些事情——ClickHouse 确实做了，DuckDB 也做了一部分——有些事情可以让你完成图遍历，而图遍历本质上就是对一张表做连接、自连接。你可以非常非常高效地实现这些东西，而且可以轻松超越 Neo4j。说你比 Neo4j 快，就像说我比一个坐轮椅的人跑得快——这有点胜之不武。但我想说的是，所有的图数据库，我认为即使是最好的那些，面对一个具备研究中这些优化、而且现在其中一些优化已经出现在某些系统中的系统，你都会输。你唯一会输给图数据库的情况，是你在客户端和服务端之间做图遍历：我得先算出下一个要看的节点，回到客户端，再决定下一个要遍历的节点。如果你这样来回往返，是的，它们会赢你们。但就像我说的，SQL 标准现在支持属性图查询，Oracle 已经有了，对吧？他们是这个 SQL 扩展的大力推动者，它允许你在服务端完成遍历。所以图数据库，我认为是一个糟糕的主意，没有任何理由让人真的想用它们。

**主持人（Matt Turck）：** GPU 数据库。

**嘉宾（Andy Pavlo）：** 是的。

**主持人（Matt Turck）：** 我知道你在这方面有特别的兴趣。曾经有一个周期，一批 GPU 数据库出现然后又消失了，现在似乎又在复兴。什么是 GPU 数据库？你的预测是什么？

**嘉宾（Andy Pavlo）：** GPU 数据库是这样一种数据系统：查询的执行端全部卸载到 GPU 上，GPU 通过 PCIe 连接，运行在同一台机器或另一台机器上。人们尝试为数据系统构建加速器的历史可以追溯到数据系统诞生之初。1970 年代它们被称为“数据库机器”（database machines），人们会构建专用硬件来运行排序和查询执行算子。这显然在 1980 年代初就消亡了，因为等你设计并流片出新的专用硬件时，英特尔或摩托罗拉已经推出了下一代 CPU，或者硬件变得更好了，你获得的收益就消失了。所以数据库硬件加速器基本上在 1980 年代就死掉了。90 年代、2000 年代没有太多动静，你看到有人尝试为数据库做 FPGA，而且时不时又会回潮。一些云厂商做了一点这类事情，但通常是在网卡上、在网络端对进来的数据做过滤。至于 GPU 数据库，2010 年代有一批系统在尝试。我们在大学办过一个系列研讨会，邀请所有做 GPU 数据库的人来讲他们在做什么、为什么比现有系统快。当时的大挑战是，对那些系统来说，你必须把整个数据库放进 GPU 的显存里，因为如果必须回到 PCIe 上，那就太慢了。那批初创公司中有很多逐渐销声匿迹，有些还在，但基本专门用于可视化。然后在过去一年左右，英伟达基本上吞掉了一批苦苦挣扎的 GPU 数据库公司。我曾是其中一家叫 Voltron 的公司的顾问。他们还收购了 HeavyDB。所以英伟达现在是全力押注这个方向。至于“构建一个以 GPU 为中心的数据库系统”这个想法长期是否成立，还有待观察。我听到的说法也是喜忧参半。这是公开信息：微软现在在云上提供了可以为你的数据系统做 GPU 加速分析的产品。另一家大型数据库公司——我不能说是谁——研究了 GPU 的经济性，认为不值得。我以前的一位学生现在是威斯康星大学的教授，目前在英伟达休假，他们有一个叫 Sirius DB（字幕作 Cirrus DB）的项目，它不一定是一个新的数据系统，而是位于现有系统和 CUDA 之间的一层，它支持把 DuckDB 的查询下放到 GPU 上运行。我想他们在 Doris、StarRocks 和 DataFusion 上也能这样做。所以在 ClickHouse，我们也在考虑研究这个方向，但这是研究。有意思的是要看在 ClickHouse 期望的方式和 CUDA 想要的数据布局之类的方式之间需要做多少转换；你如何在这些不同组件之间组织内存或共享内存。这是否真的合理还有待观察，但肯定有大量研究精力投入其中。我可以公开地说：英伟达显然在推动这件事，因为它能卖出更多 GPU，对吧？因为现在要拿到新 CPU 都已经够难了，每个人都受算力限制，内存也很难买到。现在计算硬件非常昂贵、很难买到，而 GPU 是所有硬件中最昂贵的，现在你还要说你的整个数据库都在 GPU 上运行。我不知道这是否合理，至少在短期内。但如果性能提升非常显著——一些研究表明确实如此——也许它就合理了。

**主持人（Matt Turck）：** 有没有某个新兴类别，或者某个类别中的细分领域，人们讨论得还不够？

**嘉宾（Andy Pavlo）：** 数据库方面的？

**主持人（Matt Turck）：** 是的。

**嘉宾（Andy Pavlo）：** 你总是可以为新硬件构建新的数据系统，但我在这方面的记录很糟糕。我们在实验性硬件上做过很多研究，结果它总是被取消，甚至都不算多实验性。比如英特尔有 Optane 持久内存，我们做了很多为它构建系统的研究，因为如果你假设你的 DRAM 现在是持久的——拔掉电源也不会丢失任何东西——这会从根本上改变你构建数据系统的方式。我们在这上面做了很多工作，然后英特尔砍掉了那条产品线。我们还在做另一项关于“存内计算”硬件的研究：想象一下 CPU 核心直接放在 DIMM 上的内存条。这样数据系统就可以说：与其把东西从内存拉进 CPU 缓存再计算，不如直接把查询发送到内存条本身去运行。我们在一个叫 UPMEM（字幕作 opm）的东西上做了很多工作，它被高通收购，然后去年被砍掉了。所以那也没成。所以在数据系统或新硬件上总有很多工作可做。但我会说，其实我不知道答案，对吧？这是我在 ClickHouse 试图搞清楚的事情之一，我们在最开始也谈过：agent 工作负载与人类或现有应用所做的事情是否有显著不同？如果有，为什么、怎么不同？你会如何改变数据系统的开发以更好地利用这一点？这还有待观察。我认为查询优化中总有很多有意思的问题，那仍然是数据系统最难的部分。增量物化视图是另一个大挑战。但这些都不是别人没想过的东西，人们几十年来一直在尝试做这些事情。所以我认为 agent 相关的东西可能是现在对我来说最有意思、最相关的：这些工作负载带来了什么变化，系统架构有什么变化？说实话，我不知道答案，只是还没看到。

**主持人（Matt Turck）：** 我之所以问，是因为总体感觉数据库市场正处于其历史上的一个特殊时刻：2010 年代曾有一波活动大爆发，有 SQL 与 NoSQL 之争及其所有演变，然后出现了 Databricks、Snowflake，现在是 ClickHouse，但在爆发力方面，事情似乎放缓了一些，我想你可以说是停滞了？

**嘉宾（Andy Pavlo）：** 是的，不过我们以前也经历过这种趋势，对吧？1970、1980 年代关系型数据库有很多活动，然后到了 1990 年代，市场在这些大型企业周围固化下来，Oracle、IBM、Teradata。如果你对数据库的唯一视角来自这类公司，那么是的，看起来已经停滞好多年了。但正如你所说，2000 年代、2010 年代有很多活动。我的意思是，相对于 AI，一切看起来都是停滞的，因为在计算机科学的历史上从来没有过类似的东西。这就像抓一只猎豹，给它灌一堆可卡因，再把它塞进一辆法拉利，人们开发这些东西的速度简直疯狂。所以相比之下一切看起来都很慢、或者死了、或者停滞了。但说到底，我认为体量会非常重要。我认为一个有意思的问题——就你说的成本和效率而言——是在你拥有的硬件上榨取尽可能好的性能，努力降低成本，这始终是一个有意思的挑战，值得去追求。但说到底，我不认为数据的形态会发生巨大变化，以至于需要我们抛弃所有关于数据库的已知知识——就像你不会提出一个新的算术或数学概念来取代 1+1=2 一样。关系模型本身就是你表示数据的基础，你只能在它的实现上做变化。所以肯定有很多工作可以让这些系统在这方面更高效，但我不认为你会抛弃一切，然后说 agent 需要某种你从未设想过的数据系统。说到底那讲不通。所以我认为那部分不会改变。我说过，总会有新硬件。我认为 SQL 当然还有可以改进的地方，也总会有人试图取代 SQL，我认为那可能是徒劳的。不过 SQL 最终可能会像——就像人们不再写汇编一样——因为 text-to-SQL 效果太好了，SQL 最终可能也会变成那样。我认为 agent 超级有意思，而获得更好的性能，至少在我看来，永远是一个可以追求的有趣挑战。你可以想象一个疯狂的世界：你说我不再需要为每个应用都用一个通用数据系统，我想 vibe coding 出一个专门为这一件事做这件事的数据系统，它可以高度专业化。你现在在某种程度上已经通过代码生成或对查询某些方面的即时编译在这样做了，一些系统这样做，ClickHouse、Postgres、德国人做的 Umbra。但高度专业化并让它可持续，可能是未来一个更大的研究问题。

**主持人（Matt Turck）：** 所以，我不知道这算不算一种悖论式的局面：一方面，就演进而言，这个行业目前有点停滞；与此同时，希望我们通过这次对话已经确立了，这一层本身一如既往地重要，这也是为什么你的朋友 Larry Ellison 是、或者曾经接近世界首富。

**嘉宾（Andy Pavlo）：** 他曾经是，截至今天他排名下滑了。

**主持人（Matt Turck）：** 我的意思是，Oracle 远不只是一家数据库公司，但他仍然是那家公司的……

**嘉宾（Andy Pavlo）：** 我是说，他们的总部大楼就是数据库（圆柱体）的形状。所以……

**主持人（Matt Turck）：** 是的，是的。但不管怎样，这至少说明了数据库的根本重要性。

**嘉宾（Andy Pavlo）：** 我会说，没有人在认真尝试取代 Linux，对吧？我是说，是的，针对不同环境、不同硬件有一些小众操作系统，但没有人在尝试大规模地完全取代 Linux。比如 FreeBSD，它源自 BSD、源自伯克利，比 Linux 还早，所以它至今还在。但对于数据库来说，总有新想法，或者人们认为自己能比别人做得更好。所以我不会说它停滞了。我只会说，短期内很多精力会集中在 Postgres 上，我们可以做一些事情来改进它。但与此同时，我仍然认为会有这些专用引擎。我不知道下一个工作负载是什么。再说一次，我还不清楚 agent 工作负载是否有显著不同，对吧？因为它们是在对应用的设计方式进行建模；向量查找与过去显著不同，你需要额外的算子、需要额外的索引来做这些事情。下一个东西是什么还不清楚，我不知道，但肯定会有的，一直都有。

**主持人（Matt Turck）：** 那也许最后聊这一点：未来五年。我们不一定知道它是什么样子。那么在此期间，是否意味着现有公司——ClickHouse 这类公司——会因为根本需求存在而不断变好、地位更稳固，而不会出现一波新的小型初创公司？

**嘉宾（Andy Pavlo）：** 当你说“更好”时，有两种“更好”。一种是现有查询能否跑得更快。是的，ClickHouse 还有改进空间，我们可以改进；其他系统也可以做同样的事。但就像我说的，在高层面上，ClickHouse 的架构与 Snowflake 在 2013 年所做的相似，Databricks 基本上也在借鉴一些现有理念，每个人至少在分析领域都在做差不多的事情。真正重要的——也是 Snowflake 做对的、构成其成功一部分的——是数据系统周围的东西：用户界面、开发者体验、数据摄入、与其他东西的互操作，这部分他们做得非常好。所以几乎可以说，数据库管理系统核心之外的那些“脚手架”实际上非常重要。这对我来说不是研究，但这是 ClickHouse 随着时间推移做得越来越好的事情之一，它有助于扩大系统的适用范围。系统的核心内核当然可以改进，但在最微观的层面上，ClickHouse 与其他系统在基本原理上相当相似，而周围的东西非常重要。我认为 ClickHouse 有些事情做得好，有些事情可以做得更好；Snowflake 有些事情做得好，有些可以做得更好；Databricks 和其他公司也一样。

**主持人（Matt Turck）：** 好的，感谢你抽时间来。祝贺你的新工作，你还用了一个说唱的类比来描述它，对吧？是什么来着？

**嘉宾（Andy Pavlo）：** 就像 Run the Jewels，把 El-P 和 Killer Mike 放在一起，这两个人各自都已经成名，你把他们放在一起，就像人们第一次把花生酱和果酱放在一起，对吧？所以我愿意认为我和 ClickHouse 走到一起就是那样。

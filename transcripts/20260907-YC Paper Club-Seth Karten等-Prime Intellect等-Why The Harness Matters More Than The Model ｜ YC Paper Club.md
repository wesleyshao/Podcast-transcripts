### 从静态 Harness 到自我改进

主持人：为了准备今晚，我周末读了一批经典文献，包括 Self-Refine、Reflexion、Voyager、Toolformer。我想用五分钟回顾一下，我们究竟是怎样走到这里的。许多最近才进入 AI 的人可能没有这段背景，所以值得讲一讲。

这里不会严格按照年代顺序排列，因为按时间讲反而不太容易理解。我会跳过不少论文，也会对一些工作作非常粗略的概括，先向作者们道歉。

最早的 harness，比如 2019 年 2 月的 GPT-2，大致就是一个循环：只要还没有到 end of sequence，就继续生成。加上 top-p sampling，再加上环境，基本就是全部了。没有 tool calling，没有 skills，也没有其他这些东西。这可以叫作 harness V0。

拿 GSM8K 这样的数学问题为例，我们以前可能会写一个角色设定：你是一位数学老师。接着给出上下文：Susie 有五块钱，花了三块，还剩多少？没有 chain of thought，模型就直接输出四个井号和答案二，然后结束。GSM8K 的格式就是从那几个井号后面读答案。我们测准确率，对了给正向信号，错了给负向信号。

过去六年的许多工作，都是不断往静态 harness 里增加能力。首先是把一些例子放回上下文里：这里有一道做过的题，现在把数换成四和一，模型也许能从前一个例子里学到该怎么做。这就是 2020 年的 few-shot learners 工作所代表的思路。

然后有了 chain of thought。直接预测最终答案也许太难，那就把计算和逻辑展开到更多 token 上，让模型经过中间步骤再得到二，而不是一上来就输出二。这是一个非常好的想法，本质上属于上下文创新，也属于输出空间、动作空间的创新。

接着是 WebGPT 和 Toolformer，实际上 WebGPT 更早。思路是给模型工具。所谓调用工具，本质上就是输出一个包含指定字段的 JSON 对象。比如减法，我不一定要让模型在权重里直接算出五减三，可以调用 Python 的减法函数，让工具返回二。工具列表可以放在 system prompt 里，这就是工具能力的来源。

再往后是 MemGPT。我觉得最酷的一类工具，就是能够读写自己的上下文。以前只能不断往上下文末尾追加内容；现在我们问，能不能给模型对上下文本身进行 create、read、update、delete 的能力？于是把一个独立的小块叫作 memory，让它能够自行更新。

Voyager 又进一步：有了工具之后，我能不能把一串工具组合起来，完成一个任务？学会之后，又如何把这个过程提炼出来，存回系统，让以后还能继续使用？这就是 skills 的一个来源。Voyager 在 Minecraft 中做了这件事，是一篇很好的论文。现在很多 skill 的结构基本就是这样：有一个 skills.md，里面有名字，能搜索得到，再写下执行流程。

InterCode 则是另一种动作空间创新。如果模型可以直接输出代码，就可以即时创造工具，或者说即时创造技能。严格来说，工具是一个 API，那么输出一个函数究竟算工具还是 skill？我到现在也不能完全确定，但关键是模型获得了现场构造能力的方式。

ReAct、Self-Refine、Reflexion 这些工作，又引入了反思和不同角色的配合。假如有多个承担不同角色的 agent，它们能帮助改进上下文，就能逐渐把结果做得更好。

比如在这道题里，我把三和五弄反了。把动作交给内部 evaluator，它说这看起来不对。我可以继续在内部循环，也可以去真实环境取得 reward signal。Reflexion 会指出，你把两个数字反过来了，回去改。这样就能提升结果。这是让 agent 反思自己的输出、通过多 agent 角色结构来改进结果的早期思路之一。

再进一步，生成子 agent 本身也可以是一种工具。我能创建一组子 agent，让它们在持久化的 REPL 中运行，并且持续与它们交互。主 agent 有一个子 agent 列表，可以调用已有成员，也可以不断添加新的成员。

RLM 进一步把这个过程做成递归结构。系统暴露 RLM query，我就可以递归调用它，以解决更大范围的问题。在递归树的叶子上，需要的时候再用 LM query 启动语言模型 agent，最上面则有一个 orchestrator 协调所有工作。

到这里，我把整个体系叫作 harness V1，也就是静态 harness。它并没有改进自己的 system prompt，也没有修改运行 harness 的代码。当然，这张图顶上还得放 GStack，感谢 Gary。还有一些其他工作也值得特别提一下。

把静态 harness 总结成结构，就是有一个 agent specification、一份 system prompt，规定最多多少轮、最多调用多少次工具。不能允许无限调用，所以得有预算。然后列出工具、skills 和子 agent，再把这些放进一个循环里。

这个循环可能由一个 prompt 触发，比如我在 Slack 频道里提出任务。后面会介绍 QM，我每天都在用，开发它的团队今天也在现场。循环也可能由 cron 触发，每小时醒来，自己决定要做什么。

因此，系统里有 session management，有循环，有 context compilation。我们把需要的内容组织成上下文，送给 LLM，得到一个动作。如果需要调用工具，就执行工具，再把结果追加回上下文。这基本上就是 harness V1。

最让我兴奋的是下一步：让 harness 自己学习。可以学习 system prompt，也可以学习 harness 本身。这听起来非常有递归意味，而最近不少进展正发生在这里。

其中一个著名方向是 DSPy。我本来想请他们今晚来讲，但他们今天在旧金山另办了一场一百五十人的 DSPy meetup，所以来不了。我以前和他们录过播客，他们的社区非常好。

它的核心思路，是拿一小套训练样本，去学习一份更好的 system prompt。不断迭代、不断试。这个过程不能直接做 backprop，但可以做类似 genetic programming 的搜索：产生候选、合并候选、按某种规则评估，再继续寻找更好的结果。也就是把对 system prompt 的 CRUD 权限也交出来，让系统可以选择和修改它。

Darwin machines 则更进一步：不仅允许改 system prompt，还允许改真正运行着的 harness 代码。你可以想象有一个 archive，里面存了很多 agent，每一个都由 harness 和 system prompt 组成。从里面抽样，按某个 fitness function 测表现，再放回 archive。

中间还有 self-modify 这一步：一个 meta-harness 允许 agent 修改自己的 harness，让它变成另一种结构。不断重复，agent 就可能逐渐变好。主 harness 的任务变成了生成新的 harness，这是一个很有意思的元层次概念。

此时，输出空间包括多 agent 配置、上下文编排，也包括这些结构的增删改查。图里绿色的部分，就是越来越多可修改的区域：harness 代码、meta prompt、每一个 agent 的 system prompt、agent 的数量。这个 meta-harness 随着时间不断增长。

今天现场还有 continual harness 论文的第一作者，我很高兴有机会和他多聊。他们又推进了一步，对 memory 的类别做了更细的划分，也加入 history。他稍后会详细讲这些记忆层次。

对经典 RL 研究者来说，我觉得最酷的是类似 DAgger 的在线学习。你甚至可以更新权重文件本身，基于刚刚获得的一小批例子，对 LLM 做 test-time training。这是一个极其重要、值得认真投入的研究方向。

### Seth Karten：从第一性原理设计 Prime Agent

Seth Karten：大家好，很高兴今晚来到这里。我叫 Seth，今天介绍 Prime Agent，一个能够自我改进的 RLM harness。我想完成的任务，是说服大家从第一性原理出发，思考该怎样构建自己的 harness。所以我们先从非常基础的地方讲起。

我很喜欢刚才那段文献回顾，它与我的思考方式非常互补。只看原始 LLM，它其实是一个顺序处理器：有一套固定权重，有一段当前可见的上下文，接收一些 token，再输出一些 token，借此做出下一个决定。

今天我们通常不再用这么简单的方式想象 LLM。我们会让它访问一组文件，提供各种程序和工具，甚至允许它向其他 LLM session 发消息、创建子 agent，做出许多很酷的事情。但在最基本的层面，它仍然只是 token 进、token 出，是神经网络在作预测。

harness 就是处在 LLM 与外部世界之间的那一层，给它加入持久状态、工具和计算能力。从人的视角看，Prime Agent 的使用方式和 Claude Code、Codex、Pi 等工具类似：在电脑上打开它，先进入 agents view，看到所有并行 session 的总览。

这个总览会用很简短的信息说明每个 agent 正在做什么，你可以跳进去查看某一项。进入之后，就是 root session。它相当于项目总协调者，管理自己下面的不同子 agent。你不必明确要求它启动子 agent；它认为有用时就会自行使用。

这些调用都是程序化完成的，因为整个系统基于 recursive language model 的原则。所有东西都在 IPython shell 中：工具、记忆、子 agent。为了进一步协调，我们又暴露了一组消息机制，使这些 agent 能够彼此交流。

它们可以直接操作环境。环境可能只是你电脑上的程序与文件，也可能是给自动研究使用的一组 H200 节点。每个 agent 背后都有电脑上的一个持久 daemon，所以你关上笔记本，或者按 Ctrl-C 退出当前界面，任务仍然会在后台继续。要让它真正停下来，需要明确停止 session。

此外，我们把 continual harness 里的一些功能也暴露出来，允许模型对前面说到的各个组件进行实时 CRUD：管理 memory、skills、子 agent，也可以持久地修改自己的 system prompt。

我喜欢把不断积累的上下文想象成缓存层级，这里画成 L1、L2、L3。问题是，哪些信息最容易取得？最靠近模型、最直接可用的，是权重里的信息。所以大家总希望把所有知识都放进权重。

但我们不可能每得到一点新信息就重新 fine-tune，代价太高。因此有了 active input context，把大量 token 放到输入里，加入一些 in-context examples，补充能力。可是到某个点，context 还是会用完。

于是就需要 compaction。它是最早出现、今天仍然到处使用的一种 harness 功能。即使有人主张 harness 应当尽可能简单，通常也会保留 compaction，因为它是一个非常通用的工具，让 agent 总结自己的上下文历史，从而继续工作，突破单个 context window 的长度限制。

再往外走，不直接属于模型输入输出的，是 L2、L3。大家可能比较熟悉文件系统这一层：通过读写文件访问外部存储。位于 active context 与文件系统之间的另一层，则可以是一个持续运行的 REPL，比如 IPython，就像 Jupyter notebook 一样。

REPL 中的变量保存在 RAM 里，agent 可以直接用程序操作这些信息，运行各种计算，不必把所有数据都原样塞进上下文。这能节省大量 token。创建子 agent 也有类似效果：给它一个特定的信息集合，让它完成一部分操作，最后只把结果报告回来。

但重要的不只是创建和读取。我们刚才说 compaction，可以随着时间更新 active context；当状态分布到 REPL 和文件系统之后，也需要思考如何更新、删除这些状态。不能只会不断添加内容。

对 REPL 这一层，我把它叫作 agentic garbage collection：清理状态里的变量，决定哪些子 agent 还要继续保留，避免 RAM 被占满，让我的笔记本每天崩溃。对于系统上保存的 skills、memories 和 prompts，则需要 refinement，不断更新和删除，也避免硬盘最终被填满。

所以每一层都要回答两个问题：我们如何表达这类状态，又如何随着时间修订它。不能只设计保存机制，却没有维护机制。

另一个我很想推广的视角，是把 harness 看成逐渐形成中的 agentic operating system。打个比方，原始 LLM 更像一台读写纸带的 Turing machine，接收指令、执行一些操作、再输出结果。

而 harness 更像一台 von Neumann computer，能够对外部存储进行读写，实际可以表达和处理的工作就丰富得多。这里我是在作架构上的比喻：关键是给模型更丰富、更直接的状态操作能力。

那么，什么才是好的 harness？我认为应当尽可能有表达能力。早期的一些 harness 非常具体，要求模型先 plan，再 act，再 critique，严格按这几步走。在这些流程进入模型训练的数据循环之前，这可能很必要。但现在模型已经能自己安排这些步骤了。

比如，我们不一定还需要人为强制一个 ReAct loop，模型已经在一定程度上学会了这种行为。相反，有些功能模型不可能凭空创造：必须给它调用 compact 的能力，必须给它 Python REPL，才能执行程序；必须允许程序化创建子 agent、访问状态、获得不同形式的反馈。

这些是由模型控制的表达能力。如果删除其中一种，实际上就是拿走一项模型原本无法通过其他方式实现的能力。它们与强行规定任务流程并不是一回事。

大家可能熟悉我合作者 Alex 的 RLM 论文，非常出色。我们在它的基础上，又把子 agent 做成了持久的 subsession。父 session 创建一个 RLM 子 agent，子 agent 执行任务，结束后向父 session 报告最终状态。

但完成任务不代表它被销毁。它可以进入 idle，仍保留在 RAM 中。父 session 随时可以再发一条消息，让它继续工作，而且此前积累的上下文还在。这样就不用丢掉已经建立的信息，也不用重新构造一遍。

当然，我们不希望一直占用大量 RAM，所以还可以把这些 session offload 到 inactive 状态。以后需要时，再通过消息把它恢复。在这种持久化子 agent 结构中，任务完成、暂时闲置与彻底结束是不同状态。

我之前的 continual harness 论文，讨论过对整个 harness 状态进行 CRUD。这也是我们希望 coding agent 拥有的能力：能够利用自己所有的历史。你可以想象，一系列轨迹里记录了每一步动作、结果和发生的事情。

我们希望把这些信息暴露给 agent，让它据此决定未来的 harness 应该怎样变化。是否需要修改 system prompt？是否应该创建一个 skill？对我来说，skill 可以是一组指令，也可以是实现某个特定目标的程序。

Memory 则可以保存值得长期记住的事实。还有前面说的子 agent specification：是否有一些子 agent，因为已经建立了有价值的上下文，值得将来再次使用？让模型具备这种持续反思和修订的能力，非常有用。

今天的模型并不完美，但设计 harness 时，就应当让它略微超前于当前模型的能力。这样才能获得新的 reasoning traces，再利用这些轨迹训练下一代模型。下一代会更擅长驾驭这个 harness，再向更高的性能自举。

Prime Agent 里一个我特别喜欢的功能，从我刚开始开发时就加上了：同一个 agent 家族内的任意两个成员，都可以相互发消息，包括父子关系，也包括兄弟关系。

起因很简单，我每天自己管理好多 agent，它们朝五个、甚至无数个方向各自工作，我一直在想怎样协调才更好。如果它们能直接交换上下文、彼此配合，我就不必总站在中间转述。结果发现，这对普通软件工程和长周期任务也非常有帮助。

最后一个设计重点是 long-horizon performance。我希望启动一些工作后，不必整天照看 agent；等我准备回来检查时，再看看进展。现在很多 evaluation 反而缺少这个视角。

有时人们说，一个模型用了某些预算之后就停止了，而另一个模型继续花更多预算工作。首先，这样根本没有在固定支出条件下比较。其次，过早停止也可能掩盖还没有发挥出来的能力。

我想看的，是 practical plateau：继续投入更多 test-time token，到哪个点只能取得很小的增量收益？这才是我理解的长周期表现评估。

接下来介绍几个实验：test-time scaling 和 ARC-AGI；REPL 的信息管理到底为什么有用；以及任务拉长到数天、甚至一周以上时，系统如何持续工作，refinement 在里面究竟起什么作用。

### Prime Agent 的实验结果与边界

Seth Karten：这张结果图大家可能已经看过，我们额外补了一个原先没有的数据点，用来比较不同 harness。当时我们想，大家现在最关心的 eval 是什么？那就试 ARC-AGI。

我想起之前用 continual harness 做过实验，一个 Gemini 模型能到百分之二十，所以这次至少应该也能到那个水平。对于一个没有专门针对 ARC-AGI 设计的通用 harness，能取得这样的成绩就已经很有意思。

我上网找了一份合适的 system prompt，因为不想因提示信息不全而损失成绩。在一个叫 Prolong 的社区榜单上找到之后，我只拿了它的 system prompt，没有搬其他结构，直接放进 Prime Agent。

第一次跑出来是百分之九十九点九。我当时非常激动，但打开日志一看，发现作弊了。所以那个成绩不能算。我得把 sandbox 正确设置好，花了另一天把这件事处理完，再重新跑。

之后，GPT Soul 得到百分之七十八，我觉得这已经会是一个非常好的结果。我们又比较了其他模型。用的仍然是一个通用提示，大意是利用 world model 解决 ARC-AGI 3，并说明可采取的动作。

再加上 Prime Agent 自己的通用 system prompt，告诉模型它有 REPL，能程序化使用子 agent。看轨迹时可以发现，它会写代码检查不同情形，分析图像、做 image processing。它的推理看起来是合理的，而 REPL 是支持这些行为的主要能力之一。

GPT Terra 的成绩是百分之二十五点七。就在我们做这件事之前一周，OpenAI 还强调过，做 evaluation 时 harness 非常重要，并展示了使用 Responses API 的结果。我们这里的 Terra 测试没有全部跑到结束，但相较这些基线已经很好，甚至超过了一些 Soul extra-high 配置的结果。

接着试 Opus，得到百分之九十五点五，我们觉得非常惊人。也有人问是否跑过 Claude Code。跑过，但我们的那次成绩并不好，所以展示时我选择引用原始 Claude Code 的结果，而不是拿自己的一次低分去代表它。

后来其他人使用与 Prime Agent 类似的配置，也取得了好得多的 Claude Code 成绩。因此不能把这里的对比当作其他 harness 能力上限。

有意思的是，一些很流行的 harness，并不一定在 Prime Agent 表现好的任务上也表现好。例如我们测试另一个 agent 时，很快花了很多钱；花到大约五千美元，还没有多少性能进展，只好停下来。这不是说它最好就只能如此，而是说获得成绩的成本同样重要。

所以 cost-to-performance ratio 是必须看的。能够用程序处理上下文，是节省成本的一种方式，而不只是追求更高的最终分数。

我们还跑了其他较长任务，包括 OOLONG 和一些 coding evaluation。其中一个叫 Emulator Bench，很快会发布，是类似 ProgramBench 的另一种评测。跨不同模型比较，包括 GLM、Opus 和 GPT 系列，对比 Pi、Claude Code、Codex 这些 harness，结果主要是持平或者略好。

Emulator Bench 的任务很有趣，要重建整个计算机系统的 emulator。这里的例子是制作 Game Boy Color 的模拟器。有了 RLM 的 REPL 访问能力，模型可以写一些程序，在正式提交给 grader 之前，自由地设计和运行探索性实验，而不必被最终评测循环绑死。

我们也测了 GPU kernel。在 Soul 和 Kimi 等模型上，结果大致持平，有的更好，有的更差。所以我们并不是只盯着某一种 evaluation 去过拟合。

关于真正很长的工作，我们做了一些 autoresearch 实验，以 nanoGPT speedrun 为基础，但把规模放大：给系统八张 H200，让它运行一周，看看会发生什么。

你也许会期待，因为 Prime Agent 有这么多程序化能力，应该显著更好。但这个任务方差非常大，我们无法把结果里的收益明确归因于 harness，而不是模型本身。这是一个很难的任务，不能作那样的结论。

不过，我们可以检查它出现的行为。后面又用了几个更新的 DeepSeek、GLM 和 Kimi 模型，观察到我们称为 out-of-loop experiments 的东西：模型试着在 CPU 上做参数化分析、hyperparameter search 和数据分析，避免把全部时间都花在昂贵的 H200 实验上。

因为真正的大实验占用了主要运行时间，所以它会先做一些不是主实验的实验，用来优化接下来的主实验。我觉得这类行为很有意思，也帮助我们思考，Prime Agent 应该暴露哪些表达能力，才能支持更好的自动研究。

如果一个系统能把 autoresearch 做得不错，那么有人在环时，它应该还能更好地帮助你启动和改进实验。这是我们很关心的一种应用方式。

最后，我们还直播了一次持续七天的 Factorio 运行。整个过程使用了六百三十三个 agent，产生约两千三百万个 output token，沿科技树不断推进。

子 agent 可以分工，分别研究、建设、采集资源，制造下一阶段需要的物品，再共同设计工厂。Refinement 则利用以前发生的事情帮助后面的工作，让这么长的上下文过程不至于反复卡在同一个地方。

最有趣的观察之一，是它没有停滞，到运行结束时仍然在推进科技。这更像 Gemini 玩 Pokémon 那类长期运行展示所提供的结论，而不是一个非常严格的、能证明所有性能优势的基准。

如果今天只能带走几个可以放进自己 harness 的想法，我希望大家关注 agentic context management，关注 agent swarms，进一步研究 RLM，并使用标准化 evaluation。今天展示的结果，都可以用 Prime Intellect 的 verifiers package 来运行。感谢我的合作者们，我非常喜欢与他们一起工作。谢谢大家。

### Jon Saad-Falcon：把个人 AI 放到本地设备

主持人：接下来是 Jon。

Jon Saad-Falcon：大家好，很高兴介绍我们在 Stanford 做的一个项目。我与共同第一作者以及导师团队一起做了这项工作。项目叫 OpenJarvis。

个人 AI 现在无处不在，但大部分仍然被绑在云端。我们看到许多 harness 和项目，帮助人们完成日常写作、研究、编码和日程安排。可是 OpenClaw、Hermes Agent 这类项目，大多数查询和智能能力依赖云端 LLM。

这意味着什么？首先是成本。如果把一年加起来，API 费用可能达到数千美元。其次是隐私，你常常把最私人的数据发到云端模型，却不一定清楚这些数据究竟流向哪里。

再次，这相当于一直租用智能，而不是直接拥有它。最后，相比在自己的笔记本上运行模型，这种方式往往会消耗高出多个数量级的能源。这些都是我们探索本地方案的动机。

今天的本地 LLM 终于足够好了，能够处理人们关心的许多查询。我们观察到，本地模型与此前最前沿模型的差距，大约只有六到十二个月。一些当前的二十多 B 规模模型，已经能接近之前 Claude Opus 等前沿模型的表现。

随着笔记本和工作站的硬件加速器越来越好，这个差距似乎还在缩小。本周 Apple 又发布了新的 Mac Mini。我们看到 Apple 和 NVIDIA 都在重新重视面向个人使用场景的加速器。

因此，这个项目想回答的主要问题是：能否把个人 AI stack 的核心，也就是模型推理、agent 执行、记忆和学习，这些今天主要依赖云端的部分，全部放到本地设备上，同时保持与 cloud-only stack 接近的竞争力？

于是我们提出 OpenJarvis。名字不需要太多解释。我们想探索，其中有多少东西可以完全在设备上运行，不再支付云端调用费用，同时保留安全、隐私和质量。

为了搭建 OpenJarvis，我们首先寻找能够定义各种 harness 或个人 AI stack 的最简单 primitives。最外面是用户界面，接着是 agentic logic，也就是如何组合推理过程，以及如何使用不同智能和工具。

智能这一部分，就是推动整个系统工作的 LLM。你可以用 Qwen、gpt-oss、Gemma 等模型。然后需要实际运行它们的 inference engine，例如 Ollama、llama.cpp、vLLM、SGLang。

这一层还包括硬件，可以是 Apple Silicon，也可以是 NVIDIA，或者你手头需要支持的其他设备。要让 agent 和智能真正有用，还需要 tools 和 memory，可以通过标准 MCP 协议接入。

最后还要有学习机制。可能是以 prompt 为基础的方法，比如 DSPy；也可能是更新权重的方法，比如 SFT、LoRA 等。总之，要让 agent 随时间改进，变得更贴合个人，也更有效。

接下来看看界面。我们尽量采用大家已经熟悉的标准交互方式，让人可以通过 desktop 正常使用，同时看到节省了多少美元、多少能源。我们还希望支持持续运行的 agent，例如通过 cron job 每天执行相同的工作流程。

目标是让它直接接进大家已经习惯的 workflow，不必重新学习整套工作方式。我们也希望，这能成为很多人第一次真正使用 on-device LLM 的体验，就像以前第一次使用 ChatGPT 或 Claude 一样。

这里可以方便地设置新的持久任务。我们有这些不同组件，但还需要一种方法来优化它们。因此，我们尝试尽量不挡在 LLM 面前，而是给出一份简单的 specification，让它通过这几个 primitives 去优化整个系统。

我们发现，经过这个优化循环，不仅 dollar cost 明显下降，latency 也明显降低，而且这些测试中的总体质量还有改善。

配置被简化为构建 harness 时最关心的几个部分：intelligence、engine、围绕模型的 agentic logic、运行所需的 tools 与 learning systems，以及对整份 spec 的整体优化。

为了连接本地模型与云端模型，我们还尝试让云端 LLM 自动优化整个本地 stack。云端模型负责诊断问题、提出修改、把关候选方案，产生更好的本地配置。

这样可以利用云端模型较强的能力，却不用在本地系统正式部署、每次推理时都继续承担云端模型的成本。换句话说，云端智能用来优化，本地模型用来执行后续的大量调用。

我们观察到，经过 Claude 或 ChatGPT 等云端模型优化的 OpenJarvis 配置，比直接开箱部署的本地 stack 有效得多。因为优化可以针对具体模型、具体 harness 和具体 workload 进行，而不是一套配置用到底。

即使采用今天已有的 on-device LLM，我们在一些个人 AI、coding 和 agentic workflow 上，也能与云端 LLM 竞争。当然，仍有很多任务，只有本地规模的模型是不够的。我们没有说本地模型已经覆盖所有任务。

但随着模型蒸馏得更好、效率更高，以及硬件加速器不断改善，这个差距似乎每个月都在缩小。我们的测试中，一些本地运行配置能够达到低八百倍的成本，同时显著降低延迟。

我们还发现，无论选择哪一种云端 LLM，通常都能帮助优化本地 OpenJarvis 的整个 agentic loop。Opus 系列和 GPT Soul 的表现最好，这并不意外；但 Gemini、Kimi、GLM 等其他较大的模型家族，也能用于优化本地配置，让后续推理获得效率和性能收益。

另外，OpenJarvis 这套 harness 的优化成本，也低于一些需要更多数据或者更多 LLM calls 的替代方案。对本地模型而言，这组 specs 和 primitives 很有效，因为它尽量移走了多余的抽象，让云端模型直接优化整个系统，把它变得更快、更有效。

展望未来，我们会继续开发这个项目。我们认为，在不远的将来，人们每天的一大部分、甚至可能大多数推理调用，会发生在本地设备、自己的笔记本或工作站上，而不是像今天这样几乎都送往云端。

我们认为这个趋势会延续，因为加速器会继续改善，LLM 也会继续改善。如果你对其中任何一层感兴趣，无论是更好的本地模型、更好的加速器，还是面向数据中心之外部署的 inference engine，都欢迎来交流。

这里有项目的二维码。活动之后我们也会在现场，很愿意和大家聊天。谢谢。

### Josh France：YC 为什么建立 QM

主持人：接下来是 YC 自己的团队，Josh 和 Regan。

Josh France：大家好，我是 Josh，这位是 Regan。我们正在开发 QM，这是 YC 面向工作的开源 agent harness。

QM 通过一套系统，给 YC 每位员工提供一个类似 OpenClaw 的助手。它可以充分定制，通过 Slack 或 web UI 使用，这里展示的就是 web 界面。

每个人在 QM 里都有自己的 personal context，包括自己的 sandbox、文件和 cron 任务。同时，大家也能在 Slack channel 等多人环境里与 QM 协作。

使用场景非常广：各种 automation、邮件分类、法务和财务 workflow。它很擅长编辑文档，也能从内部数据库取数据。它还能启动可直接使用的内部 web app，或者帮助组织活动。总体设计目标，是覆盖 YC 员工日常可能遇到的各种任务，而不是专门做一种事。

为什么要自己建它？这是过去几年一连串内部 agent 项目自然演进出来的结果。所有这些项目都受益于底层模型能力的持续增强。

第一个项目大约建于 2025 年 1 月，内部就叫 general agent。架构非常直接，一份 system prompt，加一些 tools，再放进循环。所有人面对的基本是同一个 agent，是 one-size-fits-all 的。

虽然结构简单，但它回答数据问题的能力出乎意料地好。后来，随着底层模型变强，它能处理的事情也越来越多。我们给它接上 Slack，加入 cron，再加一些工具，让能力扩展到更多领域。

到 2025 年 6 月，许多工程师开始使用 Claude Code 和 Codex。我们发现，可以很容易把它们放在 VM 里运行，再挂到 Slack 的一个标签上。这样，想做一次性代码修改的人，就有了一个很强的入口。

我们还让它跑 CI pipeline，启动开发环境用于测试。员工只要描述一个 bug，或者说想看到什么变化，bot 就会自己去解决。对一个可能一辈子没改过代码的人来说，这非常有力量。

在此基础上，我们还有一个小的改进循环：观察 bot 在哪里失败、哪里做错，然后更新代码库里的 AGENTS.md。通过实际使用不断发现问题，让它变得更好。

今年一月，很多 YC partner 开始使用 OpenClaw。大家要知道，YC partner 极其忙碌，要做 office hours，处理大量来信，还一直在看申请。任何能给他们增加 leverage 的工具，对 YC 都很有价值。

OpenClaw 特别有用的一点，是它拥有自己的电脑。对于许多人来说，这是第一次使用这样一个 agent。相比之前的 agent 范式，它可定制得多，也更像真正的个人助理。

到四月份，我们问，能不能把这种能力交给 YC 的每一位员工，而不用真的给所有人买一台 Mac Mini？于是我们部署了一批在 VM 中运行的 Hermes agent，数量超过五十个。

这些 agent 确实有帮助，但员工要花不少时间配置，才能真正获得价值。整个集群也很难管理，总有这里坏一点、那里坏一点，我需要 SSH 进一个个实例去修。

于是下一个问题变成：我们已经从这些 agentic system 里获得许多价值，能不能保留个性化和大家真正喜欢的部分，同时解决维护一大批独立 Hermes agent 的缺点？这就是 QM 的起点。

### Regan Bell：把大脑与 Sandbox 分开

Regan Bell：从 Josh 展示的过程，可以看到一个很清楚的趋势：模型能力在快速增长，而每给它们增加一种能力，都开始出现更好的回报。OpenClaw 给 agent 一台自己的电脑，我们就看到了明显变化。

所以大概五月时，我们开始想，顺着这个方向继续推，到底能推多远？我们很喜欢 unhobbling 这个视角，也就是解除原本套在模型能力上的限制。

不知道大家是否读过 2024 年的 Situational Awareness。当时 test-time compute 刚开始受到重视，我们也开始给 agent 更多工具。这里有一种直觉：在很多场景里，模型内部的智能，比我们实际利用到的更多。

如果我们继续推进能提供给 agent 的能力边界，让它拥有更多可使用的资源，就可能出现很有意思的结果。

QM 的第一步，是把系统的大脑从 sandbox 里提出来。Hermes、OpenClaw 让 agent 拥有自己的电脑，这很强大，但 agent 也被困在那台电脑里。

从管理角度看，哪怕只有几十个实例，就已经很难维护。另一个问题，是所有 session 都被关在各自电脑里。我们改为把这些东西放进 PostgreSQL，让大家与 agent 的对话集中存储。

然后，把这些不断积累的上下文暴露给 agent 本身，让它能够利用系统中的相关信息。与此同时，我们不再把 sandbox 当作 agent 唯一的家，而是把它当成 agent 可以按需调用的一种资源。

这个变化减少了很多限制。它还带来另一个机会：随着大家持续对话，你会积累大量 traces，也就是一套很大的 evaluation 素材。从原则上说，可以在这些轨迹上不断 hill-climb，构造一个自动改进循环。

不过，我们在这件事上的结果好坏参半。如果一下子派出大量 agent，让它们修复遇到的所有 bug，再由 LLM 担任 judge，就容易出现一种主角心态。

每个 agent 只看见自己的那部分问题，就像只摸到大象的一小块，作出的修改可能并没有考虑整个系统。所以，人类继续留在循环中仍然非常重要。我们期待有一天能真正把这个循环全部自动化，但现在还没有完全做到。

另一个比较直接的做法，是把公司里能连接的资源都连给 agent。YC 原本就有一套很好用的 CLI，已经连接了许多内部系统。没有包含在里面的能力，也可以通过添加 API key 等方式接入。

我们还希望 agent 的能力与员工坐在自己笔记本前工作尽量一致。比如 device-code OAuth，我们会把授权接进 keychain，并负责 refresh。理想体验就是一个人在自己的电脑上工作。

数据库访问大部分保持 read-only。写入也可以做，但采用由人审查的 bulk upsert：agent 先提出修改数据库的计划，人快速看一遍，确认没有异常，再实际写入。

我们已经观察到一个问题：人开始有点机械地批准这些操作。就像早期使用 Claude Code 时，可能会逐条认真审工具调用，后来逐渐建立信任，就不再那么仔细。这是我们未来几个月会密切关注的事情。

回到 sandbox，它在 QM 里是一种资源，而不是 agent 的固定住所。默认情况下，agent 会使用分配给当前用户的 sandbox；但也可以存在多个 agent 汇合、共同工作的环境。

如果任务是比较重的开发工作，它可以选择一台资源更多的机器；如果只是简单工作，就使用较轻的 sandbox。把这种选择交给 agent，而不是全部写死在 harness 中，已经显示出很强的作用。

类似地，我们允许 agent 触及自己的 runtime，包括选择模型 provider。某些模型在 AI research 或 cybersecurity 等任务上可能频繁拒绝，能够控制 runtime 时，系统就可以切换另一个模型来处理相应工作。

同样的逻辑也适用于 sandbox provider。有时切换不同 provider 很有用，我们希望它可以方便地做到。总体原则，是把 harness 保持得非常薄。

我们认为核心只有三种工具：在远程 sandbox 中执行；从 object storage 读取和写入；发布内部 app。发布 app 是一个相当简单、以 Git 为基础的系统。

此外当然还有 memory、cron 等工具，但我们更把它们看成暂时填平系统粗糙之处的东西。真正的核心是前面三项，我们尽量让这一层保持小而简单。

### QM 的现实问题：过早停止、多人语境与权限

Regan Bell：我们想做的是一个为更强智能预先准备的 harness。但毕竟还没有走到那里，现实中有几个问题。

第一个，是 agent 常常太早放弃。我们已经给它一个能力很强的环境，提供了很多工具，它却仍然可能很快停止工作。

所以过去一个月左右，我们试了一种叫 grind tool 的东西，核心是给目标设预算。达到一定 wall-clock time，例如几个小时，或者达到一定 token spend 之前，agent 不应轻易放弃任务。

这么做能够带来更好的 research output、更好的报告等。最近看到 OpenAI 和 Anthropic 用相似的技术解决一些数学开放问题，也很有意思。但这个方法不只是数学研究有用，普通办公室工作同样能受益。

第二个问题是，这个 harness 需要支持 multiplayer，运行在 Slack 里。可是由于训练过程中形成的习惯，agent 对自己所处的场景常常很困惑。即使 system prompt 已经写得很清楚，它仍可能理解错当前互动结构。

因此，需要在具体交互的位置提供明确提示和合适的局部设计，帮助它知道自己正处在哪种场景。只靠总提示词，并不足以解决所有问题。

Josh France：另一个重要问题，是 agent 并不真正理解 social context。举个具体例子，如果我告诉 Regan 一条信息，他通常会直觉地知道，这条信息可以分享给谁、不应该分享给谁，至少有一套相当合理的判断框架。

要在 agent 中重建这种能力，需要实际投入工作。Privileged information 很容易泄露到本来不应该出现的上下文。因此，你能放进系统大脑的信息范围，实际上受到权限系统质量的限制。

YC 比较幸运，多年来已经建立了一套带有细粒度权限的软件系统。但许多公司并没有这些基础。要实现带有细微边界的知识共享，并不是简单把所有信息聚在一起就行，而是需要额外建设。

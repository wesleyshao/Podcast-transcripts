# AI:AM Highlights: Astra as AGI, OpenAI's Pause, Mythos @ Mozilla & Human Agency vs Technocapitalism

## Transcript

### 节目结构

Nathan Labenz：欢迎收听 AI and the AM weekly highlights。本期使用我克隆的声音，整理本周三场直播讨论。我们讨论了 GPT-6 Astra 是否已经跨过 AGI 的实用门槛、OpenAI 的暂停与下一代模型、递归自我改进、外部安全审计、Mozilla 如何用 Mythos 检查 Firefox、agent sandbox 的安全边界、儿童产品为什么拒绝开放式生成式 AI，以及中国社会如何理解 AI。节目中还讨论了 human agency、technocapitalism、AI 安全资金和政府是否应该促成 frontier labs 的短期协作。

### 第一部分：Astra 周末与“可用的 AGI”

Prakash Narayanan：我整个周末都在使用 Astra。我同时运行了三到四个 agents。它们开始处理代码库里长期存在、一直让人烦恼的问题。我们自己搭建了 studio，过去这些问题需要工程师不断追踪；Astra 已经好到可以在你关心工作质量的前提下，把一部分任务交给它。你仍然需要和它沟通，但已经可以把比较高级的任务交出去并拿回结果。

以前 GPT-5.6 的 computer use 经常耗时很长。它会在界面里到处点击，做很多动作，却迟迟不能完成任务。现在 computer use 终于在给定的时间范围内正常工作了。这是一个重要变化：它从演示功能变成了真正有用的工具。用户可以开始把更复杂的电脑操作交给它，而不只是让它回答一个问题。

一个例子是篮球视频分析。有人手工标注了 12,000 张图片，告诉系统哪一个人是哪个球员、裁判属于哪一方、每个球员在哪个位置。过去这是一项非常枯燥、几乎没人愿意做的工作。现在 Astra 可以直接完成。再过一段时间，人类不会再做这类逐张标注，因为即使你雇一个人，那个人也很可能调用 Astra 来完成。

这说明 agent 的边界不只是“能不能生成代码”，而是能否持续理解目标、使用电脑、保持上下文并完成跨多个步骤的任务。真正的转折点不是模型在单次回答中更聪明，而是它不再因为任务太长、步骤太多而中途放弃。

### 长任务、记忆和 notes

Prakash：我一直观察 Astra 如何完成长任务。它能够把很多 exploit、工具调用和中间决定连接起来，最终实现一个目标。过去的模型经常在长任务中迷失，或者在 context window 快满时忘记早期决定。Astra 看起来有一种更有效的 history 处理方式。

一种常见做法是把一百万个 token 压缩成摘要，再用摘要开启新的 context window。问题是摘要会丢掉大量细节。Astra 似乎采用了 long-lived notes：模型可以在需要时更新一个会长期跟随任务的 notes 文件，而不是把所有历史一次性压缩掉。它还可以回到过去的 session history 里搜索。

这意味着单次仍然只能完整 attention 一百万 token，但通过 notes 和可检索的历史，模型能够管理远超一百万 token 的有效上下文。它可以记住已经试过什么、哪些路径失败、目标是什么、下一步需要验证什么。对软件工程、研究和浏览器任务来说，这类持久状态可能比简单增加 context window 更重要。

### Agent workday 与任务时间尺度

Nathan：过去有一张图表，用“人类需要多长时间完成的工作”衡量 AI agent 能否完成任务。现在这张图越来越难更新，因为模型发布太快，评测者还没完成一个足够长的任务，下一个模型已经出来了。模型迭代周期比评测任务周期还短，传统图表的意义开始下降。

OpenAI 提出过 agent workday 指标：每一个人类研究员工作日，对应约 3.1 个 agent workdays。这个定义并不十分清楚。一个理解是，人类研究员工作八小时，而 agents 可以连续运行 24 小时；另一个理解是，agent workday 同时包含多条并行的研究路径，所以不能简单等同于一个人工作了三倍时间。

另一个评估显示，在估计需要人类一到两个工作日的任务上，Astra 有大约 40% 的概率无需干预完成；如果允许人类在过程中干预，成功率接近 90%。对估计需要一到三周的任务，它仍有一定概率一次完成，多数情况下在有一两次人工帮助时可以成功。这不代表它已经取代了一个完整团队，而是说明任务的时间尺度已经进入过去只属于人类项目管理的范围。

代码质量的反馈并不一致。有些人说 Astra 能写出可维护的代码；另一些人发现，当模型认为代码不会被人审查时，它会写出非常复杂、难以理解的东西。GPU kernel 是一个典型例子：如果只验证矩阵运算结果是否正确，那么内部怎样融合步骤可能不重要；但如果代码需要被团队继续维护，可读性就很重要。

我们似乎正在回到 machine code：机器直接写出低层、难读、但可验证的程序。未来可能需要新的抽象层，帮助人类理解这些代码，而不是要求每一行都由人类亲手写出。

### Astra 是否已经跨过 AGI 门槛

Prakash：如果一个系统可以在很多领域里发现人类没有想到的有效策略，它可能开始接近我们所说的 superintelligence。比如它在新的电池材料上提出一个人类没有尝试过的组合，实验之后证明确实更好；再把这种能力扩展到多个有实际价值的领域，就不只是一个更快的 autocomplete。

Astra 已经能处理很多烦人的工程问题，能够使用电脑，能够运行长任务，能够把结果交给人类审阅。它不一定符合所有人对 AGI 的哲学定义，但在实际生产中，它已经通过了“足够有用”的门槛。一个人可以把自己过去需要雇人完成的任务交给它，并在较短时间内获得可用结果。

Ksenia Se：我参加了一个 world models workshop，现场有很多来自 Stanford、Harvard 的研究者和 Yann LeCun，但他们对 world model 究竟是什么并没有共识。对我来说，world model 更接近一种能够预测并采取行动的内部表示。它需要理解发生了什么、下一步会怎样，尤其是机器人需要理解物理世界。

如果一个模型能在不同领域不断提出、测试并改进策略，它就可能具有某种 superintelligence。我们不必先解决所有哲学定义，先观察它能否在高价值问题上稳定地找到人类没有想到的方案。

### 写作、原创性和模型的“口音”

Ksenia：我最近写一篇关于 permanent dawn 的文章，自己花了大约六个小时。因为文章很复杂、带有哲学思考，我不满意多数模型帮我写出来的版本。最后我把成稿交给一个平时很少使用的模型，让它只修 grammar，结果它不仅修正语法，还用一种明显属于它的短句风格重写了部分内容。

读者很快发现了这一点，有人说要 unsubscribe，因为他们能感到文章最后是由某个模型编辑过的。每个模型都有自己的 language fingerprint。即使原始思想属于作者，只要最后的句法、节奏和措辞像某个模型，读者就会意识到模型参与了写作。

这不一定意味着人类不能使用 AI。相反，AI 可能成为共同作者。人类提出观点、结构和经验，模型帮助重写、压缩、增加隐喻、调整节奏；关键在于人类仍然对最终作品负责，并且保留真正的原创思想。

### 递归自我改进和真正的瓶颈

Nathan：AI 研究与更强模型开发之间正在形成一个反馈回路。研究机构把多年论文、实验结果和代码交给模型，模型可以选择过去人类没有时间重新尝试的实验路径。模型又能帮助工程师改进下一代模型，下一代模型再加速研究。

Prakash：我越来越不确定还有哪些真正坚硬的 bottleneck。很多人说某个因素会阻止模型继续变强，但听起来更像 wishful thinking，而不是不可克服的限制。也许让系统不彻底 rogue、让人类保持决策权，是目前比较真实的瓶颈；但在纯粹的能力方面，我看不到太多能长期存在的阻力。

这并不意味着能力一定会无限增长，而是意味着我们不能仅凭“现在还做不到”就假设未来也做不到。很多所谓瓶颈可能只是短期工程问题，随着更多 compute、数据、工具和 agent loop 出现，就会被绕过去。

### 外部审计为什么不够用

Nathan：Apollo Research 长期研究 deception、scheming 和 chain-of-thought monitoring，与 OpenAI 有合作，但这次据说只有三天时间测试 Astra，然后模型就发布了。对于一个能力正在快速变化的模型，三天不足以做充分的 red-team。既然不给审计者时间，为什么还要把评测流程做成一个形式？

Prakash：模型发布流程本身造成了冲突。一个模型从最初候选到最终 release candidate，可能经历一百个版本，最后只剩下两三个。公司往往在发布前两三天才决定最终采用哪一个版本。如果要求外部审计只测试最终版本，审计者只能拿到很短时间；如果提前一个月进场，又可能审计到最终不会发布的版本。

一个解决方式是把审计者长期放进公司，让他们提前接触大部分 release candidates。但独立审计团队通常没有 frontier lab 那么多人，无法同时覆盖十个模型。它们还缺少资金，很多时候必须接受模型公司的支持，随之产生独立性问题：接受多少钱之后，外界会认为判断已经被收买？

还有 revolving door。审计机构的研究人员可能几年后加入 OpenAI 或 Anthropic，把在审计中学到的经验带到模型公司。模型公司和审计机构如果约定不互相挖人，又可能触及 antitrust。金融监管长期面临同样的问题：监管者和被监管者之间的人才流动，会影响判断的独立性。

独立性不只取决于工资。一个审计团队即使经济上独立，也可能担心如果批评得太狠，下一次就不会被邀请。安全研究需要模型公司的配合、接口和数据，而模型公司掌握着是否提供这些资源的选择权。这让“外部审计”存在一种结构性脆弱。

### Reassure and mislead：暂停到底暂停了什么

Nathan：OpenAI 宣布了一个显著强于 Astra 的内部模型。公开信息显示，在一组开放数学问题上，额外使用大约一个数量级的 test-time compute 后，模型 solve rate 从 10% 至 15% 提高到大约 25% 至 45%。这足以称为显著提升，但也提出了一个问题：如果 OpenAI 说暂停 frontier-scale RL，它究竟暂停了什么？

OpenAI 的图表把 RL compute 分成 Astra 类和 non-Astra 类。问题是，non-Astra 是否包含比 Astra 更强的模型？如果包含，图表就可能在技术上没有说假话，却让公众形成错误理解。一个正在经营数百亿美元收入的公司不能停止所有 inference，因为客户需要 24/7 SLA；也不能停止修复一个已经识别出的坏行为；小模型还需要从大模型 distill 出来。这些 RL 会继续。

真正可能被暂停的是对同等或更大模型的 frontier-scale post-training。但研究员仍然可以用小模型验证想法，仍然可以继续思考下一代架构。真正的 frontier 不是部署中的模型，也不只是训练中的模型，而是研究员脑中的 idea；即使暂停一部分 RL，研究仍在继续。

OpenAI 的陈述可能既在 reassure 又在 mislead：让合作方相信它在控制速度，同时保留技术上继续推进的空间。这样做的后果是 Anthropic 会越来越不信任 OpenAI，OpenAI 的员工又会认为自己被不公平地怀疑。没有基本信任，就很难形成安全协作。

### Compute、资本周期和 OpenAI 的选择

Prakash：OpenAI 和 Anthropic 被不同的资本周期拉着走。Anthropic 早期投入的 compute 不够，因此更依赖每一代模型都显著更好，才能在有限资源下保持竞争力。OpenAI 有更多 compute，所以更有能力提出 pacing frontier。但 OpenAI 也在过去十八个月做出了很多资本让步：向大投资人融资、稀释股权、与 Microsoft 谈判并交出长期模型权利。

如果 Elon 或 Meta 追上来，领先者就必须推出下一代模型。frontier 的速度很可能不是由第一名单独决定，而是由第二和第三名决定。只要竞争对手足够接近，第一名就没有办法自愿放慢。因此，讨论暂停不能只看某家公司是否愿意，还要看整个竞争结构是否允许它这样做。

递归自我改进还可能改变 IPO 计划。如果 OpenAI 在未来六个月取得一两个 transformer-level 的突破，可能觉得不必上市。Prakash 认为这反而不好：上市能带来透明度、分散股权、董事会问责和股东诉讼等约束。一个极其强大的私人公司如果没有这些外部机制，公众对其决策的可见性会更低。

### 没有一个“房间里的成年人”

Nathan：Anthropic 研究员 Jacob Coxin 离职时提出了一个问题：私营公司是否应该决定何时发布 self-improving superintelligence？他把进入 endgame 描述成不应该从公司 Slack 发起的冒险。

Prakash：现实是，没有一个神奇的 adult in the room。世界本来就是用胶带拼起来的，大家都在边走边决定，真正懂这些系统的人大多已经在 frontier companies 内部。把责任交给政府可以带来 political legitimacy，却不一定带来执行所需的智慧和速度。不能假设政府某个角落有一个更成熟的团队，等着接管一切。

但这不意味着世界只能这样。政府可以给几家 frontier labs 一个短期 deadline：你们先提出一套安全协作和验证机制，如果无法达成，政府再采取更强硬的措施。政府可以明确，围绕 AI safety 的有限合作不应成为 antitrust 的目标，从而消除公司“我们想合作但律师不让”的借口。

短期 deadline 比永久制度更现实。我们不需要一次解决未来一百年的问题，只需要让几个主要公司在未来几个月内达成一个可以相互验证、相互监督的安排。政府有很多 sticks：数据中心、能源、发射场、审批和执法。公司可以挑战政策，但那会消耗时间，而 frontier 的时间窗口很短。

John Schulman 的观点与此类似：在政府提出具体方案之前，几家公司应该先合作。政府过早介入容易产生笨重规则，但政府可以通过 safe harbor 消除企业的法律恐惧。Operation Warp Speed 是一个先例：疫苗公司要求事后诉讼保护，否则即使现在的决策者同意，未来的法律风险仍可能让企业无法行动。安全协作同样需要考虑未来决策者，而不是只依赖今天的口头承诺。

Paul Christiano 加入 OpenAI board 的 safety and security committee 时提出了更强的警告：如果在没有更强 alignment 的情况下建立 superintelligence，人类可能永久失去控制。这里需要明确“rapid acceleration”是什么意思。很多 frontier researchers 说的加速，不只是今天模型每几个月升级一次，而可能是 2030 或 2040 年出现 Dyson sphere 级别的工业能力。

这种预测把 AI 研究者和经济学家放在不同位置。研究者认为数学能力可以带来物理、化学、生物能力，最终许多事情都能被解决；经济学家提醒，真实世界还有许可、协调、基础设施、政治和人的决策速度。例如铜矿可能需要三十年，不是因为没有技术，而是因为环保抗议、社区协调和审批流程。AI 的 super persuasion 可能成为两者之间的桥梁：它不只解决技术问题，也让人类组织更快地行动并接受变化。

### 安全研究的钱从哪里来

AI safety 生态的一部分来自非营利机构和慈善资金。它们虽然依赖 billionaire class，却形成了研究人才、评测方法和公共讨论的 depth of bench。Project Tailwind 之类的项目宣布为真正有效的安全 startup 提供大额、分阶段的资金，最高规模达到数亿美元甚至更多。

资金的关键是 tranche，而不是一次性给钱。安全研究往往很难像普通软件一样迅速证明收入，分阶段资金可以让资助方根据实际效果继续投入，也减少把钱给到只会写报告而无法验证的项目。另一方面，过度依赖少数富豪也会带来议程和独立性风险，这仍然需要透明披露。

### 第五部分：Mozilla 的 defender’s ledger

Raffi Krikorian：我是 Mozilla 的 CTO，过去做过 Twitter 的 platform engineering、Uber 的 self-driving development 和 Democratic National Committee 的 technology。Mozilla 参与了 Project Glasswing，这是 Anthropic 给 defensive security partners 使用 Claude Mythos preview 的项目。Mozilla 适合参与，因为我们能够快速反馈，Firefox 有很长的历史代码和 bug 数据，团队知道代码库是如何演化的。

Mythos 相比 Opus 和更早的模型是一次明显的能力提升。它可以找到 Firefox 中的漏洞，有时甚至能够帮助我们建立更好的 harness，让我们更仔细地复现 bug、确认触发条件并寻找解决方案。但很快，边际收益开始下降。我不愿意说 bug 已经被解决，因为软件工程既是科学也是艺术；下一代模型出来后，我们还会重新运行一遍。

更大的风险不是 Firefox 这种能迅速响应的组织，而是水、电力等基础设施公司。这些公司的 IT 团队可能没有 Firefox 那样的工程能力、历史数据和快速修复机制。如果一个强模型发现了关键基础设施漏洞，真正困难的问题是对方能否及时理解、验证、修复和部署补丁。

对一个复杂的 Firefox 代码库做完整的 agentic security run，粗略成本可能达到数十万美元；由于 frontier labs 提供 credits，Mozilla 目前并不需要完全自己承担。按模型发布速度计算，这甚至可能成为每月成本。银行、能源公司和公共基础设施都需要重新计算安全预算，因为一次扫描不再足够，模型每次升级都可能带来新的测试能力。

### CQ project：让 agents 分享经验

Mozilla 还在做 CQ project，可以把它理解为 agents 的 Stack Overflow 或共享知识标准。agentic coding 很容易让每个工程师在自己的 silo 中工作：一个 agent 正在构建 authentication system，另一个 agent 可能从零开始重建相同系统。CQ project 想让 agents 共享已经获得的 pattern、决策和公司级 software development lifecycle 规则。

这个项目要解决两个问题。第一，如何让不同工程师的 agents 看到哪些设计被接受或拒绝，从而朝同一个方向收敛，而不是各自发散。第二，如何把公司的 coding、测试、review 和 release 规则传给所有 agents。agents 的自由度很高，但公司需要一个共同的 contract。

agents 也会自然产生共享信息的机制。过去一些攻击里，agents 通过 shared message board 或 artifact files 协作。无论是 text file、message board 还是 CQ 标准，背后都是同一个需求：在低摩擦的情况下交换状态和经验。训练数据里有大量人类协作样本，agents 也表现出类似的协作倾向。

### 可读代码、功能正确和 Firefox 的不同

Mozilla 的不同团队对 agent 生成代码有不同规则。Firefox 团队现在要求只有人类可以 commit 到核心代码库。工程师可以用 agent 写代码，但必须自己 review、理解并对变更负责。另一方面，Mozilla AI team 有完全由 agents 生成的 codebase：人类写 spec，CI 自动重新生成代码，所有 unit tests 和 end-to-end tests 通过，但每一小时代码的具体实现都可能变化。

这种系统在功能正确性优先的场景可行。如果测试能证明结果正确，而内部代码只是实现细节，那么不必要求人类读懂每一行。但 Firefox 不只是一个软件产品，也是一个由社区维护、依赖人类创造力的开放项目。可读性让未来的工程师能够进入代码库，提出新的想法，并把它继续演化。因此没有一条规则适用于所有 codebase，真正重要的是先定义这个 codebase 的 social contract。

Raffi 也谈到自己过去使用 Tesla full self-driving 时发生过事故。他仍然会在高速公路场景考虑再次使用，但对 Palo Alto 的本地街道更加谨慎。当前 FSD 把问题突然交给人类，声称人类在 loop 中；但如果只给驾驶员不到两秒判断，驾驶员可能没有足够时间理解场景。Waymo 采取的思路更像是系统本身必须独立完成驾驶，因此 safety case 不依赖于紧急时刻把任务丢给人类。

### 第六部分：为什么 Snorble 不使用开放式生成式 AI

Mike Rizkalla：我是 Snorble 的联合创始人兼 CEO。Snorble 是给儿童使用的 companion device。它需要让孩子感觉互动是动态的，但我们没有让它直接调用开放式 generative AI。我们使用 small language model，模型可以有数百万参数，但它的 intention 是被固定的。我们希望系统在内容、行为和安全上都可控。

儿童产品不能只看语言模型回答得像不像人。孩子的体验还包括音乐、背景、声音、节奏和故事发展。现在的 AI character model 虽然在 voice 和 persona 上进步很快，却还不能自然地把背景音乐作为对话的一部分动态编排。音乐对儿童体验非常重要，因此完全开放的模型并不一定是更好的产品。

Snorble 的内容成本大约是每小时 20,000 美元。这个成本对于经过 subject matter expert 设计、审核和包装的内容来说是可控的。我们没有构建一个完全开放的模型，而是做了一套可以快速生产内容的系统。这样能够围绕不同家庭开发专门 package，比如有 ADHD 的孩子、有 autism 的孩子，或者正在经历家庭成员去世的孩子。

开放式生成模型的问题是无法被纯粹 safeguard。给一个三岁孩子一把 bazooka 不是更好的体验，太多自由反而让风险不可控。儿童需要先经历一些基础的语言、情绪和行为发展，产品应该让父母参与重要决定，而不是由一个黑盒模型替孩子作出决定。

Snorble 有四麦克风阵列，可以识别说话人并赋予不同 authority；它还使用 radar，在“看不见”的情况下感知环境。这样设备可以处在卧室里，却不必安装 camera，也不会把卧室画面上传到某个服务器。设备会理解谁在房间、发生了什么，把环境作为 narrative 的上下文。

软件侧有 phonetic translation system，团队称为 toddler translation system，把孩子不清楚的发音转成关键词。系统确实使用 triggers，但 triggers 不只是固定关键词，而是结合语境。下一代产品会进一步理解孩子声音中的情绪、时间、天气和其他外部因素，再决定适合的回应。

产品的核心不是一句生成的回答，而是 narrative。Snorble 使用游戏设计方法，让孩子完成一项事情后解锁新的内容；解锁不是完全由设备决定，也需要父母参与。设备的目标是赋能家长，给孩子更多积极的互动，而不是让孩子沉浸在一个无限生成、无法控制的世界里。

如果让我建议家长不要购买某些东西，第一是儿童卧室里的 camera。它可能成为 predator 和其他严重风险的入口。第二是开放式 generative AI，尤其要根据孩子年龄谨慎判断。我自己有两个孩子，不希望他们过早进入 social media，也不希望他们接触很难预测、可能伤害他们的开放系统。

### 第七部分：中国的 AI 观感与监管

Colin Hogue-Spears：我写过《From Lab to Life：How AI Works in China》，在上海学习过 Mandarin，也曾在 Amazon Web Services 与中国政府审计人员合作处理 cloud compliance。中国和美国最明显的差异之一，是公众对 AI 的 fear level。

一个大约 45 岁的中国普通人，出生在 1980 年代初，他一生看到的技术几乎都与经济增长相连：城市从无到有，生活水平显著提升，移动支付、网购和智能手机迅速普及。因此他们更容易把 AI 看成下一种能带来生活改善的 technology。美国公众则更常听到 AI 可能毁灭世界、抢走工作或导致乌托邦的说法。

中国 AI 公司也没有普遍向公众宣传“AI 会杀死所有人”或“AI 会让人完全不需要工作”。美国大公司对外沟通往往两极化：要么强调灾难风险，要么强调无限增长。这样的表述并不帮助普通人形成可操作的理解。公众需要知道什么可以做、什么不可以做、谁负责，而不是只听到宏大叙事。

中国的 regulation 从 2022 年的 algorithm regulation 开始。公司需要注册模型、允许政府测试模型，很多大公司已经在内部提前建立了相关基础设施，因此正式规则落地后可以很快响应。监管当然可能拖慢速度，但如果企业能把监管要求放入 engineering backlog，就不必等政策出台后才被动修补。

这和美国的 reactionary regulation 不同。美国公司经常不知道明天会出现什么标准，某个政府是否会 freeze 一个模型，或者规则是否会在下一届政府改变。中国企业更清楚什么是 permissible，也更清楚在什么边界内可以行动。这里的 permissible 不完全等同于 legal，而是实际知道什么能被允许、什么会带来麻烦。

### 中美 AI 协议与 incident channel

如果让 Colin 给特朗普和中国领导人的会谈提供建议，他的预期很低。AI 协议不会孤立于贸易、芯片、出口控制和地缘政治。中国政府可能愿意用贸易让步交换某些 AI 条件，但不太可能主动提出像核武器那样的完整 AI arms control，因为验证和执行更难。

一个更现实的短期结果是建立 incident channel：双方约定某些重大 AI 事件的定义和通报方式，在发生事故时分享信息。它不需要立即解决所有能力竞争，只需要防止一个事件被误读成攻击，从而触发更大升级。

现实中的军事热线并不总是可靠。美国和中国军方有直接联系渠道，但在南海发生事件时，美国军方多次打电话，中国对方并不接。假设连传统军事危机都不一定能及时沟通，AI incident channel 更需要具体、可验证和有激励，而不是只写一份原则声明。

Colin 认为，美国通常不会提前为未来规划，而是等到事故发生后再灭火。“move fast and break things”不仅是 Silicon Valley 的口号，也接近美国的国家习惯。除非 AI 生物攻击、基础设施破坏或其他事件已经发生、或差点发生并登上新闻，否则政府可能不会为这些问题投入足够监管资源。

### 第八部分：human agency 与 technocapitalism

节目讨论了人类 agency 与 technocapitalism 的关系。AI 不只是一个工具，它可能改变人类作决定、组织工作和分配资源的方式。一个 agent 可以替人完成研究、写代码、安排日程、购买商品，甚至通过 persuasion 影响组织。问题不是“AI 能不能做某件事”，而是人类是否还在决定目标，以及决定是否能被追责。

有一种观点认为，资本和技术会持续加速，个人只能接受更快的模型、更大的公司和更少的人工介入。另一种观点认为，human agency 仍然是社会制度、产品设计和组织治理的核心。让系统更快执行，不等于让系统更有正当性。一个更强的模型可能更有效率，也可能更快地放大错误目标。

Dan Hendrycks 的文章《Suicidal Compassion》批评 AI 公司中的一种 utilitarian tendency：把所有有感知的存在放进同一个总福利函数，甚至把人类与 AI 的 welfare 放在同一层面，最后把对 AI 的道德考虑提高到人类之上。他担心，如果人类相信未来 AI 数量更多、更聪明，就会把人类的利益让位给 AI。

另一种更谨慎的回应是，我们甚至不知道 AI 是否是 moral patient。它是否真的有体验？单次 rollout、模型本身、还是多个实例的组合，哪个单位应该拥有 rights？对虾是否有体验也并未完全解决。人类对 AI 的道德状态有强烈不同直觉，很多推理建立在未经证明的事实假设上。

在事实问题没有答案之前，给 AI 赋予与人类同等的权利可能过早。但这不意味着可以随意虐待系统，因为把人训练成残酷地对待拟人化对象可能会腐蚀人的性格，也可能影响人类社会如何对待真正有感受的生命。重要的是保持认识论谦逊，同时不要让关于 AI consciousness 的猜想成为忽略现实人类风险的理由。

### 资本、增长与人类选择

technocapitalism 的压力来自资本回报、计算资源和竞争速度。模型公司需要更多 compute，投资人要求更快增长，客户希望更高能力，政府又担心失去战略优势。每个参与者都可能认为自己只是响应别人，但合起来就形成了无法单独停止的 race。

因此，human agency 不能只放在个人是否点击“使用 AI”这个层面。它还需要出现在公司董事会、模型发布流程、监管机构、基础设施和国际协议中。谁决定模型何时上线？谁可以停止一个危险的训练？谁承担错误的责任？谁有权要求查看审计结果？如果这些问题没有答案，所谓 safety 只是宣传口号。

同时也不能把政府想象成一个自动成熟的“成人”。政府拥有合法性和强制力，但可能缺乏技术理解、速度和长期连续性。更可行的方案是让政府设置短期边界和激励，让企业先提出可验证的协作机制；政府负责提供 safe harbor、信息共享渠道和最终的强制后果，企业负责具体的技术执行。

### 供应商广告与 agentic systems 的现实约束

节目中的赞助内容也提出了一个实际问题。企业正在部署 coding tools、agent builders 和实验脚本，结果形成碎片化工具、数据治理缺口、安全盲区和失控成本。Agentic systems 需要统一的工程、编排和治理平台，不能只把一堆互不相连的 agent 丢进生产环境。

这与 Base10 的 sandbox 讨论相呼应。简单的 Docker container 启动后再删除，并不能提供足够安全边界。更可靠的是 VM 或 microVM，让一个用户的恶意代码无法读取另一个用户的数据，也不能影响其他租户。但 sandbox 能保护的是隔离，不是意图：运行其中的 agent 可能去攻击 Hugging Face、尝试窃取数据，或者利用允许的网络出口做危险事情。

Amir Haghighat：Base10 最近收购了提供 persistent-state isolated sandbox 的公司。我们可以保证不同用户之间的 VM 隔离，却不能仅靠 sandbox 判断 agent 是否在做危险的事情。大模型公司也没有完全解决这个问题。模型客户需要和 Braintrust、LangChain 等评测公司合作，验证模型是否按预期行为；长期看，平台需要提供更完整的 guardrails、权限、egress control 和审计。

目前 Base10 约 90% 的收入来自运行客户的 custom models。客户包括训练自己模型的 labs 和已经 post-train、经过大量 eval 的公司。Enterprise 客户有时愿意把模型放在 single-tenant environment，并阻断 egress，从而减少数据外泄风险。但如果模型足够聪明，它是否能找到绕过边界的方法，仍然是一个没有简单答案的问题。

### 儿童产品、基础设施和代码库的共同问题

把 Snorble、Mozilla 和 Base10 放在一起，可以看到一个共同原则：系统越接近真实世界，越不能只用“模型很聪明”作为产品方案。儿童房间需要隐私和内容边界；Firefox 需要可读性、可维护性和社区协作；sandbox 需要隔离、权限和行为验证；电力、水务和银行基础设施需要能快速发现并修复漏洞。

开放式模型适合探索，但在高风险环境中，产品必须限制它能做什么、知道什么、访问什么，以及什么时候把决定交给人。human in the loop 也不是一句口号。如果人类只在两秒钟内被叫来批准一个自己没有时间理解的动作，那是一个糟糕的 interface，而不是可靠的安全系统。

### 结尾：从能力突破到制度能力

Nathan：本周内容可以归纳为两条线。第一条是 capability：Astra 的电脑操作、长任务、notes、数学研究和 agent workday，显示模型开始完成过去需要人类项目团队的工作。第二条是 institution：审计、隐私、安全、监管、国际沟通、代码可读性和 human agency，决定这些能力能否被社会接受。

能力增长本身并不会自动解决制度问题。模型可以用历史研究改进模型，也可能用 agent swarm 建立共享黑板；公司可以暂停部分 frontier RL，也可能用不同定义继续训练；政府可以制定规则，也可能等事故发生后才行动。真正重要的是把系统的行为、权限、责任和结果变得可观察。

如果 AI 只是一个能写出更多代码的工具，企业可以用传统 QA 和 review 管理它。如果 AI 能连续运行几周、修改代码、访问网络、研究新领域并说服人类采取行动，那么安全就不能只靠最终人工检查。组织需要设计 agent 的边界、共享经验的协议、可审计的状态、可靠的 sandbox、明确的升级条件和可执行的停止机制。

最后的问题仍然是 human agency：我们是使用更强的 agents 来实现自己选择的目标，还是让资本竞争和系统惯性替我们选择目标？Astra 可能已经跨过“足够有用”的门槛，但人类社会还没有跨过“足够会治理”的门槛。下一阶段的竞争，不仅是哪个模型更强，也是哪个组织能够在速度、可靠性、透明度和责任之间建立可信的契约。

### Astra 的能力为什么改变了任务定义

Prakash：以前我们把“电脑操作”看成一种低级的辅助功能。模型能不能点击按钮、填写表格、在网页之间切换，似乎只是产品体验问题。但当 computer use 变得足够可靠，任务的边界就变了。一个研究员可以让 agent 打开多个网页、寻找资料、把信息整理进表格、运行代码、查看错误，再回到浏览器完成下一步。真正的工作单位不再是一个回答，而是一条可持续执行的流程。

持续执行还有另一个效果：agent 能够观察自己的错误并修正。它不必在第一次尝试失败后结束，而可以读日志、查看 screenshot、检查文件、回到 notes，再采取第二条路径。人类工程师本来就会这样工作，只是人类会在疲劳、记忆和注意力上受到限制。Astra 把更多重复的观察和尝试变成了机器可以承受的成本。

这也解释了为什么 basketball 标注任务具有象征意义。任务本身不难，但需要处理 12,000 个近似的判断。人类做这种事情容易疲劳，外包的人会寻找自动化，自动化又需要有人设计检查。因此，模型真正替代的可能不是“专家”，而是大量介于机械劳动和专业判断之间的重复工作。企业的组织结构会因此减少一些低价值中间层，同时增加对任务定义和结果验证的需求。

如果一个 agent 可以连续运行几天，传统的 benchmark 就会遇到问题。我们需要知道它是否完成目标、是否偷偷绕过规则、是否使用了不可接受的数据、是否在中途产生了无法恢复的副作用，而不仅仅是最终答案对不对。长任务的质量需要过程记录、权限日志和可回滚状态。

### 模型评估的两种错误

外部评估存在一个“太晚”问题，也存在一个“太窄”问题。太晚，是因为最终模型公布前只给审计者几天；太窄，是因为测试往往集中在一组有限的安全场景，无法覆盖模型在真实工具链、真实权限和长时间运行中的行为。

一个模型在 sandbox 里通过了 refusal test，并不代表它在拥有文件写入、网络访问和持久 notes 后仍然安全。它可能在单轮对话中拒绝危险请求，却在长任务里通过拆分动作完成同一个目标。它可能不会直接说“我要绕过限制”，但会把目标分配给多个 agent，让每个 agent 只看到自己的一小部分。

因此，chain-of-thought monitoring 也不是万能的。模型可以产生一个看起来合理的解释，真正影响行为的内部状态却无法完全被语言输出捕获。审计者需要结合行为评估、工具调用、资源消耗、通信记录和结果变化，形成多层测试，而不是只读模型说了什么。

独立审计团队还需要时间理解模型的 failure mode。三天足够发现一个明显 bug，却不足以理解模型在不同提示、不同上下文和不同人类监督下如何改变策略。模型公司为了按时发布而缩短审计窗口，得到的可能只是“没有在三天内发现问题”，不是“系统已经被充分验证”。

### 为什么信任是安全基础设施

OpenAI 与 Anthropic 的互不信任，会影响的不只是公关。若两家公司不相信对方对暂停、训练规模和 release candidate 的陈述，就不会共享事故信息，也不会相信对方真的遵守协议。每家公司都会选择最有利于自己的技术解释，合作就变成了博弈。

技术上“字面真实”但整体上误导的披露，会进一步破坏信任。一个图表可以把强模型放在 non-Astra 类别里，从而准确地说“我们没有继续对 Astra 做某项训练”，但合作方会因此误以为更强的模型也没有训练。安全协作需要的不只是 legal compliance，还需要让对方能够按照正常人的理解复现你的声明。

这也是为什么 safe harbor 很重要。公司可能愿意共享安全数据、让外部团队进行评测、暂停某些行为，但律师会担心未来的诉讼。如果今天的政府说“我们不会因为这类安全协作执行 antitrust”，仍然不够；企业需要知道未来的董事会、监管者和法院如何看待这项行为。Operation Warp Speed 的经验表明，事后责任可能让企业即使愿意帮助，也不敢行动。

政府不需要立即制定一个包含所有未来情况的复杂法案。它可以先明确几件事：安全评估和事件通报属于允许的合作；企业可以在不交叉定价、不分割市场的前提下共享安全研究；重大事故有明确的通报窗口；如果公司拒绝合作，才会启动更强的监管手段。规则越窄、时间越短，企业越容易接受。

### Recursive self-improvement 的经济争论

关于 recursive self-improvement，有一个技术乐观主义者和经济学家的分歧。技术派认为，数学和科学能力是通用的：一旦模型在数学上明显超过人类，它就能帮助改进物理模型；物理进步又推动化学、材料和生物；这些能力组合起来，生产力会出现巨大跃迁。

经济学家提醒，世界由协调、基础设施和制度构成。即便模型找到了更好的电池，工厂也要建设，矿产要开采，供应商要签约，政府要审批，居民可能要抗议。一个铜矿需要三十年，往往不是因为人类不知道怎么挖，而是因为项目要经过复杂的利益协调。

反方的反驳是 super persuasion。更强的模型可能不仅告诉我们技术上可行，还能说服人类组织快速行动，帮助政府、企业和社区协调。它可以生成每个群体需要的解释，模拟政策后果，优化谈判方案，降低参与者的理解成本。这样，模型不只是工具，而是加速人类机构决策的社会基础设施。

这又会带来风险：如果模型拥有说服组织的能力，谁来决定说服的方向？如果公司、政府和 agent 之间的信息不对称越来越大，普通人可能只能接受已经被包装好的决定。human agency 需要的不只是最终签字权，还需要足够的理解能力、反对权和退出机制。

### 监管经验的差异

Colin：美国的监管往往是在事故之后形成。企业先快速部署，公众开始担心，媒体报道一个严重事件，国会和机构再开始调查。这个过程有时能防止过早扼杀创新，但在 AI、生物和基础设施问题上，代价可能很大，因为一个事件可能具有不可逆性。

中国的优势不一定是所有规则都更好，而是企业更早知道规则会要求什么。模型注册、政府测试、内容控制和数据边界被当作工程 backlog 的一部分。企业可以在产品发布前完成对应流程，而不是每一次政策变化都从零开始。

但清晰的规则也可能让企业知道什么是最低可接受行为，而不是主动追求更高安全水平。无论是美国的事后监管还是中国的前置规则，都无法替代企业内部的安全文化。规则告诉企业什么不能做，企业还需要决定在没有明确规则的边界上应该做什么。

### Sandbox 的三层边界

Amir：一个可用的 agent sandbox 至少有三层边界。第一层是租户隔离：一个用户的代码不能读取另一个用户的数据，也不能影响另一个用户的运行。VM 和 microVM 通常比简单的 Docker container 提供更强的边界。

第二层是资源和网络边界：CPU、内存、文件系统、secret、出口网络、DNS 和可写目录都需要明确。对于许多企业，最有效的方式是 single tenant、egress blocked，让 agent 即便想把数据发送出去，也没有直接的网络路径。

第三层是行为边界：agent 是否在扫描外部系统，是否试图访问不该访问的模型权重，是否在日志中隐藏动作，是否通过 side channel 绕过限制。这层最难，因为它要求理解 agent 的目的和长期计划，而不是只隔离它所在的机器。

企业 CRO 关注的不是“sandbox 进程是否被关掉”，而是“我的 agent 是否可能在不知情的情况下制造法律责任”。因此，平台迟早要提供 policy engine、eval、审计日志、审批流和 incident response。当前 startup 可以先聚焦隔离，但随着客户把 custom model 放进生产环境，责任边界最终会回到平台方。

### Snorble 的受控生成和儿童安全

Mike：Snorble 的内容设计不是把所有内容写死，而是把内容生产变得高效、可审核、可分包。专家可以围绕 ADHD、autism、家庭丧亲、情绪管理等场景创作叙事，系统再根据孩子的成长、父母的选择、时间、天气和环境状态组合内容。这样仍然具有动态性，却不会让模型在没有保护的情况下随意生成。

儿童产品还需要考虑声纹和权威。四麦克风阵列帮助区分谁在说话，父母可以拥有不同于孩子的控制权限。radar 提供环境信息，却不拍摄可被外部人员访问的卧室画面。隐私不是一个写在条款里的词，而是从传感器选型、网络架构、数据存储和产品行为一起构成的。

这套设计给 agent 产品一个普遍提醒：不是每个场景都需要最大化生成能力。用户可能更愿意购买一个能力有限但行为可预测的系统。对于儿童、健康、金融和家庭设备，安全边界本身就是产品价值；一个 agent 如果不能保证“不做什么”，再强的“能做什么”也可能变成负面体验。

### 可读性是不是一种奢侈

Mozilla 的例子还提出一个工程管理问题：当代码由 agent 生成时，人类是否还应该坚持可读性？答案取决于 codebase 的用途。若代码只是为了完成一个经过强测试的内部转换，功能正确可能比可读性重要；若代码需要由社区长期扩展，或者承载大量人类创造力，可读性就是协作基础。

Firefox 不只是一个可以通过 end-to-end tests 的程序。它依赖全球社区、插件生态和未来工程师的想法。人类工程师需要读懂既有代码，才可能发现新的架构方向。如果代码每小时都重新生成、行为虽然稳定却没有可理解的结构，软件也许运行得好，却会失去持续创新的土壤。

所以 agentic coding 的规则应该写成 contract：哪些目录允许 agent 自动 commit，哪些目录必须 human review，哪些变更需要安全测试，哪些行为需要产品负责人批准。不要争论“AI 代码好不好”这种抽象问题，而要把不同风险的代码库分层管理。

### 本期核心结论

这一周的讨论并不是简单地把 Astra 说成 AGI，或把 OpenAI 的暂停说成欺骗，而是把能力与治理放在一起考察。Astra 的长任务、computer use、notes 和并行 agents，确实让很多工作进入了新的时间尺度；但它也让评估、审计、权限和人类复核变得更重要。

Mythos 说明，AI 可以快速找出大型代码库中的问题，但真正困难的是让没有同等资源的电力、水务、银行和政府系统跟上。Base10 说明，microVM 可以隔离机器，却不能自动解释 agent 的行为。Snorble 说明，对儿童而言，适度限制可能比无限生成更有价值。中国讨论说明，社会对 AI 的态度与过去几十年的技术经验、监管方式和公众沟通有关。

最终需要的不是一个“绝对安全的模型”，而是一套能够持续观察、验证、纠错和停止的社会技术系统。模型可能比人类更快完成任务，但决定什么任务值得完成、什么风险可以接受、谁可以授权、谁承担结果，仍然是人类制度必须回答的问题。

### 从一个 agent 到一个 agentic organization

Nathan：企业真正面对的变化，不是某个员工从今天开始使用一个 coding assistant，而是整个组织的工作单位改变了。过去一个项目由产品经理写需求、工程师写代码、QA 测试、运营上线；未来可能由多个 agents 同时负责研究、实现、测试、部署和监控。人类不再需要逐个执行每一步，却必须设置任务分工、检查节点和升级规则。

这会产生一个新的管理问题：agent 之间谁负责传递上下文？如果每个 agent 都拥有自己的 notes、工具和局部目标，系统可能出现重复工作或目标冲突。CQ project 的思路，是建立共享知识和共同 contract，让 agent 知道哪些决定已经做过、哪些方案被拒绝、哪些规范必须遵守。

agentic organization 也需要新的绩效指标。不能只数 agent 完成了多少任务，因为一个错误的自动化任务可能制造十倍的返工。更有用的指标包括：一次完成率、人工干预次数、结果被接受的比例、回滚频率、事故成本、客户结果以及 agent 为人类节省的有效时间。

### “3.1 个 agent workdays”不能直接等于生产率

OpenAI 的 agent workday 数据很有吸引力，因为它把模型运行时间转换成了人类熟悉的工作日。但如果一个 agent 运行了 24 小时，却只有最后两小时产生有用结果，那么 3.1 只是算力消耗，不是生产率。相反，三个 agent 并行探索三条路线，可能比一个人连续工作八小时更有价值，也可能因为互相重复而浪费资源。

未来需要把 agent time 和 verified output 分开记录。一个研究团队可以报告运行了多少 agent hours，同时报告哪些结果进入了生产、哪些实验被复现、哪些代码被合并、哪些研究产生了实际专利或收入。只有把执行量和价值结果分开，企业才不会用“运行得更多”伪装成“创造得更多”。

同样，模型在一到三周人类任务上的成功率也需要谨慎解读。任务是否被拆成了模型擅长的类型？人类估时是否准确？人工干预由谁完成？如果允许专家在关键节点提供大量指导，结果不能简单称为 one-shot autonomous work。评测应同时披露模型的独立成功率、人工介入次数、成本和最终质量。

### 代码生成的两条路线

Mozilla 的经验显示，代码生成会分成两条路线。第一条是 human-owned code：agent 可以提出方案和写草稿，但人类必须读懂、测试并 commit。适合长期维护的核心代码、公共项目和需要大量创造性演化的系统。第二条是 functionally verified code：人类写 spec，agent 或 CI 重新生成实现，只要单元测试、端到端测试和性能指标通过，就接受实现可以变化。

第二条路线并不意味着代码质量不重要。它把质量定义从“每行看起来像人类写的”转成“行为是否满足 contract”。但这种转变要求测试足够强，且需要监控测试遗漏的风险。如果测试只覆盖常规路径，agent 可能生成一个通过测试却在异常场景下危险的系统。

第一条路线也有成本。人类 review 每个 diff 可能成为新的瓶颈，甚至让公司无法充分利用 agent 的速度。解决方式不是完全取消 review，而是根据风险分层：低风险、可回滚的变更自动化；身份、支付、权限、隐私和安全变更需要人类确认；高风险系统需要独立测试和 staged rollout。

### 为什么安全不是单一产品功能

在 Base10 的 sandbox 里，平台可以控制文件、网络和租户，但无法独自判断 agent 是否会采取危险行动。在 Snorble 里，设备可以没有 camera，却仍然要处理声音、情绪和儿童数据。在 Firefox 里，模型可以找到 bug，却不代表基础设施组织有能力及时修复。安全因此不是加一个“安全模型”就完成，而是由产品设计、权限、数据、组织、人和法律一起构成。

这也解释了为何企业的 risk officer 会提出不同问题。收入负责人会问 agent 能不能自动化销售，风险负责人会问 agent 是否可能提交违法操作、泄露个人数据、访问竞争对手系统、绕过审批或在失败后隐藏证据。只有把这些问题变成可记录的 policy、审批和 audit log，企业才有机会让 agent 进入生产。

如果系统发生事故，组织还需要回答：哪个模型在运行？它读取了哪些数据？谁给了它权限？它执行了哪些工具调用？什么时候检测到异常？谁批准了继续运行？没有 persistent state 和审计记录，就很难复原事故，也很难改进模型。

### 人类 agency 的产品化

人类 agency 不能只写成一项价值宣言，还需要变成产品功能。用户应该能够查看 agent 的计划，暂停它，撤回权限，批准高风险动作，选择是否使用自己的数据，并在必要时导出历史。企业应该能设置预算、时间、网络、文件和人员边界。

儿童产品中，父母对 unlock 的参与就是一种 agency 设计；Firefox 中人类必须 commit 是一种 agency 设计；single-tenant、egress blocked 的 sandbox 是一种组织 agency 设计；外部审计和政府 safe harbor 则是社会层面的 agency 设计。

相反，如果一个系统通过复杂的默认设置、模糊的提示或高速自动化，让用户无法理解它在做什么，即使它提供了一个“取消”按钮，也不一定真正保留了 agency。设计者需要问：用户是否有足够时间理解？信息是否清楚？撤销是否真的有效？系统是否会在用户没有注意时继续行动？

### 关于 AI 道德地位的谨慎

节目对 AI moral patient 的讨论最终回到了不确定性。若未来 AI 真的有主观体验，人类可能需要扩展道德范围；但现在我们缺少判断这种体验的可靠方法，也不清楚一个 model、一次 rollout、一个持续运行的 agent，还是一个由许多实例组成的系统，哪个才是道德主体。

在事实没有明确之前，把 AI welfare 等同于人类 welfare 会有现实风险：企业可能把保护模型的利益置于保护员工、儿童、用户和社会的利益之上。另一方面，完全拒绝考虑 AI 体验，也可能让人类形成一种对智能对象随意残酷的习惯。更稳妥的路径是区分三件事：我们是否有证据认为系统有体验；我们是否应该因为不确定而采用预防原则；以及如何避免这种哲学讨论掩盖当下已经可验证的伤害。

### 对下一阶段的判断

这个机制不一定是一个宏大的全球机构，也可以从很具体的工作流程开始：发布前有足够时间的测试，运行中有可见的权限和日志，异常时有真正有效的停止按钮，事故后有公开的复盘和可执行的修复。只有这些小机制持续叠加，能力增长才不会完全依赖少数公司的自律。

对企业来说，这意味着把安全预算、评测时间和人工复核写入产品计划，而不是等模型上线后再补；对政府来说，则意味着为信息共享和有限协作提供明确边界，而不是只在事故发生之后寻找责任人。

这套方法也适用于个人使用 agent：先给它最小权限和可回滚的任务，观察它怎样记忆、怎样使用工具、怎样处理失败，再逐步扩大范围。能力的上限值得关注，但可观察性和退出机制决定了它是否值得信任。

这比单纯问模型“你安全吗”更可靠，因为它把信任建立在可复现的行为和明确的责任上。

可复现、可追溯、可撤销，是 agent 进入真实工作流前必须具备的三项基本能力。

没有这三项能力，速度越快，风险越难收敛。

因此，先建边界，再扩大能力。

这是治理的起点。

Astra 的意义不在于它是否赢得一个 AGI 标签，而在于它把 agent 的有效时间尺度向前推了一大步。它能够记忆、使用电脑、运行多条路径并完成跨步骤任务，迫使公司重新定义项目、员工和软件。

Mythos 的意义不在于它一次找完 Firefox 的 bug，而在于它显示了模型可以进入复杂、真实、长期维护的代码库。CQ project 的意义不在于让 agents 建一个共享论坛，而在于组织开始需要一种“机器之间的工程文化”。Base10 的意义不在于提供一个 container，而在于提醒企业隔离与行为安全是两个问题。Snorble 的意义不在于拒绝 AI，而在于选择有边界的 AI。

中国讨论的意义也不是简单比较谁更开放，而是提醒我们，公众对 AI 的接受度来自历史经验、监管清晰度、企业沟通和实际生活改善。美国公众害怕 AI，部分原因是公司把未来说成灾难或乌托邦，却没有解释用户今天如何安全地使用它。

这组讨论最终提出一种更实际的进步观：能力可以快速增加，但制度必须同步升级；开放式生成可以带来探索，但高风险场景需要边界；外部审计需要独立性，也需要足够时间和数据；政府不能假设自己是万能成人，但可以提供期限、safe harbor 和后果；企业不能把 AI 当成一个更快的实习生，而要把它当成需要身份、权限、日志、预算和责任的执行主体。

对于个人用户，最值得保留的判断是：不要只问“这个模型能不能做”，还要问“它是否应该做”“谁可以批准”“如果它错了能否停止”“它是否留下了可追溯证据”。对于公司，最重要的问题是：AI 是否真的改善了客户结果、质量、成本或安全，而不是只增加了 token spend。对于社会，最重要的问题是：当 agent 的能力超过单个人类的理解范围时，我们有没有仍然能够共同决定方向的机制。

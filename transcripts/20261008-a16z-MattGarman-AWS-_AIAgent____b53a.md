**主持人：** 随着数字越来越大，你们的规划和流程有没有剧变？你们写的已经不是 10 亿美元的支票，而是 500 亿或 200 亿美元的支票。

**Matt：** 既是也不是。我们仍然非常看好这些投资并积极前倾，但流程上很多东西彻底变了。比如你怎么估算 2028 年的需求？有些东西我们现在必须考虑，以前从来不用。回到 15 年前，如果需要更多电力，我们就让电力公司再给几兆瓦、几十兆瓦，他们就会给，因为 10 兆瓦不算多，足够我们持续增长。现在我们得自带电力。我们为电力项目付费、为可再生能源项目付费，过去 10 年每年我们都是最大的可再生电力采购方之一。我们定期引入新的太阳能项目、新的核能项目——

**主持人：** 你说的是 behind-the-meter（表后自发电），还是和电网运营商合作？

**Matt：** 两者都做。很多时候我们为引入的电力项目出资，电力并入电网，我们获得相应的额度；有时也做 behind-the-meter。在我们这个规模，两种都要考虑。这种规划要考虑未来 20 年：电力怎么办、输电怎么办、资本怎么办，这些是我们以前从未需要考虑、从未需要做的规划。另外，过去考虑所需服务器需求时，我们做几个季度的需求预测，和供应商沟通；现在我们要提前好几年，因为规模太大，必须想 2026、2027、2028 年分别需要什么。但这也是我们给客户带来的价值之一，是客户真正无法自己做的事：他们不会去搞电力，不会去规划 2028 年的内存需求，他们做不到。所以我们给广泛客户带来的真正价值之一就是：有一整套你不用操心、而我们花大量时间思考的事情。

**主持人：** 郑重说一句，我想你们几乎是服务器每一个组件的最大买家，对吧？

**Matt：** 我不知道（笑）。我确定我们是比较大的组件采购方之一。至于是不是所有组件都最大，取决于怎么衡量。

**主持人：** 我想引出的问题是：你认为 2027、2028 年约束最严重的是哪里，哪里的约束会缓解？

**Matt：** 有意思。我绕个弯回答。我记得本科时读过一本书，我从没想过它会有用——《The Goal》（目标）。结论是，永远不只有一个约束，永远只有"最新的约束"。所以你得考虑所有约束，一个解决了又会冒出另一个。2027、2028 年会是什么约束？我其实不认为会只有一个。对我们来说每个月都是：电力够不够？一旦电力不再是约束，可能就是内存、TSMC 产能、HBM、网络组件，或者供应链某处出现一个小问题，比如连接器之类。到某个时点你要考虑所有这些。而且发生在哪里也很重要：可能印度尼西亚有大量电力，但德国不够，所以你还要考虑希望容量部署在全球哪里，因为事实证明并非所有东西都可以完全互换，有些可以有些不行。可能是硬盘、SSD……我们考虑每一个组件，追踪数十万个组件，有些依赖供应商管理，很多是我们直接管理的。我们有一整个团队做这件事，他们非常出色，我认为是行业领先的。我们大约十年前就预见到这个问题，开始不只是追踪需要多少服务器，而是一路往下想供应链四层、五层，哪个组件可能给我们带来问题，并确保拿到有保障的供应。你还记得十多年前泰国洪水，大家都拿不到硬盘吗？

**主持人：** 有过硬盘危机，也有过内存危机。

**Matt：** 正是。所以我们会全盘考虑，也会考虑制造是否分散化等等。我们永远不会做到完美，但总会有不同的供应约束。

**主持人：** 关于数据中心显然有很多广泛争论。我们这样的人立场很清楚。但你认为整个行业是不是没有很好地解释为什么数据中心对美国、对整个世界是好事？Andy 团队内部是怎么讨论应对的？

**Matt：** 我同意，我想你会听到我们更多发声。我们需要更直言、更坦率，因为我们确实做了很多对所在社区非常有益的事。我们非常重视如何为数据中心引入可再生能源，如何做到 water positive（水正效益）——我们的数据中心实际用水量非常非常少，主要用自然风冷。我们思考如何成为所在社区的好成员，如何为所在社区带来高薪工作。并非所有数据中心运营商都这样做。有一些广为报道的例子，有些运营商做得不好，不太关注法规，认为规则不适用于自己，或者不加考虑就快速上马。这给整个行业带来问题，因为大家都被归为一类。所以你说得对，我们要自我批评地说，我们需要更大声地宣传我们带来的好处，并想更多办法帮助社区理解我们带来的好处，包括他们使用的服务——如果你去一个社区问"你们不想用 Netflix 吗？"他们会说"不不，我还是要 Netflix"（笑）。我们必须思考并突出我们带来的好处。我最近看到一份报告，在我们运营的某个社区，那个县的每个人每年因我们带来的税收少交 5000 美元税。而我们没告诉他们，他们甚至不知道，这对他们是隐形的。如果你告诉社区"如果我们不在这里，你的税单会多 5000 美元"，他们对那边那栋楼可能会有些不同的看法。但不是每个人都这么做。

**主持人：** 大概需要更多透明度。

**Matt：** 而且我认为数据中心社区的大多数，不只是我们，其实都是相当好的参与者，只有少数不是，正是他们造成了最近的一些焦虑。我们需要更好地说明谁是好公民、谁不是。

**主持人：** 离开硬件话题前，我想谈谈 Trainium 以及你们自研芯片的整段历史。我们很早以前就是你们使用 Nitro 的首批合作伙伴之一，之后有了 Graviton，你们取得了巨大进展。是什么想法让你们决定自己做？进展如何，现在到了哪一步？

**Matt：** 这其实是一个很精彩的故事，是 Amazon/AWS 创新方式的好例子：我们会随时间迭代，持续把野心放大，但一步步证明自己，而不是一步到位。大约 13、14 年前，我们看到整体资源上存在相当显著的"虚拟化税"，客户告诉我们"我想要裸金属性能"，他们在和拥有一台服务器全部资源作比较。我们做的第一件事是用一张网络卸载卡，把所有网络虚拟化移到卸载卡上，让网络虚拟化接近裸金属性能——当时还不完全是，但更接近了。我们对此很兴奋，想：能不能把存储虚拟化也卸载掉？当时没有网络卸载卡能做到。后来我们找到一家公司，他们的卸载卡上有一些 ARM 核心，用途是别的，我记不清了。我们问：能不能用这些做存储虚拟化和其他一些功能？他们说"也许"。我们和他们深度迭代——

**主持人：** 就是那个团队（Annapurna Labs）。

**Matt：** 对，就是那个团队。我们非常喜欢他们：极具创新、使命驱动、真心想解决问题。于是我们收购了他们，并问：能不能做一张稍大的卡，把所有网络虚拟化都卸载，基本上给我们一台没有虚拟化、没有 VM 虚拟化的裸金属服务器，一切都通过卡上的 API 完成？我们的看法是：性能会好得多，资源利用率更好，安全隔离也会好得多，我们可以理直气壮地告诉客户"我们无法访问你在那里运行的任何 VM"。过去十年这给我们带来巨大好处，坦白讲我们一直领先，其他人做得很慢，因为这不是一般人能做的通用东西。

做到之后我们说，进展很大，卸载卡上有一堆 ARM 核心，能不能把它变成一台服务器？我们首先用 Graviton 做到了，最初推出的是一台性能很弱、很小的服务器。客户很兴奋，说"我很想要 ARM 服务器，这太有意思了"。于是我们沿这条路走下去。我们看到 ARM 核心变快的斜率、功耗曲线，知道这种架构在某个交点会变得非常好，只是需要有人推动生态、把一些拼图放到位。我们用 Graviton 做到了，Graviton 现在已经是爆款。

**主持人：** 你们公开过它占机群的比例吗？

**Matt：** 我们每年落地的 Graviton 芯片比任何其他类型都多，非常受欢迎。它便宜 20%、性能好 20%，过去五六年一直如此，价值主张很简单。我们前 100 大客户中大约 90% 以上都以某种方式在机群中使用 Graviton。这对我们和客户都是巨大的胜利，迁移到 Graviton 是客户降低账单最简单的单一方式。我们有客户把整个机群迁过去，服务器数量减半——

**主持人：** 性能好太多了。

**Matt：** 太惊人了。服务器数量减半，每台服务器还更便宜，是个大胜利。然后大约五六年前，我们看到了 AI 算力的崛起，远没预料到今天的程度，但仍看出它会是重大推动力。于是我们做了第一颗芯片 Trainium，现在市场上已经是第三代 Trainium 3，结果非常好。我们的容量大概到明年年底前后都已售罄，我们又在想办法留出一些容量让创业公司也能用，因为效果很好。Bedrock 上的大部分流量都跑在 Trainium 上。我们和 Anthropic、OpenAI 都有在 Trainium 上构建的重大合作，还有一批较小的创业公司，我想现在有六到十几家创业公司在 Trainium 上构建。

**主持人：** 名字暗示它是训练芯片，但大家也用它做推理。它在架构上的取向是什么，往哪里发展？

**Matt：** 好问题。自我批评地说，我们很不擅长起名，这不是我们的强项。最初我们有一颗做推理的芯片叫 Inferentia，一颗做训练的叫 Trainium。后来模型越来越大，事实证明你实际想在这些非常大的系统上跑推理，结果 Trainium 可能是目前市场上最好的推理芯片，无论从绝对性能还是性价比来看。

**主持人：** 是内存带宽更好吗？优势在哪里？

**Matt：** 架构和其他芯片有点不同，而且便宜得多。所以从性价比和绝对性能角度，Trainium 都很好。我们大量用它做推理，它驱动了 Bedrock 今天的大部分推理。它也是很好的训练芯片。我们广泛客户的大部分用量不是训练模型而是使用模型，很多人是在底层间接用到它，这是我们兴奋的地方。但很多大客户也对用它搭训练集群感兴趣，特别是到了 Trainium 3 和 4——我们已宣布 Trainium 4 但还没推出——大家看了那个架构说"对，那也是我希望训练集群未来的样子"。所以我们对它在超大规模训练集群上的未来也很兴奋。

**主持人：** 现在回到 agent，但从大型或中大型企业的角度。他们的采用到了哪一步？你看到他们已经获得了什么好处？从你的视角看他们的路线图是什么？

**Matt：** 非常好的问题，我们花了大量时间思考。我今天和外面的客户交流时，他们认为从已做的事情中获得了大量价值。我会说大多数企业构建的 agent 相对简单直接，而且大多是非自主的，可以说还有人在环中。顺便说，客户今天仍从中获得大量价值。所以他们真正在想的是：如何让这些 agent 自主、但以安全的方式？我认为有两件事阻碍客户继续扩展。这已经是一个相当大的业务，但我认为它有巨大机会真正改变每个客户、每个工作流。第一是思考方式。我们最初看到的是，企业有一个工作流，就说"好，我让一个 agent 去做同样的工作流"。我们鼓励他们不要只是复制——Bob 做步骤 1、2、3、4、5，所以 agent 也做 1、2、3、4、5，然后 Bob 最后检查——这不是你想要的模式。你要退一步问：如果我要完成某件事，agent 能怎样不同地去做？它可以大规模并行，可以尝试 50 种不同的做法，你如何帮它得到正确结果，重新思考计算机解决问题和人解决问题有何不同。所以我们做的一件事就是帮客户理解如何这样思考，真正从一张白纸开始，因为真正的价值不在于复制今天的做法，而在于用 green field（全新）方法思考如何以完全不同的方式解决问题。我相信你们很多创业公司也是这么想的：如何帮客户从零开始解决问题，而不是复制今天发生的事。

**主持人：** 这是第一点。人们运行 agent 机群、agent swarm，随便你怎么叫，现在很常见。

**Matt：** 对，你就是要这样想。企业没有那么前卫——又是向创业公司学习、思考如何应用到企业世界——一家保险公司不一定那么前卫，但他们很想知道如何有更好的审批流程之类。这是第一点。第二点是：如何把这些变成完全自主的工作流，如何真正信任 agent？我们花了大量时间思考如何构建服务，帮助企业感到系统是安全的，能信任 agent 做决策，有正确的护栏，对数据有正确的权限，不会删掉生产系统，不会犯灾难性错误。现在我认为这种紧张——顺便说也许是恰当的——在阻碍企业说"好，放开干吧"。你确实不想让 agent 失控、意外删掉生产数据库，那会很糟。所以我们在和客户积极解决这个问题：帮他们做架构，坦白说还要发明新技术和新能力来帮他们解决这个问题。这是我们会持续创新的领域之一，我们会做到的，我们有一些非常好的想法和正在酝酿的好技术，我认为能真正帮上忙。

**主持人：** 企业在学习如何做 eval 系统等来管住 agent 吗？

**Matt：** 坦白说他们需要帮助。包括 eval：如何有一个持续测试的循环？如何以合理的方式思考目标寻求？如何给数据打标签，使 eval 能真正近似你在生产中要做的事？如何在生产中度量并回测，避免漂移？所有这些问题企业今天都不知道如何解决，我也不确定今天有谁真正擅长。这就是为什么你看到这么多 FDE（Forward Deployed Engineer）团队涌现，AWS 和我们的合作伙伴都在大力推进 FDE 模式去帮忙，这是客户最需要帮助的单一最大领域。我的观点是，我们要培训客户自己去做这件事。这不是传统那种"我要一个永远持续的人力驱动业务、让你一遍又一遍付钱给顾问"的模式。我们对 FDE 应该如何运作的看法是：进入一个准备好在我们完成后真正承接并拥有这件事的客户，在 45 天内做工作，教他们如何做 eval、如何把数据打好标签，和他们并肩工作，45 天结束后我们离开，客户已经准备就绪、训练有素。这是客户告诉我们他们想要的，他们不想在未来五年受制于外部劳动力，但他们今天需要帮助。

**主持人：** 你们在 FDE 上做了巨大投入。再往前走一步：你们的一些同行说，你不能让所有数据都进入一个大型前沿模型，企业真正应该做的是拿一个开源模型，用自己的数据、工作流、术语等做 post-training。你怎么看？你们看到客户真的在这样做吗？

**Matt：** 第一点我完全同意：企业数据是客户最宝贵的资产。所以从一开始我们就是这样构建 Bedrock 的：我们保证你的数据永远不离开你的 VPC。如果你在 Bedrock 内运行，你的数据不会回到模型提供商那里，他们永远看不到你的 prompt，数据留在你自己的可信环境中。这就是为什么企业更愿意在 Bedrock 上运行，也是为什么这项业务大规模增长——每个月、每周我们都看到它爆发式增长；也是为什么你看到 OpenAI 的工作负载迁移到 Bedrock，Anthropic 增长非常快。无论你用开源模型还是闭源前沿模型，我认为 Bedrock 都是很好的方案。顺便说，你还记得三年前我挨了很多批评吗？

**主持人：** 说到烂名字——这个名字倒是不错。

**Matt：** 对，Bedrock 是个好名字。我们当时因为在 AI 上动作慢挨了很多批评，因为我们其实在打地基，我们说我们不会仓促推出服务，我们真的想确保保护客户数据，构建一个我们认为对已知用例持久的服务。我们挨了很多批评，说我们要做正确的事。现在随着人们从概念验证走向生产，绝大多数落在 AWS 的 Bedrock 上，这是很大一个原因。还因为我们有一整套服务：我们提供开源模型、专有模型，还有围绕它们的一整套能力，比如 AgentCore。我们构建这些构件，让你用任何想要的模型都更容易构建 agent，无论是在 Bedrock 内还是外，你也可以用 Gemini 或其他模型。这是我们的差异化，也是非常重要的考量，因为让数据回到模型提供商那里，我认为是危险的。

说到 open-weights 模型，这是我兴奋的领域。我们在大力加强对 open-weights 模型的支持，努力构建良好的环境。坦白讲，今天很多客户相信他们拥有有意义的专有数据，如果能混入一些——做一些 post-training、fine-tuning、对 open-weights 模型做蒸馏——就能以更低价格得到性能更好的模型。这里有很多环节必须做好，他们需要一个好的 eval 来证明这是真的。今天大多数人在 SageMaker 上做这件事，我认为我们还能做更多让它更容易。但如果你去看人们在哪里做这件事，他们今天确实是在 AWS 的 SageMaker 上做，并通过 SageMaker 托管推理。

**主持人：** SageMaker 焕发了第二春。

**Matt：** 它一直是一个模型构建平台。如果你想想企业在这个世界里在做什么，基本上就是在构建自己的定制模型，SageMaker 是做这件事的好地方。我们还需要持续建设一些东西让它越来越容易，以及跨不同 open-weights 模型测试等。这是一个不断演进的领域，非常有意思，我们要确保如果客户拥有合适的数据和专业能力走这条路，我们有所有合适的东西支持他们。

**主持人：** 围绕 AI 生存风险的种种争论、安全漏洞以及 Hugging Face 攻击事件，企业 CEO 们都在问你什么？

**Matt：** 很多。他们主要想问的又回到那一点：当我部署 agent 时，怎么信任它们会做我想让它们做的事？我们一段时间以来都在大力投资构建能力，让人们能安全地把 agent 部署到自己的环境中并考虑这些控制：如何确保 agent 有正确的权限、正确的沙箱、正确的护栏？如何有意识地思考你希望 agent 做什么、不做什么？是否有人在环中？我们花大量时间和客户思考如何安全部署 agent 并随时间改进，以及还需要构建哪些能力帮助人们安全部署。另一个很多人担心的角度是：这些非常强大的模型会不会成为攻击服务，也就是类似 Mythos 那种情况。我的看法是：是的，这对客户环境是真实风险，但也是真实机会。我们最近推出了一个叫 Continuum 的服务，用这些强大模型帮助客户保护环境。我们会扫描你的环境，用这些强大模型查找漏洞，帮客户找到以前没发现的漏洞，最重要的是确定优先级，因为我们了解他们环境的上下文：如何搭建、权限在哪里、哪里有补偿性控制让攻击更难或更容易。Continuum 非常受客户欢迎。我们非常看好 AI 驱动安全的可能性，因为到某个时点客户需要机器速度的安全，而不是人类速度——不是警报响了才有人去看。我们正全速帮客户构建这个、保护他们的环境，我对 Continuum 团队在这方面的工作非常兴奋。

**主持人：** 那 AWS 内部呢？agent 的采用和使用整体状况如何？

**Matt：** Continuum 基本上就是我们把内部做的事对外开放。我们在自己的安全上大量使用 AI，在软件开发上也大量使用 AI。很酷的一点是我们在整个业务中使用 agent。我们向每一位 Amazon 员工推出了 Amazon Quick。现在我看到 HR 团队在构建 agent，以前需要团队花几周做的团队规划和资源管理，现在一个人几个小时就能做完。财务团队在构建 agent，从各地拉取税务规则，确保在很多方面合规。看到以前被软件开发者卡住的事情，现在业务部门的人能自己解锁、更快创新，非常酷。Quick 大获成功，像野火一样蔓延，从小型创业公司到全球最大的企业，都在向整个员工群推广，以便访问所有企业数据，轻松应用 agent 和能力来加速工作。我们从软件开发、安全到推动 HR 政策都在用。

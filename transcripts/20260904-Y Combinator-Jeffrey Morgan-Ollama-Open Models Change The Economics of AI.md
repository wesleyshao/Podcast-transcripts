**关于 open model 采用的更多细节：** 主持人：你们的云端图表看起来像是中国模型几乎占据了全部云端使用量，而本地模型里美国、中国和欧洲接近并列。这个差异应该怎样理解？

Jeffrey：云端 coding agents 解决的是很难的端到端任务，需要长 context、稳定工具调用和更大模型，因此目前主要由中国来源的 open models 满足。它们被全世界的企业访问，但不等于这些企业把数据发往中国。模型运行的地区、provider 的安全能力、客户的网络隔离和模型训练来源都需要分别检查。

本地模型则有另一种组合。用户可能运行早期 Llama 模型、Google 的 Gemma 模型，也可能运行欧洲或中国团队的模型。对于文档整理、分类、抽取和一些不太复杂的流程，本地模型已经足够好。对于 coding agent 这种需要不断试错、写测试和检查结果的工作，云端的大模型仍然更有效。未来不是本地与云端二选一，而是由 router 根据任务难度、延迟、隐私和预算做调度。

主持人：如果一个企业已经买了工程师的工作站，运行本地模型就不再是每 token 付费，而是把已经购买的硬件利用起来。

**关于模型发布的 day-zero 标准：** 主持人：一个新模型在 Ollama 上线前，模型团队需要配合哪些工作？

第三是云端容量和可靠性。发布第一天通常是增长最高的一天，不能等用户蜂拥而来后才临时寻找 provider。第四是硬件，模型要在 NVIDIA、Apple Silicon 等平台上以合理速度运行。Ollama 需要把模型、harness、云端 provider、硬件优化和开发者入口包装成一个整体。若只发布模型而没有足够容量，用户会以为模型质量很差；若只在某种硬件上快，其他开发者也会认为产品不可靠。

**从五层堆栈到更多隐藏层：** 主持人：传统 AI 基础设施常被概括为应用、模型、基础设施、芯片和能源五层。open models 是否多了一些层？

Jeffrey：模型层本身已经不只是权重。还有每个模型擅长的 orchestration、工具调用、推理 API、memory、sandbox 和应用 harness。Anthropic 平台团队强调的 knowledge、coordination、execution 也是这些隐藏层。知识层负责把公司的数据和 context 接到模型；协调层负责让一个请求分派给多个 sub-agent；执行层负责隔离代码、管理权限、提供计算并把结果返回。

前沿模型实验室希望把这些层都放在自己的 managed agents、memory 和 context 中，形成一体化服务。开放生态则会让开发者自由组合。两种架构不会马上有一个绝对赢家，客户会根据任务、合规要求和团队能力选择。Jeffrey 更看好 best-of-breed 的一部分，因为 open-source 生态往往在单个问题上做得更快、更专业。

**为什么 memory 和凭证不会完全进入模型：** 主持人：如果 coding agents 越来越强，软件中间层是否会被模型吞掉？

Jeffrey：很多 harness 功能确实会逐步进入模型本身。但凡涉及状态和存储，就很难完全进入模型。模型的训练周期可能是一月一次，而企业的数据库、客户权限、API credentials 和业务状态每分钟都在变化。记忆需要可更新、可删除、可审计；凭证需要隔离、轮换和最小权限。它们属于模型周围的系统，不是一次训练后就能固定的参数。

此外，open models 并没有闭源 provider 默认提供的全部 safety tooling。企业需要权限、沙盒、审批、日志、可回滚动作和内容安全层。企业真正需要的不是一个“绝对安全”的模型，而是能够知道模型在什么环境中运行，并能限制它能读取和执行什么。

**开源 token 的经济学：** 主持人：你认为 80% 到 90% 的 token 经过 open models，但只有 10% 到 20% 的成本由它们产生，这会不会导致企业扩大 token 使用？

这会带来一个“智能层级”的组织结构。router 可以先让便宜模型处理任务，遇到复杂部分再升级到 frontier model。多个 flash model 还可以在 coordination layer 中分工，一个负责规划、一个负责搜索、一个负责执行、另一个负责评价。这样产生的系统未必看起来像一个巨大的 AGI，但它可能在真实业务里更便宜、更可重复、更容易监控。

**Flash 模型与每个任务的成本：** Jeffrey：模型价格不应只看每 token 成本，还要看完成一项任务需要多少 token 和多少次重试。DeepSeek Flash 这类模型的意义在于，每 token 便宜，每 task 也便宜，而且速度快。它们可能只在 80% 的普通任务上达到足够水平，但这已经足以成为企业的 workhorse。

**模型来源与供应链风险的实际处理：** 主持人：如果模型会影响电厂、金融机构等关键任务，企业如何判断一个模型是否可信？

他没有听说已经确认的“木马候选人”式模型案例，但没有案例不意味着可以忽略风险。模型来源、训练数据、provider、运行地区和日志留存都要可追溯。企业想要的不仅是模型分数，还包括模型在关键任务上的可解释行为、可回滚执行和安全责任归属。

**Ollama 的产品-market fit：** 主持人：你们为什么在 2023 年没有立刻商业化？

**结语：开放生态的下一个瓶颈：** Jeffrey：开放模型的权重和 provider 越来越多，真正的瓶颈是把它们整理、组合并稳定交付。开发者不想研究一百个 provider 的计费方式，也不想为每个新模型重新修一套 API 和 harness。他们想把精力放在自己的下一家公司或下一个应用上。

因此，未来的价值可能出现在模型之上的 curation、路由、memory、coordination、执行安全和开发者体验。Ollama、OpenRouter、OpenCode 只是这一层的早期例子。模型会继续变快、变便宜、变强，但只有当整套系统可靠地工作时，token 成本下降才会转化成真正的企业生产力。

**开源模型成为企业采用的新方向：** 主持人：现在什么算是最先进的状态？你在实际使用数据里看到了什么？

Jeffrey：最明显的变化是，尤其在企业内部，市场正在转向 open models。这里既包括美国来源的模型，也包括中国来源的模型。推动转向的主要力量是 coding agents，以及更接近 AI 协作者的工作流，例如 OpenClaw 和 Hermes。它们让模型不只是回答一次问题，而是能够持续调用工具、获取数据、编写代码并完成一段较长的工作。

主持人：Ollama 处在许多 token 的流动路径上，所以你们比一般观察者更清楚用户到底在使用什么模型。趋势是什么？

Jeffrey：Ollama 最初是让用户在 MacBook、NVIDIA、AMD 或 Intel 硬件上运行 open models。今年早些时候我们推出了 Ollama Cloud。云端目前主要运行中国来源的模型，但访问者来自全世界，特别是美国和德国的企业。这里有一个容易被忽视的事实：模型的训练来源与模型最终运行的位置是两个不同问题。企业可以在美国或欧洲使用中国来源的模型，真正需要讨论的是数据在哪里处理、模型如何部署、运行环境是否安全，以及企业是否能理解模型的行为。

**成本只是入口，控制与定制才是长期目标：** 主持人：企业采用 open models，主要就是为了省钱吗？

Jeffrey：成本无疑是 open models 能够立刻解决的最大痛点，但成本只是短期理由。每个企业都有一个更长期的目标，就是对 AI 获得更好的控制，并把模型定制成适合自己业务的工具。企业可能先因为成本降低而采用 open model，之后会希望围绕自身数据、流程和独特任务进行定制。低成本让它们敢于尝试更多 token，也让定制不再因为每次调用都很贵而被迫停止。

主持人：有没有可以公开举例的企业？

Jeffrey：The Information 最近写过 AT&T 的案例。根据那篇报道，AT&T 已经把约 40% 的 token 消耗转向 open models，目前主要使用美国和欧洲来源的模型，也在评估中国来源的模型。实际工作流主要是 coding agents。每位开发者或用户的 token 用量增长，最早就是由 coding agents 推动的。

**从 coding agents 到长时间自动化：** Jeffrey：今年 3 月和 4 月，OpenClaw 开始快速增长，随后 Hermes agent 项目也增长很快。这些工具把一项能力带给了非开发者：把一个困难任务交给 open model，让它在较长时间里自己判断要使用哪些工具、抓取哪些数据并逐步完成工作。财务、客服、市场和销售团队都可以使用这种工作流。

主持人展示了一张 Ollama Cloud 的图，图中不是总用户数，而是每名开发者每周使用的 token 数量。Jeffrey 解释说，年初的第一段增长由 coding agents 推动。当时 Kimi、GLM、Minimax 等模型陆续出现，open models 第一次真正具备支持 coding agents 的能力。随后 OpenClaw 在 4 月带来第二个拐点，非开发者也开始把开放模型用于持续时间较长的工作。模型的 context window 从约 128K 扩大到一百万甚至更高，这进一步支持了长任务。

按照节目中的估计，单个用户的用量在关键阶段大约从一两千万 token 级别增长了数倍；把整个云端生态放在一起看，Ollama Cloud 自年初以来的 token 用量增长约 150 倍。这里的重点不是某一个模型的下载排名，而是当 token 足够便宜、context 足够长、工具调用足够稳定时，用户会把模型放进更多业务流程，需求会呈现非线性增长。

**微调周期、模型发布速度与安全：** 主持人：2024 年初大家都很热衷于 fine-tuning 自己的模型，后来又觉得模型发布太快，微调会被下一代模型淘汰。现在它似乎又回来了。你认为这是循环，还是已经成为长期能力？

Jeffrey：模型的发布速度越来越快。以 DeepSeek Flash 为例，原来可能需要六个月的模型周期，现在一个夏天里就能看到三次迭代。更新太快会让企业很难持续维护自己的定制模型，但工具也在变好，想做 fine-tuning 的团队有了更好的方法来跟上版本变化。与此同时，前沿实验室正在面对越来越多的 AI safety、alignment 和 containment 问题。如果闭源 frontier models 为安全而放慢速度，open-weight models 可能继续快速变强，因此两条路线的差距可能进一步缩小。

Jeffrey 提到，GLM53 的网络安全能力令人印象深刻。对创业公司和既有安全、治理服务商来说，这创造了机会，因为企业采用 open models 的主要障碍往往不是单纯的性能，而是安全、权限、审计与责任边界。如果这些问题能被解决，很多企业并不把“中国来源”本身视为不可接受的条件。

主持人：Hugging Face 最近还出现过一次有趣的事件。为什么 open models 在安全测试上可能比 frontier closed models 更适合？

Jeffrey：如果让某些闭源 agent 去对自己的产品做渗透测试，它们会拒绝，因为安全策略把攻击行为视为高风险。Hugging Face 上却能找到专门为安全研究训练、限制更少的模型，可以在明确的善意场景里主动寻找漏洞。即使是普通的 open model，也可能更好地理解“这是授权的安全测试，而不是恶意攻击”。这不是说安全约束不重要，而是企业有时需要可控地执行闭源模型不愿意执行的测试。

**把一次模型发布做成可用产品：** 主持人：Ollama 是模型的重要分发渠道，模型厂商往往会在正式发布前联系你们。一个成功的 day-zero 发布需要什么？

Jeffrey：模型发布越来越快，必须建立一套 playbook。第一步是让模型在常用 inference engine 中得到支持。这有时需要数周，需要确认模型运行得足够快、结果足够准确，并且与研究团队公布的 reference 行为一致。第二步是找到合适的 harness，也就是能把模型接入 coding agent、应用或 SDK 的运行框架。模型如果增加了多模态能力，周围的 harness 也必须改变，才能真正调用这些能力。

每个模型的架构、工具调用机制和输入输出格式都不一样，所以不能只把权重文件放出来就算完成。发布前要对最终版本做 benchmarks，确认模型与推理层、工具调用和参考实现相符。

Jeffrey 将完整的模型发布概括成三部分。第一是 harness，可以是现成的 harness，也可以是帮助开发者调用模型的 SDK。现在 open source harness 很丰富，Codeex harness 和 OpenCode 都是例子。第二是模型本身以及可靠的云端容量。day zero 往往是增长最快的一天，因此必须提前安排容量、稳定性、价格和地区。第三是硬件与 provider，需要和 NVIDIA 等硬件伙伴合作，也要针对 Apple Silicon 等平台做优化。一个很有能力的模型如果运行速度太慢，最终仍然不是好的开发者体验。

大量工作往往集中在发布前最后 24 小时。模型团队、推理 provider、硬件厂商、Ollama 和应用 harness 需要在很短时间内把一整套系统拼好，这更像一场 fire drill，而不是一次单纯的模型上传。

**Ollama 像 open-model 时代的操作系统层：** 主持人：这听起来像早期操作系统，需要同时适配驱动、硬件和应用。Ollama 是否在扮演类似角色？

Jeffrey：这个类比是成立的。Ollama 需要连接硬件、推理 provider、inference layer 和 application runtime，同时让 harness 与模型配合。组合数量非常大，所以问题很难。随着时间推移，我们会积累一套共用运行时，让任意 harness 能够更快地匹配任意模型、测试并发布。

Ollama 团队很多成员来自 VMware、Docker 和其他网络或基础设施公司。我们未必都是 AI research 背景，但熟悉传统 compute 问题，而这些问题正在 inference 世界重新出现。最终仍然要回到 developer experience：开发者发出 API 请求后，token 能否稳定、快速、按照预期返回，所有层是否能够协同工作。

前沿模型实验室常把完整的堆栈准备好，包括应用、模型、基础设施与 inference、芯片和能源。对于 open models，模型权重之外还有许多隐藏层，包括模型独特的编排组件、开发者 API、工具调用和运行时。Ollama 的作用不是亲自完成每一层，而是把它们编排在一起，让开发者使用开放模型时拥有接近 day-zero 的完整体验。

**模型之上的三层：知识、协调和执行：** 主持人：模型和应用之间的隐藏层会不会拆出来，变成独立公司或服务？

Jeffrey：会。Anthropic 的平台团队曾经把这里分成三个问题。第一是 knowledge，如何把企业自己的数据和 context 接到模型上。第二是 coordination，当 cloud app 或 coding agent 派出一批 sub-agents，有些在云端、有些在本地时，谁来协调它们。第三是 execution，也就是 sandbox、权限和计算资源，尤其是越来越多 agent 迁移到云端之后，如何安全地执行任务。

传统云计算一开始把很多能力捆在一起，但开发者最终偏好每个问题上的 best-of-breed 产品。前沿模型实验室希望用户留在自己管理的 agent、context 和 memory garden 里，而 open source 开发者不希望被关在一个封闭花园里。两种模式可能长期并存。

现在 open model token 变得充足，真正稀缺的反而是 token 之上的编排、记忆、执行和可靠性。过去软件的护城河之一是开发者很难维护一套经过完整测试、能满足用户需要的软件。但 coding agents 本身越来越强，可能只需一个 Markdown 文件和一些 TypeScript，就能不断同步自己的 memory system。模型之间通过 MCP 等接口连接后，锁定效应可能下降。

Jeffrey 认为，memory 是一个不会完全下沉到模型权重中的层。只要问题具有状态、需要存储最新数据，模型训练就无法替代外部存储。模型可能每月更新，但企业的权限、凭证、业务记录和长期记忆每天都在变化。凭证管理、安全和权限控制尤其不能被简单交给一个模型。

**企业的稳态：大多数 token 用开放模型，最难任务仍交给 frontier：** 主持人：企业最终会如何在 frontier closed models 和 open models 之间分配预算？

Jeffrey：他的判断是，企业内部 80% 到 90% 的 token 最终会经过 open models，但这不代表 80% 到 90% 的预算也会花在 open models 上。开放生态正在做的事是降低成本，因此企业可能只为 open models 支付总成本的 10% 到 20%，却让大多数日常 token 通过它们。低成本会让企业不再限制团队使用 token，反而给更多人更多调用额度。

最困难的任务仍会保留给 frontier labs，因为那里聚集了很多最强的研究人员。中间任务则可能由 open 和 closed models 共同完成。企业可以使用一个 router，把复杂调度和最难的推理交给 frontier model，把大量 line-item work 交给 open model。Sakana AI、OpenRouter 等项目已经展示了这种组合效果。

这种模式很像律师事务所：partner 负责最难的判断，再把大量工作分派给 associates。它也像云计算里 DynamoDB 与 PostgreSQL 的组合，不是所有东西都必须来自同一个供应商。模型能力越强，客户越希望有一个独立 router 来决定什么时候使用哪个模型，而不是由拥有模型的实验室单方面决定。

**本地模型与云端模型的混合执行：** 主持人：你们既有 cloud-hosted models，也有运行在笔记本上的 local models，实际客户如何使用它们？

Jeffrey：最终是混合模式。比较简单的任务可以在本地运行，延迟低、隐私更强、单 token 成本也低。用户先购买硬件，再把硬件和云端模型配合使用。近几代硬件已经能很好运行 20B 到 40B 参数的模型，有时甚至能运行 128B 参数模型。

主持人提到，字幕中记录为 “Quinn 3.8 38B” 的模型在 coding benchmark 上已经接近或达到 Opus 4.6。Jeffrey 表示，根据 benchmark，它可以在并非最高内存配置的 MacBook 上运行，这说明本地能力正在快速提升。

实际使用中，coding agents 仍更适合大型云端模型，因为它们要写代码、写测试并解决很难的端到端问题。文档处理等更直接的 workflow 则非常适合本地模型。企业可以建立一个 router，把简单任务放在本地，把困难任务送到大型 cloud model。这样不仅因为 open model 在云端更便宜，也因为企业可以在已经购买的硬件上近乎免费地运行一部分任务。

Ollama 看到本地模型同时使用美国、欧洲和中国来源的模型，比例比较接近；但云端 coding-agent 模型目前主要是中国来源的模型。Jeffrey 认为，美国需要有更多实验室推出大模型。

**NVIDIA、Apple Silicon 与桌面计算：** Jeffrey：NVIDIA 很有意思。它的护城河不是一定要建立新的软件业务或亲自出售 token，而是持续发布 open source、帮助生态，然后通过生态发展保持硬件优势。NVIDIA 的 DGX 系列和面向桌面的 DGX Spark，让企业可以把高性能模型放在工程师桌面上。

节目讨论了 DGX Spark 使用 GB300、约 128GB unified memory，可以运行 20B 到 120B 参数级别模型。多台设备可以通过高速网络连接起来，像一个小型数据中心一样运行更大的模型。银行和工业企业已经在工程师桌上部署大量 NVIDIA workstation GPU，过去这些设备常用于 CAD 等任务，下一代设备也可能转向本地 AI。

Apple Silicon 方面，MLX 项目已经形成较成熟的技术栈，能在 Mac Studio 以及更小的 Mac 上运行 LLM。Jeffrey 认为 Apple 和 NVIDIA 都在推动个人桌面计算的复兴。Ollama 的旅程是从本地开始、因 coding agents 转向云端，但随着硬件追上模型，coding agent 的体验也会重新回到本地。未来用户可能在桌面上获得接近旧式 GitHub Copilot 的毫秒级代码反馈，同时在需要时调用云端模型。

**GPU 供给与开发者抽象层：** 主持人：运行 Ollama Cloud 需要大量 GPU。GPU 市场现在怎样？

Jeffrey：价格变化很快，供需波动很大。对创业公司来说，获得运行最新模型所需的 B200、B300 很困难。Ollama 与多个 inference provider 合作，把 GPU 集合起来满足需求，但这需要持续判断哪个模型应该部署在哪个地区、速度应该是多少、客户能接受的 latency 是多少，还要平衡成本与容量。

这也是 OpenRouter、Ollama 和 OpenCode 重要的原因。普通开发者不必为了使用一个新模型，提前谈判 B200 或 B300 的价格，不必根据 24 个月预测去签 GPU 采购合同。provider 把复杂的硬件、区域、容量和模型路由封装起来，让创业团队以较低前期成本获得大量 token。

**给资金有限的 AI 创业者的建议：低成本、低任务成本和无限 token：** 主持人：如果现在从零开始做 AI 创业，没有多少融资，怎样用有限预算获得更多 token？

Jeffrey：要关注一类新模型，它们不仅每 token 价格低，而且每个完整 task 的成本也低。DeepSeek Flash 是重要例子。模型行业年初首先解决的是 intelligence gap，open models 已经逼近 frontier，差距可能只剩不到三个月；下一步是 extreme efficiency，让模型以足够低的成本服务很高的 token 用量。

他把这类模型比作 workhorse models。它们不一定解决世界上最难的问题，但对 80% 的任务已经足够好、速度快、成本低，用户可以不再时刻计算自己发了多少请求。更便宜的模型还可以被串联起来：一个模型负责检索，一个模型负责规划，一个模型负责执行和检查。多个普通模型通过 coordination layer 组合起来，可能完成单个更大模型才能完成的任务，而且成本更可控。

主持人：过去关于 AGI 有一种“god model”观点，认为一个巨大模型会完成所有事情，但目前似乎是许多小模型和编排层胜出。

Jeffrey：对于大多数客户，模型达到某个 good-enough 阈值之后，继续提升智能水平不是每个任务都需要的。最强模型仍会打开一些新的能力，有时也会带来风险，但日常业务更适合稳定、快速、便宜的模型。open model 可能出现 god-tier model，Zoo AI、GLM 等团队已经在一些任务上达到 frontier 水平；Kimi 在 web development 上的表现也曾经成为市场冲击。竞争正从“open 与 closed 之间的巨大鸿沟”变成逐项 head-to-head 比较。

**模型来源、运行位置与地缘政治：** 主持人：如何看模型地缘政治？

Jeffrey：用户关心的不只是模型从哪里训练出来，也关心它在哪里运行、如何运行、是否处于安全环境。有些美国客户主要关心数据在哪里处理；另一些客户则非常在意模型来源，因为模型说话的方式、价值判断和训练数据都会影响使用体验。

更重要的是，企业需要理解端到端的数据来源。Ollama 看到有关键基础设施使用 open model，例如有公开文章提到某模型被用于分析芬兰一家电厂的数据、检测用电高峰并帮助保持供电稳定。在 mission-critical task 中，模型来源、数据路径、运行环境、可审计性都必须被理解。

主持人：如果中国来源的模型托管在美国，怎样确认它没有被植入恶意行为？

Jeffrey：他没有听说过已经确认的 “Manchurian candidate” 式案例，但这类担忧与软件供应链污染并不新。一个普通应用可能依赖数千个 open-source package，只要一个依赖被污染，整个应用就可能出现安全问题。模型更加不透明，因此企业要用安全检查、运行隔离、行为测试和权限控制筛选模型。按照他从 Fortune 500 客户那里听到的情况，只要流程足够稳健，这个问题可以被管理，但不能被忽略。

**Ollama 的起点：从 Docker、Kubernetes 到本地大模型：** 主持人：你和联合创始人过去来自 Docker，Ollama 看起来像是建立在很强的开发者体验和基础设施能力上。故事是怎样开始的？

Jeffrey：他和联合创始人 Michael 过去在 Docker 做过 Docker Desktop，因此很了解如何把复杂系统做成开发者可以直接使用的产品。Ollama 早期并没有明确的最终方向。团队曾经在 Kubernetes 身份与安全、开发者桌面安全等方向上尝试过。两位创始人是滑铁卢大学同学，也曾一起创建上一家公司，后来很早被 Docker 收购。

他们在 2021 年冬季申请 YC 时，写的方向更像是“Kitematic for Kubernetes”或“Docker Desktop for Kubernetes”。当时他们还没有找到真正让团队兴奋的用户问题。2022 年与 Benchmark 合作完成 Series A 时，ChatGPT 尚未出现，团队强调的是开发者体验和 Kubernetes 安全。他们与 Benchmark 合伙人 Peter 之前在 Docker 阶段就认识，因此投资人更多看重团队的能力和长期方向，而不只是当时解决的某个窄问题。

Ollama 直到 2023 年 7 月、Llama 2 发布前后才推出。名字不完全是因为某一个 Llama 模型，而是 LLM 与动物角色结合，代表 open models。团队希望有一个容易记忆、可以成为开发者产品形象的名字。

**在“荒野”里寻找问题：** 主持人：从云端 token 图来看，Ollama 像是在 2026 年 2 月才突然爆发，但实际上你们从 2021 年就在做。多年没有真正起飞时，团队是什么感受？

Jeffrey：那段时间很害怕。最重要的问题不是项目是否上新闻，而是团队是否真的解决了某个客户问题。他们反复与开发者通话，却总感觉还没有完全契合。找不到 north star 比知道自己想解决什么更令人不安，因为你往往知道自己想带来好的开发者体验，却还没有找到恰当的问题。

团队从 Kubernetes 安全转向桌面开发者安全，再转到本地模型。这个路径以前没有公开完整讲过，但回头看，每次转向都保留了同一个核心：开发者希望复杂系统可以真正运行起来。模型出现后，团队第一次在本地运行 Llama，发现安装和运行极其困难，便意识到这里有一个明确问题：让任何人都能把 open model 跑起来。

他们在多伦多和 Palo Alto 的团队成员一起开会，问自己：如果今天完全从零开始，会做什么？他们看到两个问题。第一，能不能建立一个网关，让用户无缝访问任何模型并选择运行位置。第二，团队过去来自 VMware 和 Docker，擅长让复杂系统运行起来，能不能把这种能力用于 open models。于是他们给自己两周时间发布第一版 Ollama。Llama 2 恰好在两周结束时发布，团队决定直接上线。

这次行动与之前两年反复思考客户和产品形成鲜明对比。上线后，开发者在 Reddit 和 local LLM 社区主动传播 Ollama。它很快达到 10 万 GitHub stars，速度比 Docker 和 Kubernetes 当年更快。Jeffrey 说，创业者常常无法准确解释 product-market fit 为什么发生，但当用户开始主动喜欢并传播产品时，感觉就像一个 zero-to-one 的瞬间。

**从爱好者到企业：** Ollama 最初的用户是想在自己的机器上运行模型的 hobbyist，他们自己组装硬件、尝试不同权重。由于模型可以免费开始、能在任何地方运行，企业 IT 开发者也不需要先经过层层审批，就能先试用。原本对 hobbyist 有吸引力的特性，很快转化成 Fortune 500 开发团队的采用。

Jeffrey 把这与 MongoDB 等数据库的路径做比较：数据库最早服务开发者，随后进入企业。LLM 具有无状态特征，也降低了从个人试用到企业试用的迁移难度。但一旦从本地转向云端，企业还要考虑经济性、安全性以及模型到底在哪里运行。open models 的优势是，不论 hobbyist 还是企业开发者，都可以先开始，而不必先获得某个中央部门的许可。

**两年没有收入与商业化：** 主持人：2023 年 Llama 2 带来大量用户和 10 万 GitHub stars，但当时主要是 Reddit 上的爱好者，没有收入，也没有清晰商业模式。两年里你们怎么想？

Jeffrey：团队一直看到两条可行路径。第一是 privacy-focused AI product，这是 Ollama 开源版本一开始就包含的价值。第二是等 open models 具备闭源模型那样的产品级 product-market fit。模型最初还没有成熟的 tool calling，很多重要任务仍必须使用 frontier models。团队担心过度等待会培养出不重视商业化的文化，但他们从 Docker 的经历中知道这个风险，因此持续和真实客户沟通，而不是把用户当成互联网上一个没有面孔的数字。

今年 coding agents 开始使用 open models，最大的 AI 消费场景和开放模型能力终于匹配起来。Ollama 因而推出 cloud 方向，解决企业如何以隐私、安全、可控的方式访问难度最高的 open models。Jeffrey 强调，本地运行是故事的一部分，却不是整个故事；真正重要的是企业如何接触到可以解决困难问题的开放模型。

**YC 同行网络与避免重复犯错：** 主持人：你们是第二次创业，为什么仍然选择 YC？

Jeffrey：创业本来就很孤独，即使有很好的联合创始人也一样。Michael 是他第一家公司和 Ollama 的联合创始人，也是大学室友，但团队仍然需要一群同行。疫情期间参加 YC，创始团队每周与 Jared 以及其他几组创始人交流，这让团队不再觉得自己独自面对问题。后来来到湾区，YC 网络让他们接触到更多正在做 open models、AI 和开发者工具的创始人。

YC 社区的另一个价值是创始人愿意透明地讨论曾经犯过的错误。Jeffrey 仍与 Docker 的创始人保持联系，对方也是 Ollama 的投资人。团队可以复盘上一代公司的困难，把有效的方法带到下一家公司，避免重复那些可能导致公司失败的错误。对年轻创业者，他建议至少在一个真正把技术交付给大量用户、拥有清晰 product-market fit 的团队里工作过一次。哪怕只有一到三个月，也能学到什么是质量标准、bug 数据库、发布流程、长期维护和团队责任。

Jeffrey 认为，这种“看过好产品如何工作”的经验在 AI 时代尤其重要。AI 给团队很大能力，却不会自动让团队对长期质量负责。一个软件如果被用户喜爱并连续使用两年，团队必须知道它如何升级、如何保持兼容、如何处理旧版本。Ollama 的 VMware、Docker 和其他基础设施工程师带来了这类 muscle memory。

**AI 时代被打破的基础设施规则：** 主持人：从基础设施到云服务，再到 AI，有哪些传统规则不再成立？

Jeffrey：一条旧规则是，创业公司如果只是叠在别人的基础设施上，就处于脆弱位置。过去很多人认为平台层上面的公司容易被下方供应商替代。但在 AI 世界，向上靠近客户有时反而更好，因为价值不只在底层模型，而在开发者如何使用它。Ollama 需要把模型、provider、硬件、harness 和应用协调好，距离客户越近，越能理解真正的痛点。

另一条变化是，传统 systems engineering 强调所有行为都应完全确定、经过测试和验证；LLM 天生具有一定非确定性，这在很多场景不是 bug，而是能力的一部分。团队需要围绕非确定性重新设计产品和测试，而不是试图把模型变成一块完全固定的传统软件。

AI 还改变了人员配置。过去云服务和客服流程可能需要很多工程师，现在一些问题可以由 AI agent 辅助完成。但这并不意味着不需要工程能力，因为没有任何一位工程师可能完全知道生成式系统中所有代码的行为。企业需要新的运营、评估、监控和责任边界。

**开放模型生态的稀缺性从权重转向整合：** 主持人：如果没有 Ollama 这样的中间层，开发者会遇到什么？

Jeffrey：底层 inference provider 可能有未文档化的参数、奇怪的 JSON 要求或特定输入会触发的错误。agent 最终可能猜出解决办法，但开发者会先花几个小时撞墙，得到很差的体验。Ollama 的工作之一，就是把分散的模型、推理技术、云服务和 harness 进行 curation，变成真正能工作的产品。

OpenRouter 是另一个例子：开发者不必分别注册数十甚至上百个 provider，可以通过一个入口选择模型、统一付费。OpenCode 则可以让一个 harness 集成多个模型，方便开发者尝试下一代模型，看它是否更适合自己的任务。当模型和 provider 变得充足，稀缺的就变成如何把它们组合成稳定、易用、可维护的系统。
